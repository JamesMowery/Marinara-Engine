# Аудит очистки кода

**Дата аудита:** 2026-07-22

**Целевая ветка:** `staging`

**Цель:** найти артефакты, которые можно удалить, и ограниченные упрощения, не меняя поведение во время работы.

**Статус реализации:** находки с высокой уверенностью и низким риском выполнены в рамках той же очистки.

## Итоги реализации

Сделано:

- удалены четыре недостижимых модуля исходного кода, устаревший сборщик sidecar, средство запуска тестов без тестов и завершенные описания задач;
- удален буфер отладочного журнала, который существовал только для недостижимой панели отладки, при этом диагностика в консоли браузера сохранена;
- закрыты все 60 находок неиспользуемого кода, подтвержденных компилятором, и включены проверки неиспользуемого кода в клиенте и на сервере;
- удалены 53 невостребованных клиентских хука, вспомогательных функции, типа и объявления интерфейса – пакетами по предметным областям;
- удалены восемь осиротевших зависимостей с высокой уверенностью, а также исправлены файл блокировки, проверка установки рабочего пространства и текст по устранению неполадок;
- корневая команда `pnpm test` теперь запускает реальные регрессионные проверки, а не сообщает об успехе при нуле тестов;
- переиспользован существующий выбор ключевого кадра раскадровки, а дублированная логика токенов запроса Spotify объединена;
- переупорядочивание переменных пресета ограничено запрошенным пресетом: ранее игнорировавшийся `presetId` теперь работает как граница целостности.

Сознательно оставлено для отдельной работы по совместимости или продукту:

- `@rollup/wasm-node`;
- серверные экспорты, которые могут быть внешними API или точками подключения тестов;
- объединение парсера PNG и геометрии обучающих подсказок;
- крупные переработки редакторов, поля ввода и больших модулей;
- поля совместимости, запланированные к следующему мажорному выпуску.

Подробные находки ниже сохранены как свидетельства состояния до изменений. Там, где остались формулировки в виде рекомендаций, приоритет имеет этот раздел об итогах реализации.

## Проверка

Выполненная очистка прошла все поддерживаемые в репозитории способы проверки:

- `pnpm install --frozen-lockfile`
- `pnpm check` (контроль неиспользуемого кода, TypeScript, ESLint и продакшен-сборки)
- `pnpm test` (все регрессионные наборы плюс дымовые проверки в браузере: 81 пройден, 51 пропущен намеренно)

Браузерный набор попутно вскрыл четыре предположения о поиске элементов, зависевшие от состояния, – это выяснилось, когда общая команда тестов стала честной. Теперь эти тесты переходят к нужному экрану явно, разграничивают дублирующиеся мобильные элементы управления и обращаются к настоящему прокручиваемому блоку ленты Noodle, не ослабляя при этом свои продуктовые проверки.

## Краткая сводка

Репозиторий большой (1665 отслеживаемых файлов и примерно 478 000 строк по рассмотренным типам файлов с исходным кодом), однако большинство крупных файлов – это работающий код продукта, а не очевидный мусор. Самый безопасный путь очистки – набор небольших удалений, каждое со своим доказательством, а не масштабная переработка.

Первая линия очистки в исходном аудите выявила:

- четыре модуля исходного кода, на которые никто не ссылается (899 строк суммарно);
- один устаревший скрипт сборки sidecar (173 строки);
- одно средство запуска тестов, которое завершается успешно, не выполнив ни одного теста (54 строки плюс привязка в скриптах пакета);
- два завершенных описания задач по этапам, оставшихся в корне репозитория (235 строк);
- 60 неиспользуемых объявлений, импортов, параметров и локальных переменных, подтвержденных компилятором;
- восемь вероятно осиротевших прямых зависимостей – при условии проверки чистой установкой и сборкой;
- один вероятно неиспользуемый статический спрайт Mari – после дымовой проверки в браузере.

Только четыре недостижимых модуля, устаревший скрипт, ничего не делающее средство запуска тестов и описания задач дают 1361 отслеживаемую строку. Предложенную работу все же стоит разбить на небольшие PR по очистке, чтобы у каждого удаления было узкое доказательство и простой откат.

## Как проводился аудит

Аудит опирался на несколько видов свидетельств:

1. Инвентаризация всех отслеживаемых файлов, типов файлов, основных областей исходного кода и самых больших файлов.
2. Анализ импортов и экспортов по дереву TypeScript (AST), включая относительные импорты и псевдонимы репозитория.
3. Поиск точных имен и названий файлов по всему отслеживаемому исходному коду, скриптам, документации, манифестам и рабочим процессам.
4. Пробные запуски компилятора TypeScript с принудительно включенными `noUnusedLocals` и `noUnusedParameters` для клиента и сервера.
5. Поиск по прямым зависимостям плюс точечный разбор истории Git там, где зависимость или скрипт выглядели брошенными после прежней переработки.
6. Сравнение нормализованных окон текста на дубликаты, а затем ручной разбор самых заметных совпадений.
7. Проверка синтаксиса отслеживаемых файлов JSON, Python и Bash.

Метки уверенности, которые используются ниже:

- **Высокая:** несколько независимых проверок сходятся; удаление должно быть механическим.
- **Средняя:** ссылок сейчас нет, но динамическая загрузка, внешние потребители или продуктовый замысел все же могут иметь значение.
- **Отложить:** законная возможность упрощения, но область возможных регрессий слишком широка для прохода по удалению артефактов.

Статический анализ не может доказать, что нигде нет поиска по строке во время работы, использования скачанного пакета, путей, заданных пользователем, или внешних потребителей. Такие случаи отмечены отдельно, а не отнесены к мертвому коду.

### 1.2 Устаревший скрипт сборки sidecar

На `scripts/build-sidecar-runtime.mjs` не ссылаются ни скрипты пакета, ни рабочие процессы, ни документация, ни исходный код. **Рекомендация (высокая уверенность):** убрать их из рабочего дерева. История остается доступной в Git. Если какое-то обоснование все еще ценно, перенесите только это обоснование в подходящий документ по архитектуре, а не сохраняйте инструкции по задачам.

### 1.4 Обманчивое средство запуска тестов без тестов

Это опаснее обычного мертвого кода: зеленый результат `pnpm test` сейчас подразумевает покрытие, которого нет.

**Рекомендация (высокая уверенность):**

1. Удалить серверное средство запуска тестов и серверный скрипт `test`.
2. Оставить проверку структуры установщика для Windows, но при необходимости дать ей честное собственное имя.
3. Переопределить корневой `test` так, чтобы он запускал осмысленный набор регрессионных и дымовых проверок, либо убрать общий псевдоним и описать в документации `pnpm check`, `pnpm regression:*` и `pnpm smoke:ui` как настоящие команды проверки.
4. Исключить возможность того, что CI сообщит "tests passed" только на основании запуска без тестов.

На `@rollup/wasm-node` в клиенте тоже нет ссылок, но это может быть резервный вариант Rollup для отдельных окружений. Считайте эту находку **средней уверенности**: изучите историю упаковки и CI, а перед удалением докажите, что сборка проходит на всех поддерживаемых платформах.

Не относите к неиспользуемым такие зависимости, как `workbox-window`, `pino-pretty`, корневой `esbuild`, пакеты типов или инструменты только для командной строки, лишь потому, что в коде не нашлось текста импорта. Для PR по зависимостям обновите `pnpm-lock.yaml`, установите все с чистого состояния и прогоните полную линию сборки и проверок. Удаление пакета из уже заполненного дерева `node_modules` доказательством не считается.

## 6. Ограниченные упрощения

Это улучшения удобства поддержки, а не удаление мертвого кода. Каждое должно в точности сохранять поведение и иметь узкое регрессионное доказательство.

### 6.1 Точно или почти точно продублированная бизнес-логика

1. **Выбор ключевого кадра раскадровки – низкий риск.** В `GameSurface.tsx` есть локальная реализация `findStoryboardKeyframeForSegment`, совпадающая с экспортируемой `findReplayStoryboardKeyframe` в `lib/game-session-replay.ts`. Переиспользуйте функцию из библиотеки и удалите локальную копию.
2. **Нормализация поиска Spotify – низкий или средний риск.** `SPOTIFY_STOP_WORDS`, `SPOTIFY_MOOD_EXPANSIONS` и сам процесс расширения дублируются в `game-spotify-music.service.ts` и `tool-executor.ts`. Вынесите небольшую вспомогательную функцию для токенов запроса Spotify, чтобы два пути не могли разойтись.
3. **Извлечение метаданных карточки персонажа из PNG – средний риск.** `extractCharaFromPng` реализован независимо в `import.routes.ts` и `st-bulk.importer.ts`. Вынесите одну серверную утилиту и проверьте на регрессионных примерах обычные текстовые блоки, международные текстовые блоки, данные в base64 и в сыром виде, карточки V2 и V3, а также испорченные файлы PNG.
4. **Геометрия всплывающих подсказок в обучении – средний риск.** `GameTutorial.tsx` и `OnboardingTutorial.tsx` дублируют логику пересечений и размещения. Вынесите только общий расчет геометрии; правила для мобильных устройств и продуктовые особенности каждого обучения оставьте явными параметрами.
5. **Нормализация правки игрового фрагмента на клиенте и сервере – средний или высокий риск.** Чистая нормализация в клиенте и на сервере похожа. В общий код переносите только то, что действительно не зависит от среды выполнения – схему или нормализатор; разбор данных и сохранение оставьте на сервере.

### 6.2 Большие повторяющиеся области интерфейса: широкое объединение отложить

- `CharacterEditor.tsx` и `PersonaEditor.tsx` содержат заметно повторяющийся процесс управления спрайтами.
- `ChatInput.tsx` и `ConversationInput.tsx` повторяют логику направляемого плана и поля ввода.

Смысл в объединении действительно есть, но слияние любой пары целиком создало бы огромную область возможных регрессий. Выносите по одному целостному хуку или компоненту за раз – для редакторов начните с управления спрайтами, для полей ввода с направляемого плана – и после каждого выноса проверяйте в браузере оба места использования.

### 6.3 Работающие точки повышенной сложности

Самые большие работающие модули – это `server/routes/game.routes.ts`, `client/components/game/GameSurface.tsx`, `client/components/chat/ChatSettingsDrawer.tsx`, `server/routes/generate.routes.ts` и `client/components/panels/SettingsPanel.tsx`. ## 7. Что сознательно исключено из очистки

- Поля совместимости, явно принятые на весь ряд выпусков 2.x: формы совместимости для стиля изображений, состояния игры, синтеза речи, трекера персон и контекста режима Conversation. Удалять их можно только через миграцию с изменением версии в следующем мажорном выпуске.
- Сгенерированные реестры и манифесты возможностей. Пересоздавайте их своими скриптами, не правьте вручную.
- Код скачиваемых пакетов агентов Illustrator, Music DJ, Lorebook Keeper и остальных. Очистка среды выполнения и промптов, принадлежащих агентам, относится к `Pasta-Devs/Marinara-Agents`; здесь остается только их встраивание в приложение.
- Модули Home Assistant в `custom_components` – их обнаружение построено на соглашениях об именах и манифестах.
- `MarinaraLauncher.exe` – его использует код миграции ярлыков на панели задач.
- `start-local.bat` – на него не ссылаются скрипты пакета, но он вполне может служить человеку для локального запуска. Удаляйте только после уточнения замысла у сопровождающих.
- Объявления схем, которые выглядят неиспользуемыми, но выполняются при инициализации модуля или регистрации таблиц.
- Серверные маршруты – только потому, что не используется удобный хук React. Их все еще могут вызывать скачиваемые пакеты или потребители API.

## 8. Рекомендуемый порядок очистки

Работа должна остаться простой и удобной для проверки:

1. **PR A – артефакты:** удалить четыре недостижимых модуля, устаревшую запись о компоненте в документации, устаревший скрипт sidecar, завершенные описания задач и – после ручного подтверждения – неиспользуемый спрайт Mari.
2. **PR B – честная картина тестов:** удалить средство запуска тестов без тестов и переименовать или переопределить скрипты пакета так, чтобы успешные команды означали настоящие проверки.
3. **PR C – очистка по компилятору:** закрыть 60 диагностик TypeScript, затем включить проверки неиспользуемого кода в настройках клиента и сервера.
4. **PR D – зависимости:** удалить восемь пакетов с высокой уверенностью, исправить проверку установки рабочего пространства и текст по устранению неполадок, пересоздать файл блокировки и доказать, что чистая установка и сборка проходят.
5. **PR E и далее – пакеты по областям:** удалять неиспользуемые клиентские экспорты по предметным областям, а затем по одному разбирать дубликаты вспомогательных функций с низким риском.

Не смешивайте в одном PR по очистке удаление зависимостей, широкую переработку интерфейса и разбор маршрутов.

## 9. Таблица проверок

Для каждого изменения выполняйте подходящую проверку:

- Любая очистка кода: `pnpm check`.
- Изменения в общем коде или крупные серверные: сначала `pnpm regression` либо узкая команда `pnpm regression:<domain>`, а перед слиянием – полный набор.
- Очистка компонентов и хуков интерфейса: `pnpm smoke:ui` плюс ручная проверка затронутого сценария в браузере.

- Очистка зависимостей: чистая установка по файлу блокировки, `pnpm check`, продакшен-сборки и CI на поддерживаемых платформах.
- Объединение импорта PNG: прямые регрессионные проверки импорта на корректных и испорченных карточках персонажей.
- Файлы выпуска и версий, если они неожиданно затронуты: `pnpm version:check` и `pnpm credits:check`.
