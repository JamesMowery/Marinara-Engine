# Game Modeのルールセットを作成する

ルールセットは卓上ゲームの仕組みをGame Modeに伝えます。判定で振るダイス、キャラクターシートの項目、消費するリソース、休息で回復するものを定めます。このガイドは独自のルールセットを作って共有したい方向けです。他の人が作ったルールセットで遊ぶには、[ルールの選択](../game/getting-started.md#choosing-rules)から始めてください。

ルールセットは1つのJSONファイルです。コードではなくデータで、中の内容は実行されないため、インポートしてもコンピューター上で何かを実行することはありません。他の人のファイルをインポートする前に注意して読むべき部分はGame Master向けの文章です。そのルールセットを使うすべてのゲームで、モデルへ送られるためです。

## 最初に読むこと: ルールセットでできることとできないこと

ルールセットが埋められるのは、Engineがすでに理解している仕組みの設定値だけです。現在Engineは2種類の判定方式を持ち、ファイルの`resolution.kind`で選びます。

- **`dice-sum`**: ダイスを振り、シートの数値を加えて、難易度以上を目指します。d20方式、2d6に能力値を加える方式など、多くのシステムを扱えます。
- **`dice-pool`**: キャラクターの数値に応じた個数のダイスを振り、目標に届いたものを数えます。評価値がボーナスではなくダイスの個数を表す方式に対応します。

どちらも[判定方式](#resolution-kinds)で詳しく説明します。

どちらの形にも収まらない仕組みは、ルールセットファイルでは表現できません。プール内の最大出目の採用、目標以下を成功とするパーセンタイル判定、記号ダイス、対抗プールなどが例です。これらにはEngine内の新しい判定方式が必要で、JSONファイルではなくテストを伴うコードの貢献になります。必要な場合はEngineリポジトリに機能要望を開き、計算過程を示したロール例をいくつか添えて仕組みを説明してください。その例がテストになります。

Game ModeはMarinara独自の戦闘か、ルールセットの規則で戦闘を解決できます。任意の`battle`ブロックはキャラクターシートの数値をMarinaraの戦闘へ貸し出します。[戦闘への橋渡し](#battles-lending-the-sheet-to-marinaras-combat)を参照してください。任意の`combat`ブロックは、ルールセットが戦闘を解決する方法そのものを定義します。[独自ルールの戦闘](#combat-a-fight-your-own-rules-resolve)を参照してください。Engineは現在これらの規則で戦えます。ゲームのCombat PreferenceでClassic表示を選び、ルールセットが距離を定義する場合はTacticalの戦場も選べます。

## クイックスタート

1. 使用する判定方式に合うサンプルをコピーします。[`ember-roads.json`](https://github.com/Pasta-Devs/Marinara-Engine/blob/staging/docs/examples/rulesets/ember-roads.json)は3つの能力値を持つ小さな2d6システムです。この形式がd20や6能力値を前提にしていないことを示します。[`gravewatch.json`](https://github.com/Pasta-Devs/Marinara-Engine/blob/staging/docs/examples/rulesets/gravewatch.json)は3つの評価値と6つの専門技能を持つ、小さな10面ダイスプールです。大規模な例は、[`ruleset-5e-2014.example.json`](https://github.com/Pasta-Devs/Marinara-Engine/blob/staging/docs/development/ruleset-5e-2014.example.json)の5e (SRD 5.1)を参照してください。
2. `id`を独自のものに変えます。`ember-roads`のように、小文字、数字、単独のハイフンで構成します。
3. シート、休息、Game Master向けの文章を編集します。
4. インポートします([ルールセットを試す](#trying-your-ruleset)を参照)。保存前にファイル全体を検査し、問題を行ごとに示します。
5. 新しいゲームを作成し、**Rules**(ルール)で作成したセットを選び、いくつか判定を試します。

入力中の補助を有効にするには、外側の波括弧の内側の先頭行に次を加え、エディターへJSON Schemaを指定します。

```json
"$schema": "https://raw.githubusercontent.com/Pasta-Devs/Marinara-Engine/staging/docs/extending/ruleset.schema.json",
```

スキーマは入力中のキーの誤字や型の間違いを検出します。スキルが指定する能力値など、ファイル内の名前が実在する項目を指すかは検査できません。それはインポート時に検査します。

ファイル内のどのオブジェクトにも`"$comment": "..."`を加え、メモを残せます。Engineは無視します。

## ファイルの構成

| キー | 内容 |
| --- | --- |
| `schemaVersion` | 常に`1`です。 |
| `id`, `version` | Engineが使うルールセット名と、変更を公開するたびに増やす整数です。 |
| `name` | セットアップウィザードに表示する名前です。 |
| `edition` | 任意です。版や草案を説明する1行です。 |
| `license` | 任意です。SPDX IDと、元資料が要求する帰属表示です。 |
| `coverage` | 対応範囲と、ウィザードに表示する1行の要約です。 |
| `resolution` | 判定やセーヴのロール方法です。 |
| `sheet` | キャラクターシートの全項目です。 |
| `rests` | 各休息が回復・解除するものです。 |
| `gm` | Game Masterモデルに渡す文章と、各キャラクターについて見せるシート値です。 |
| `catalogs` | 任意です。長いリストを手入力せずに済む、シート編集画面の既製項目です。 |
| `items` | 任意です。アイテムを記述する語彙です。カテゴリー、レアリティー、ステータス、スロット、お金です。 |
| `battle` | 任意です。戦闘がシートから読むものと、終了後に書き戻すものです。 |
| `combat` | 任意です。独自の戦闘解決規則と、戦闘画面が実行する内容です。 |
| `layers` | 任意です。ゲーム作成時にプレイヤーが有効にするバリエーションです。 |

ファイルは最大256 KBです。プロンプトへ入る文章(名前、ラベル、Game Master向け文章)に改行、角括弧、二重波括弧は使えません。

シート内のID(能力値、スキル、フィールド、プールなど)は、`grit_max`のように英字で始まり、小文字、数字、アンダースコアで構成します。

### 判定方式

`resolution.kind`は判定の振り方を選びます。両方式は同じキャラクターシートと3つのキーを共有するので、切り替えても`resolution`より後のファイル構成は変わりません。

- `abilityModifier`: シートの能力値を数値へ変える方法です。`identity`はそのまま使い、`floorHalfMinusTen`は5eの規則、`stepTable`は`[[score, number], ...]`で独自のしきい値を列挙します。
- `proficiencyTiers`: スキルやセーヴの習熟段階です。未掲載のスキルは先頭の段階になります。`flat`、習熟ボーナスの`multiplier`倍、または両方を加えます。習熟ボーナスがあるシステムでは、`"proficiency": { "bonus": { "derived": "proficiency_bonus" } }`で出所を指定します。
- `proficiency`: 任意で、乗算する段階があるときだけ必要です。

得られた数値の意味は方式が決めます。`dice-sum`はロールへ加算し、`dice-pool`はその個数のダイスを振ります。

#### `dice-sum`: ダイスを合計する

```json
"resolution": {
  "kind": "dice-sum",
  "dice": { "count": 2, "sides": 6 },
  "abilityModifier": { "op": "identity" },
  "proficiencyTiers": [
    { "id": "untrained", "label": "Untrained" },
    { "id": "trained", "label": "Trained", "flat": 1 }
  ],
  "advantage": false,
  "difficultyLadder": [
    { "label": "Easy", "dc": 6 },
    { "label": "Hard", "dc": 10 }
  ]
}
```

- `dice`: 個数と面数です。合計を難易度と比較します。
- `advantage`: Game Masterが2回振って片方を採用するよう要求できるかです。
- `naturals`: 単一ダイスの最大・最小出目が判定とセーヴに及ぼす効果です。`none`、`both`、`max-only`、`min-only`から選びます。単なる計算だけなら省略します。ダイス1個が条件なので、2d6方式では`none`が必要です。
- `difficultyLadder`: Game Masterへ提示する難易度の候補です。`dc`は合計が到達すべき数値です。GMは数値を書く代わりに`difficulty="Hard"`のように段階名を指定でき、Engineはその段階から数値を読み取ります。

#### `dice-pool`: ダイスを振って成功を数える

シートの数値は追加ボーナスではなく**プールの大きさ**です。評価値3と専門技能2なら5個振ります。仕組みはそれだけです。新しいシート用語もエディターもなく、評価値がダイスの個数を表すシステムも、ほかと同じ`abilities`、`skills`、`proficiencyTiers`で書けます。

```json
"resolution": {
  "kind": "dice-pool",
  "die": { "sides": 10 },
  "abilityModifier": { "op": "identity" },
  "proficiencyTiers": [
    { "id": "rating_0", "label": "Untried" },
    { "id": "rating_1", "label": "Shown once", "flat": 1 }
  ],
  "pool": { "min": 1, "max": 15, "abilityPlusAbility": true },
  "target": { "default": 7, "min": 5, "max": 9 },
  "explode": { "from": 10, "min": 8 },
  "cancel": { "upTo": 1 },
  "botch": { "upTo": 1 },
  "exceptional": { "successes": 5 },
  "situationalDice": { "min": -3, "max": 3 },
  "reroll": [{ "id": "careful", "upTo": 6, "mode": "once" }],
  "difficultyLadder": [
    { "label": "Plain work", "successes": 1, "target": 6 },
    { "label": "Grim", "successes": 3, "target": 8 }
  ]
}
```

- `die`: プールのダイス1個の面数で、2～100です。
- `pool`: 爆発が起きる前にシート値を収める範囲です。`min`が0なら空のプールは一度も振らずに失敗し、`max`は最大100です。`abilityPlusAbility: true`にすると、能力値判定で`with=`により2つ目の能力値を指定し、両方を振れます。2つの能力値を合わせて振るシステム向けです。これがなければ、能力値判定での`with=`は何も意味しません。
- `target`: 成功と数えるために必要な出目です。`min`を`max`より小さくすると、GMが判定ごとに`threshold=`で動かせます。3つを同じ値にすると固定です。
- `double`: 任意です。`from`以上の出目を2成功と数えます。
- `explode`: 任意です。`from`以上ならダイスを1個追加し、そのダイスも爆発できます。追加分は元のプールに加えて最大`pool.max`個なので、1判定の総数は最大`pool.max`の2倍です。`from`が小さくても無限に振りません。
- どちらも`min`を持てます。タグの`explode="N"`や`double="N"`、またはキャラクターが使った項目によって、判定がその規則を引き下げられる最小の出目です。`min`があれば`from`を省略でき、その場合は要求した判定でだけ規則が発動します。1つのスキルで10の目を振り足す専門技能なら`"explode": { "min": 10 }`です。`from`は`min`未満にできません。
- `cancel`: 任意です。`upTo`以下の出目は成功を1つ減らします。成功数は0未満になりません。
- `botch`: 任意です。成功したダイスが**1つもなく**、`upTo`以下が出た場合はクリティカル失敗です。1成功が相殺されたプールは通常の失敗で、クリティカル失敗ではありません。`"rule": "halfOrMore"`は別の読み方をします。最初に振ったダイス(爆発分は数えません)の半数以上が`upTo`以下なら、成功したダイスがない場合はクリティカル失敗です。それ以外の場合は結果をそのまま残し、`complication="true"`の印を付けます。結果に伴って何かがうまくいかなかったことを表します。デフォルトは`"noSuccesses"`です。
- `exceptional`: 任意です。成功した判定の正味成功数がこの値以上ならクリティカル成功です。
- `situationalDice`: 任意です。離れ業、負傷、暗さなどについて、GMが`bonus=`で1判定のダイスを増減できる範囲です。
- `reroll`: 任意です。誰も支払わずにシステムが認める振り直しで、最大6個です。それぞれ`id`を持ち、GMは判定で`reroll=`によって指定します。`upTo`以下の目を振り直します。`"once"`なら新しい目が何であれ確定し、`"until"`ならそれより大きい目が出るまで振ります。すべての目を振り直すと終わらないため、`upTo`は1から、ダイスの面数より1小さい値までです。`until`も1判定で100回振り直すと止まります。判定で指定しない限り何も振り直しません。1判定で行う振り直しは1つです。消費やキャラクターが使った項目でも振り直しを購入した場合は、より多くの目に届く方を振り、届く範囲が同じなら`once`より`until`を優先します。
- `difficultyLadder`: `successes`は必要成功数です。段階ごとに`target`も指定できますが、目標が調整可能で、その範囲内の場合だけです。その目標値は、その段階での判定が数える基準です。GMが`difficulty=`で段階を指定した場合か、ちょうど1つの段階が必要とする`dc=`を書いた場合です。複数の段階が同じ成功数を必要とする場合、`dc=`だけではどれを意図したか分からないため、目標値はデフォルトのままです。段階名を指定してください。

`cancel`と`botch`の出目は最低目標より低くなければならず、すべての規則の出目はそのダイスに実在する必要があります。絶対に発動しない規則はプレイ中に発覚させず、インポート時に拒否します。

パッケージ形式のプールルールセットはCapability API 1.24です。`explode`や`double`の`min`、`pool.abilityPlusAbility`、`botch.rule`は1.37、`reroll`は1.38です。コミュニティのインポートは読み取るEngine自身が検証するため、別の指定は不要です。

#### プール判定でGame Masterが書けるもの

```
[skill_check: skill="Ward" dc="2" who="Bram the Quiet" threshold="8" bonus="-2" with="Sinew"]
[skill_check: skill="Ward" difficulty="Grim" explode="9"]
[skill_check: skill="Nerve" dc="1" with="Warmth"]
[skill_check: skill="Ward" dc="2" reroll="careful"]
```

- `dc`は目標値ではなく、必要な**成功数**です。1から、1ロールで数えられる最大数まで指定できます。プールの最大数を基準に、爆発可能なら2倍、出目を2成功と数えるならさらに2倍です。
- `threshold=`は各ダイスの目標を動かし、`target.min`が`target.max`未満の場合だけ提供されます。
- `bonus=`はダイスを増減し、`situationalDice`を宣言した場合だけ提供されます。
- `with=`は本来とは別の能力値でスキルやセーヴを振ります。両方式に対応するため、5eでも同じ属性で"Strength (Intimidation)"を実現できます。`pool.abilityPlusAbility`がオンなら、能力値判定では代わりに2つ目の能力値を加えます。
- `difficulty=`は`dc=`の代わりに難易度表の段階を指定し、両方式で使えます。その段階の成功数(合計方式なら難易度)と、プール方式なら目標値を使います。並べて書いた`dc=`は引き続き数値で優先し、`threshold=`は目標値で優先します。どの段階にも該当しない名前や、2つの段階が共有する名前は無視します。
- `explode=`と`double=`はこの判定でそれらの規則の目を動かし、規則が`min`を持つ場合だけ提供されます。
- `reroll=`はこの判定で`reroll`項目の1つを指定し、何か宣言した場合だけ提供されます。どれにも該当しない名前は無視します。

すべてファイルの宣言範囲に制限されます。範囲外の値は最寄りの端へ丸め、ルールセットにない能力値は判定自体を拒否せず無視します。保存記録には実際に使った値が表示されます。難易度と目標値は数値で、追加ダイスは制限後の値で記録します。`with=`は実際に能力値を入れ替えたか加えた場合だけ、目は判定が動かした場合だけ、`reroll=`は指定した振り直しが実際に使われて何かを振り直した場合だけ記録し、`complication="true"`は`halfOrMore`の大失敗で結果に伴う問題が生じた場合に記録します。Engineは必ず自分でダイスを振ります。モデルが書いたプール結果は置き換え、この方式に有利はないため`mode="advantage"`を無視し、プレイヤーがターン前に振ったダイスも使いません。

#### 対象外の仕組みとその理由

以下は目標に対してダイスを数える形で表せないため、それぞれ独自の判定方式が必要です。

- **最大出目の採用**(Blades in the Darkなど)には、現在の判定結果にない部分成功の段階が必要です。
- **能力値と比較するスタンスプール**(Lasers and Feelingsなど)は、判定ごとに上か下かを決める別の比較です。
- **記号ダイス**(Genesysなど)はそもそも数値を出しません。
- **対抗プール**は2人を同時に解決しますが、判定のロール者は1人です。
- **目標以下の判定や上限のないパーセンタイル**は比較の向きが異なります。
- **ワイルドダイスを含む合計プール**(OpenD6など)はダイスを加算し、1個を特別扱いします。

この方式が以前扱えなかった残り2つは、現在実装されています。下の「消費でロールを変える」で説明します。「1ポイントで1成功を得る」や「1ポイントで失敗したダイスを振り直す」といったシステム自体の規則は`resolution.spend`です。状況に応じてシステムが無料で認める振り直しは、上記の`resolution.reroll`です。キャラクターが取得したものに属する振り直しはカタログ項目の`mechanics.check`で、その項目自身のコストを支払います。

### 消費でロールを変える

意志を1ポイント使って自動成功を得るなど、これから振るロールに支払えるシステムがあります。`resolution.spend`はキャラクターが購入した特性ではなく、システムの常設規則としてこれを宣言します。

```json
"spend": [{ "pool": "resolve", "amount": 1, "successes": 1, "perCheck": 2 }]
```

- `pool`は`live.pools`の1つです。開始時に空のプールは、プレイ開始時に消費できないため使えません。
- `amount`は1回の購入コストです。得られるものは`successes`、`dice`、`reroll`で、少なくともどれか1つを購入する必要があります。購入した成功は振って得たものではないため、ダイスの集計と相殺のあとに加えます。ダイスはプール自身の範囲内で、プールと一緒に振ります。`reroll`は`{ "upTo": 6, "mode": "once" }`の形で、`resolution.reroll`と同じように読みます。判定で何回購入しても、振り直しを購入するのは1回です。同じダイスを2回振り直しても、振り直しは1つです。
- `perCheck`は1判定の購入回数です。最大で`amount * perCheck`ポイント相当を買えます。この上限により、満タンのプールで必ず成功するロールを買うことを防ぎます。1から10の数値、派生値が読むのと同じ形式のシート上の値(`{ "abilityScore": "nerve" }`、`{ "derived": "focus" }`)、または`"pool"`(判定のダイス数と同じ回数。負傷、追加ダイス、修正値を適用する前の、その判定のシート上の数値です)を指定できます。シート上の値は振る人について読み、切り捨てて0から100に収めます。上限が0になったキャラクターは何も買わず、何も支払いません。
- `dice-pool`だけが使えます。合計ロールには追加する成功もダイスを足すプールもないため、`spend`を宣言した`dice-sum`はインポート時に拒否されます。
- 項目は最大4つで、2つの項目が同じプールを指定することはできません。判定からどちらを指すのか区別できないためです。
- `reroll`を購入する消費、数値でない`perCheck`、3つ以上の項目は、パッケージ形式のルールセットではCapability API 1.38です。

**判定自体に指定します。** GMは別の`[sheet:]`コマンドではなく、`[skill_check: skill="Nerve" dc="2" spend="resolve:1"]`と書きます。シートコマンドの適用前にダイスを振るため、別コマンドでは変更に間に合いません。1つの解決処理で、ロールとそれを変える支払いを行います。

### ロールを変えるチャーム

`resolution.spend`はシステムの規則です。キャラクターが実際に取得した項目も、カタログ項目の`mechanics.check`で判定を変えられます。

```json
"mechanics": {
  "kind": "utility",
  "cost": [{ "pool": "blood", "amount": 1 }],
  "perCostStep": { "flat": 1 },
  "check": { "reroll": { "upTo": 1, "mode": "once" }, "successes": 1 }
}
```

- `reroll`は`upTo`以下を振り直します。`once`は各ダイスを1回だけ置き換えて新しい目を確定し、`until`は振り直しを続けます。プール全体を永久に振り続けないよう、`upTo`は最大出目未満の実在する目が必要です。ファイルの内容にかかわらず、Engineは1判定の振り直し数を制限します。
- `dice`はプールを振る前にダイスを加え、`successes`は集計後に成功を加え、`threshold`は`target`の許可範囲内でその1ロールの目標を設定します。
- `explode`と`double`はその1ロールでそれらの規則の目を動かします。規則が`min`を持つ場合だけ、その範囲内で使えます。`"check": { "explode": 8 }`は8の目を振り足す項目です。`threshold`と同じく、GMがタグに書いた値より優先します。Capability API 1.37です。
- これらのうち最低1つが必要です。なければ効果を宣言していないため拒否されます。
- 対応できるのは`dice-pool`だけです。`mechanics.check`を持つ`dice-sum`はインポート時に拒否されます。

**支払うのは項目自身の`cost`です。** ほかの項目の使用と同じ仕組みで、プールと、その項目が書いた全カウンターの使用回数1回分を支払います。`perCostStep`は効果が拡大することを指定します。宣言した項目は支払った価格の回数分購入し、宣言しない項目は提示額にかかわらず1回だけ購入します。

**GMは判定で項目名を指定します。** `[skill_check: skill="Brawl" dc="3" use="Potence" spend="blood:3"]`です。上と同じく、帳簿処理より先にダイスを振るため、別のシートコマンドにはしません。

**すべて支払うか、何も行わないかです。** プールが不足すれば購入は起こらず何も引かず、元どおりのロールになります。購入回数の整数倍でないポイントでも何も買えません。`perCheck`を超える要求は拒否せず上限へ制限し、その分だけ支払います。すべてEngineが計算し、GMはプレイヤーが宣言した消費を指定するだけでダイスを操作しません。記録には実際の支払額、適用項目、振らずに得た成功数、振り直したダイス数が残ります。未取得のチャームや、Engineがカタログを読めないチャームは、信用して適用せず何もしません。

### シート

- `sections`は編集画面の項目をグループ化します。フィールド、派生値、リストは`section`で所属するセクションを指定し、能力値、スキル、セーヴも指定できます。指定すると、編集画面、ゲーム内のシート、GMのシートブロックがその見出しの下に表示します(セクションを指定しないシートは従来どおりに表示します)。セクションは`untrained`規則(後述)も持てます。
- `abilities`は基本能力値です。`skills`と`saves`はそれぞれ判定に使う能力値、`cap`、`untrained`規則(後述)を指定できます。
- `fields`は単一の値です。型は`number`、`text`、`longtext`、`boolean`、`enum`(固定の選択肢)、`dice`(`1d8`などの文字列)です。
- `derived`は他の値から計算し、手入力で上書きできません。演算は`sum`、`min`、`max`、`scale`(乗算して丸める)、`stepTable`(レベルから習熟ボーナスを求めるように、しきい値表から値を引く)、`enumTable`(列挙型フィールドやライブステートの各値に対応する数値。後述の「ライブステート」を参照)です。
- `lists`は装備、呪文、特性など、独自の列を持つ表です。`pools`を持つリストは各行を最大値付きリソースにし、回数制限のあるクラス特性などに使います。
- `live`はプレイ中に変わるものです。`pools`(HP、呪文スロット、Grit)、`tracks`(消耗などの範囲上の数値、またはマスに印を付ける負傷トラック)、`text`(集中している対象などの短いメモ)、`conditions`、`states`(形態や構えなど、決まった集合から選ぶ1つの値)です。

数値を読むものは値参照で指定します。これは`const`、`field`、`derived`、`abilityScore`、`abilityMod`、`abilityModFromField`、`skillMod`、`saveMod`、`listSum`、`livePool`、`liveTrack`、`itemStat`のうちキーを厳密に1つだけ持つオブジェクトです。たとえば最大値に派生値を使うプールは`"max": { "derived": "grit_max" }`です。

- `listSum`はリストの数値列1つを合計します。`{ "listSum": { "list": "gear", "column": "bulk", "onlyWhen": "packed" } }`です。`onlyWhen`は任意で、真偽値列を指定し、それがオンの行だけを数えます。空のセルはその列のデフォルトとして数え、`hideWhen`で隠れたリストは何も加えません。Ember Roadsはこの方法でBurdenを、キャラクターが荷物に入れた装備から計算するため、手入力の数値のようにリストと食い違うことはありません。カタログの連動列は、派生値を通じても、リストの合計を読めません。リストは自身の連動セルや、その合計を読み返す連動セルを持つことがあり、再計算が収束しなくなるためです。
- `livePool`は`live.pools`の1つの残量を読みます(リスト行のプールは含みません)。`liveTrack`は`live.tracks`の1つを読み、任意で`read`を指定します。`"value"`は現在の位置(デフォルト)、`"filled"`は`min`からどれだけ上か、`"remaining"`は`max`までどれだけ残っているか、負傷トラックだけで使える`"penalty"`は現在のペナルティです。隠れたプールやトラックは0を読みます。Gravewatchの「Harm still to take」は`{ "liveTrack": "harm", "read": "remaining" }`です。
- ライブ値の読み取りは、判定を振る時点、戦闘の開始時点、GMのシートブロックを書く時点のライブ状態を使います。まだライブ状態がない場合(シートエディターやインポートの確認画面)は、プレイ開始時の状態を読みます。プールは`start`の指定どおり満タンか空、トラックは`default`、負傷トラックは印なしです。
- ライブ状態ができる前に計算する値は、ライブ値を読めません。プールやトラックの`max`、習熟ボーナス、カタログの連動列やスケーリングです。ライブ値を読む派生値を通じる場合も、ライブ値が上限を決めるスキルを通じる場合も同じで、インポートは該当する値を示します。
- この3つは、パッケージ形式のルールセットではCapability API 1.39です。
- `itemStat`は、装備している鎧のガード値など、キャラクターが持つアイテムを読み、ライブ値の読み取りと同じ規則に従います。[シート上のアイテム](#items-on-the-sheet)を参照してください。Capability API 1.52です。

**未習熟時の判定。** キャラクターが習熟していない(段階が先頭の)スキルやセーヴは、ルールセットが別に定めない限り通常どおり振ります。別に定めるには、スキルやセーヴ、または所属するセクションに`untrained`を指定します(スキルやセーヴ自身の規則が優先します)。

```json
"sections": [{ "id": "labour", "label": "Labour", "untrained": { "by": -1 } }],
"skills": [
  { "id": "dig", "label": "Dig", "ability": "sinew", "section": "labour", "untrained": "refuse" },
  { "id": "listen", "label": "Listen", "ability": "nerve", "untrained": "harder" }
]
```

- `"normal"`: 通常どおりです(デフォルト)。
- `{ "by": -3 }`: 判定の数値に-20から20の範囲で加えます。プールならダイス、合計方式なら固定値です。シートに表示され、すべての判定が振る数値の一部で、`cap`より前に適用します。
- `"harder"`: 1段階難しくします。プール方式ではダイスごとの目標値が1上がり(目標値の範囲内に収まります)、目標値を動かせるプールのルールセットが必要です。それ以外ではロールを変えられないため、インポート時に拒否されます。
- `"refuse"`: 判定をまったく振りません。EngineはGMの要求を`reason="untrained"`付きで書き戻し、それで決着します。後から振ることはなく、GMにはキャラクターが試みられなかったことが伝わり、語りもそれを反映します。スキル判定のエンドポイントはそうした判定に400(`skill_check_untrained`)で応え、その判定に対する分岐ブロックはどちらの文章も残しません。シートエディターはその数値を表示しません。
- シートのないキャラクターには読み取る習熟がないため、未習熟の規則は適用されません。
- GMのリマインダーはセクションごとまたはスキルごとに未習熟の規則を列挙するため、GMはキャラクターが実行できる判定を求めます。

能力値、スキル、セーヴのセクション指定と、あらゆる場所の`untrained`は、パッケージ形式のルールセットではCapability API 1.41です。

スキルやセーヴは`cap`を持てます。判定が到達できる最大値を示す値参照で、成長しても超えられない評価値や、判定を押さえ込むトラックを表します。GravewatchはSootheを、番人に残っているResolveで制限します(`"cap": { "livePool": "resolve" }`)。制限後の数値がシートに表示され、すべての判定が振る数値です。`with=`による入れ替えは制限前の数値で計算し、そのあと再び制限します。上限はスキルやセーヴの修正値を読めず、上限が読む派生値も、それより上で宣言した派生値も同様です。そのためシートは引き続き上から下へ1回で計算できます。Capability API 1.39です。

`hideWhen`は、別のフィールドの値によってフィールド、派生値、リスト、プール、普通のトラックを隠します。方法は厳密に3つのうち1つです。`equals`は1つの値に一致する場合、`notEquals`は1つの値に一致しない場合(フィールドがほかの値を持つときは常に隠れます。「この種類のキャラクター専用」を表す方法です)、`in`は値のリストに含まれる場合です。指定する値はすべてフィールドが持てる値でなければならず、そうでなければ規則は一致できません。値は1つずつ検査し、`notEquals`と`in`では数値フィールドの範囲とテキストフィールドの長さも検査します。規則はシートエディターが表示する値を読みます。未設定のフィールドは空白のシートの初期値、ルールセットが提供しなくなった列挙値はフィールドのデフォルトとして読みます。5eファイルは`equals`で、呪文を使わないキャラクターの呪文スロットを隠します。Gravewatchは`"hideWhen": { "field": "watch", "notEquals": "night" }`で、夜番でないすべての番人のシートからランタンの油を除きます。レイヤーは、これらが比較する値を削除できません。負傷トラックは隠せません。シートの表示にかかわらず、ロールと戦闘が読むためです。`notEquals`と`in`はCapability API 1.39です。

普通のトラックの`max`は数値の代わりに値参照にでき、キャラクターの評価値でトラックの長さを決められます。`"max": { "field": "willpower_rating" }`です。`min`と`default`は数値のままです。名前付き段階を持つ負傷トラックの`max`は段階数と等しく、番号付きのマスのトラックの長さは自身の`max`です(後述の「名前付き段階の代わりに番号付きのマス」を参照)。`alwaysShow: true`はデフォルト値でもGMのシートブロックにトラックを表示します。毎ターン重要な評価値のためのもので、これがなければデフォルト値のトラックは省略されます。0のままの死亡セーヴ3つは何も伝えないためです。この3つは、パッケージ形式のルールセットではCapability API 1.37です。

### ライブステート: 形態、構え、明かり

列挙型フィールドはキャラクター作成時に選んだらそのままで、状態はオンかオフしかありません。**ライブステート**は、プレイ中に変わる、決まった集合の中の1つの値です。変身する者の形態、戦闘の構え、ランタンの明るさなどです。

```json
"live": {
  "states": [
    {
      "id": "stance",
      "label": "Stance",
      "values": ["guarded", "steady", "reckless"],
      "valueLabels": { "guarded": "Guarded", "steady": "Steady", "reckless": "Reckless" },
      "default": "steady"
    }
  ]
}
```

- `values`は2～40個で、それぞれ`valueLabels`の項目か、値そのものとして表示します。すべてのラベルと同じ規則(1行、角括弧なし、マクロの波括弧なし)に従い、シートコマンドが引用符で囲むため、二重引用符は使えません。ステートは最大12個です。
- `default`はすべてのシートの開始値で、省略すると最初の値です。デフォルトから変わったステートだけを保存し、ステートが提供しなくなった保存値はデフォルトとして読みます。
- `hideWhen`は、プールと同じくフィールドの値によってステートをシートから除きます。表示されず、コマンドでも設定されず、表(後述)からは値なしとして読まれます。
- GMは`[sheet: who="Name" op="state" state="Stance" value="Reckless"]`で設定し、ステートはIDかラベル、値はそれ自体かラベルで指定します。シートにないステートや値は拒否されます(`unknown-state`、`unknown-value`)。Engineはルールセットにステートがある場合だけコマンドを教えてすべての値を列挙し、各シートブロックはデフォルトの場合も含め各ステートの値を示します。「人間の姿」のような事実は、語りが毎ターン必要とするためです。
- ゲームのシート画面では、各ステートに選択欄を表示します。
- 休息では、ステートを指定する回復処理で元に戻せます。`{ "state": "stance", "to": "default" }`、または`"to"`にその値の1つを指定します。

**連動する数値。** `"op": "enumTable"`の派生値は、列挙型フィールドやライブステートの各値に対応する数値を返します。

```json
{
  "id": "stance_brawn",
  "label": "Stance on Brawn",
  "op": "enumTable",
  "from": { "liveState": "stance" },
  "table": { "guarded": -1, "reckless": 2 },
  "default": 0
}
```

- `from`は`field`(列挙型フィールド)か`liveState`の厳密に片方を指定します。`table`の各行はそれが取り得る値で、1～40行です。表にない値や、シートが隠すステートは`default`を読みます(省略時は0)。
- フィールドはキャラクター作成時に固定されるため、フィールドをキーとする表は最大値の計算に使えます。Gravewatchは夜明けの番に就く番人のResolveを1増やします。ライブステートはプレイ中に変わるため、ステートをキーとする表は`liveTrack`と同じくライブ値の読み取りです。ライブ状態ができる前に計算する値は、直接でもほかの派生値を通じても、それを読めません。キーが`state`ではなく`liveState`なのはこのためです。ライブ状態の読み取りにはすべて`live`の名前が付くので、最大値に使えないものを作者もインポートも見分けられます。
- 数値をダイスに反映するには、`resolution.adjust`でそれを指定します(「シート由来の修正値」を参照)。Ember RoadsはStanceをすべてのBrawnのロールに加え、Gravewatchは覆いを閉じたランタンや消えたランタンの分をすべてのNerveのロールから引きます。
- レイヤーは、表が行を持つフィールドから値を除けます。レイヤーの有効中、その行は読まれないだけです。

ライブステート、`enumTable`、`state`を指定する休息の処理は、パッケージ形式のルールセットではCapability API 1.42です。

### 負傷トラック: 数値でなくトラックとしての体力

HPを数えないシステムも多くあります。前より悪い段階のマスを縦に並べ、負傷時に印を付けます。`live.tracks`項目へ`kinds`と、名前付きの`levels`か番号付きの`boxes`(後述)のどちらかを与えると、範囲上の数値からこの方式へ変わります。

**システムに必要なのはどちらでしょうか。** プールは受けたダメージ量、トラックは各ダメージの量と種類を記録します。打撃、致死、加重といった種類があり、加重は治りにくい、吸収できない、最終的に死に至らせるなど、命中後も種類が重要なら、ロール後もそれを保持する場所が必要です。種類を保持できるのは印だけです。ポイントのプールは引かれた後は小さな数値となり、どのポイントがどの種類だったかシートは記憶しません。体力がプールのルールセットで`combat.damageKinds`を黙って無視せず拒否するのはそのためです。プールにも`damageTypes`は使え、敵が抵抗や完全耐性を持つこともできます。それは負傷後の種類ではなく、1撃のどれだけが通るかに関する問題だからです。

```json
{
  "id": "harm",
  "label": "Harm",
  "min": 0,
  "max": 4,
  "levels": [
    { "label": "Scuffed", "penalty": 0 },
    { "label": "Winded", "penalty": -1 },
    { "label": "Bleeding", "penalty": -3 },
    { "label": "Down", "penalty": -99 }
  ],
  "kinds": [
    { "id": "knock", "label": "K", "severity": 0 },
    { "id": "tear", "label": "T", "severity": 1 }
  ]
}
```

- `levels`は良い順に1～16段階です。各段階は`label`と0以下の整数`penalty`を持ちます。大きな負数で行動不能を表すシステムなので、`-99`も有効です。
- `kinds`は受けられる負傷の1～6種類で、各項目に`id`、マス用の短い`label`、`severity`があります。重大度は重複不可ですが、順序以外に数値自体の意味はなく、間隔は自由です。
- 両方が必要です。`levels`も`boxes`もない`kinds`は印を置く場所がないため拒否され、`kinds`のない`levels`や`boxes`は印の種類が必要なため拒否されます。トラックが持つのは`levels`か`boxes`のどちらかで、両方は持てません。
- **2つの言葉を区別してください。** `kinds`は印が取り得る種類の定義です。印はプレイ中にその種類の1つがトラックに載ったものです。定義が種類を持ち、キャラクターシートが印を持ちます。
- 負傷トラックは印なしで始まるため、`min`は0です。名前付き段階のトラックの長さは段階数なので`max`は`levels.length`で、それ以外は黙って修正せず拒否し、食い違う2つの長さをファイルに保持させません。マスのトラックの長さは自身の`max`で、シートが計算する値も指定できます(後述の「名前付き段階の代わりに番号付きのマス」を参照)。

曖昧な理解では違うトラックになるため、**規則を正確に示します**。

- 印は**重大度の高い順**に保持します。7段階のトラックは最大7つです。
- 印は末尾へ追加するのでなく、既存の印の**重大度順へ挿入**します。その重大度で入れる最上位を取り、軽い印を下へ押します。
- 適用するペナルティは**印のある最下段**のものだけで、合算しません。上のトラックの3つの印は`0 + -1 + -3`でなく`-3`です。
- `amount`は1種類の印の個数で、**1つずつ適用**します。そのため途中で埋まるトラックも、最初から満杯のトラックも同じ規則です。
- **満杯**のトラックへの追加は、新しい印を増やさず**最も軽い印を1段階重く**します。追加した印の種類にかかわらず、独自の種類の序列を1段上げます。
- 最大重大度を超えて重くなる印は最大に留まり、載せられなかった1つを**超過分**として数えます。超過分も保存するため、再読み込みで受けたダメージを忘れません。
- **回復は同じコマンドで負の量を使います。** 印より先に超過分を消します。トラックの種類の1つを指定した回復はその種類の印だけを消すため、「打撃は治るが致死は残る」は負の量と`kind="bashing"`で表します。トラックにある種類を指定しない回復は、最も軽い印から消します。

**プレイ中に印を付ける方法。** GMは`[sheet: op="damage" track="harm" kind="knock" amount="1"]`と書き、負の`amount`で回復します。マス単位で埋めるトラックでは、命中するマスを示す`box="3"`を加えます。`pool=`を指定する従来の`damage`は変わりません。単なる数値では新しい印の種類を示せないため、負傷トラックの通常の`track`コマンドは拒否されます。こうしたシステムが想定するように、プレイヤーもシートで手動で印を付けたり消したりできます。

**戦闘でも印を付けられます。** `combat.health`をプールでなくトラックに向けると、命中した1撃は`combat.damageKinds.marks`で指定したマス数に、そのブロックがダメージ種別から対応付ける種類の印を付けます。トラックが満杯なら倒れ、死亡ルールがその状態を読みます。マス単位で埋めるトラックでは、`per-point`のダメージは当たるマスを指定し、`per-blow`は最初のマスを狙います。どのマスにも入らない打撃はキャラクターを倒します。そのようなトラックを使うシステムでは、それが戦闘不能を意味するためです。回復は種類を問わず最も軽い印を1つ消します。一時ポイントを置くバッファーはないため、一時ポイントは拒否します。Engineはトラックを残り段階数として読むため、戦闘のほかの部分、倒れること、蘇生、ログ、要約は変わりません。

**休息で負傷トラックを治せます。** `"to"`でトラックを指定する回復処理は、超過分も含め、印を指定個数まで減らします。**負の**`"by"`なら超過分から先に指定個数を消すため、`"by": { "const": -2 }`は2つ消します。`kind`も指定する処理はその種類の印だけを消します。Gravewatchの「Catch your breath」は`{ "track": "harm", "kind": "knock", "to": "min" }`で、knockの印を治し、tearの印は残します。休息は負傷を記録しないため、印を増やすことになる処理は何もしません。正の`"by"`もこれに含まれ、何も通知せずに省略されるので、マイナス記号を書いてください。

#### 名前付き段階の代わりに番号付きのマス

トラックの長さがキャラクターのタフさに応じる場合は、`levels`の代わりに`boxes`を与えます。マスの数は自身の`max`と同じで、シートが計算する値(ライブ状態を読むものは不可)を指定でき、最大64です。

```json
{
  "id": "strain",
  "label": "Strain",
  "min": 0,
  "max": { "derived": "strain_boxes" },
  "boxes": {
    "penalty": {
      "by": "remaining",
      "table": [
        [0, -1],
        [1, 0]
      ]
    }
  },
  "kinds": [{ "id": "strain", "label": "S", "severity": 0 }],
  "fill": "indexed",
  "onFull": "refuse"
}
```

- 現在のペナルティは、`filled`または`remaining`のマス数(その数が何であれ)で`table`(派生値と同じ段階表で、ペナルティは0以下)から読みます。そのため印がなくてもペナルティを課す表にできます。どのマスに印があるかには依存しません。
- マスには番号が付きます。シートには「Box 3」と表示し、GMのシートブロックは段階名ではなく、全体のうちいくつに印があるかを示します。

#### マス単位の記入と、拒否するトラック

- `"fill": "indexed"`は、コマンドが`box=`で指定したマス(指定がなければ最初のマス)か、その上で次に空いているマスに印を付け、一度付けた印を動かしません。回復は、最も軽い印のうち番号が最も大きいものを消します。シート画面では、プレイヤーが空いている任意のマスをクリックできます。
- `"onFull": "refuse"`は、空きマスがない印を、最も軽い印を重くする代わりに拒否します。コマンド全体が拒否されるため、空きが2マスのところへの3つの印は1つも付きません。indexedのトラックは常に拒否するので、その横に`"onFull": "refuse"`と明記してください。

#### リストが加える段階

名前付き段階を持つトラックに`"extra": { "list": "scars", "countColumn": "levels", "penaltyColumn": "penalty" }`を指定すると、シート上のリストでキャラクターごとにトラックを延ばせます。各行は順に、そのペナルティで指定数(最大16)の段階を加えます。挿入位置は、ペナルティがそれと同等以上に良い最後の段階の後です。ペナルティが一致すればその段階の名前を、そうでなければペナルティの値を名前にします。Gravewatchの傷跡はこの仕組みです。シートが隠すリストは何も加えず、印のある段階の行を削除した場合、収まらなくなった印は超過分として保持します。シートを編集しても負傷はなくなりません。

`boxes`、`fill`、`onFull`、`extra`、休息の処理の`kind`は、パッケージ形式のルールセットではCapability API 1.40です。

### ロールへのペナルティ

`resolution.penaltyFrom`は、このルールセットのすべての判定へペナルティを適用する負傷トラックを指定します。推測でなく明示宣言なので、省略したルールセットは負傷トラック導入前と同じように振ります。

ペナルティの作用は、シートの数値と同じく判定方式が決めます。

- `dice-pool`では**プールのダイスを減らし**、独自の`pool.min`を下限にします。`pool.min`が1なら最下段でも1個振り、`pool.min`が0なら振らずに失敗します。
- `dice-sum`では**ロールの固定修正値**となり、能力値と習熟が加える数値にまとめます。

指定先は負傷トラックである必要があります。普通のトラックにはペナルティがなく、指定するとインポート時に拒否されます。結果に適用したペナルティが表示されるため、ダイスが減った理由を確認できます。GMのシートブロックにも段階とペナルティが表示されます。

### シート由来の修正値

シートの数値には、関係するすべてのロールに付いて回るものがあります。登攀には重い荷物、忍び足には鎧のペナルティ、すべてに祝福などです。`resolution.adjust`は、どちらの方式でもこれを宣言します。

```json
"adjust": [{ "value": { "derived": "burdened" }, "abilities": ["brawn"] }]
```

- `value`はシート上の値で、派生値が読むのと同じ形式です。ライブ状態も含みます。負の数値は差し引きます。Ember Roadsはキャラクターが荷物に入れた装備のBulkをBurdenとして合計し、段階表でその3ごとに各Brawnのロールから1を引きます。ライブステートをキーとする表で、形態や構えをダイスに反映できます(「ライブステート」を参照)。
- `abilities`は任意です。指定すると、その能力値のいずれかで振る判定だけに修正値を適用します。能力値そのもの、それを使うスキルやセーヴ、`with=`でそれを使って振るスキル、それを含む能力値の組です。指定しなければすべての判定に適用します。
- 負傷ペナルティと同じ位置に適用します。プールではダイスとして同じ`pool.min`の下限の範囲で、合計方式では記録が合計する修正値の中の固定値です。項目は最大8つで、判定ごとに合算します。
- ルールセットの戦闘は、開始時にシートから組み立てるすべてのロールに加えます。能力値やスキルで振る攻撃、セーヴ、能力値・スキル・セーヴから読む対抗判定とイニシアチブはその能力値の項目を受け、ほかのロールはすべてのロールに適用する項目だけを受けます。
- シートのないキャラクターは、修正値を得ないのと同じく、何も受けません。

結果にはシートが加えた分が示されるため(記録の`adjust="-2"`と、ダイスカードの1行)、プレイヤーはロールの結果の理由を確認できます。パッケージ形式のルールセットではCapability API 1.38です。

### 休息

休息は回復処理と解除対象の一覧です。各処理は1つの対象(`pool`、`poolGroup`、`listPools`、`track`、`state`)を指定し、設定する(`"to": "max"`、`"to": "min"`、または数値)か、増減する(`"by": { "const": 1 }`または`"by": { "fractionOfMax": 0.5 }`)かを定めます。負傷トラックを指定する処理は回復だけなので、`by`は負の値です。上記を参照してください。ライブステートを指定する処理は、`"default"`かその値の1つに設定するだけです。

### Game Master向けの文章

- `checkGuidance`は、GMに判定要求の方法を教える組み込みの段落を置き換えます。システム名と、いつ振るべきかを書いてください。GMはスキルと難易度だけを指定し、Engineがシートから計算して振るため、モデルに計算を求めないでください。
- `sheetGuidance`はプロンプトでシートを紹介します。重要なリソースと消費のタイミングを説明します。
- `worldGuidance`は任意で、世界生成時に1回だけ読みます。火薬なし、魔法が希少、死者が歩くなど、GMが作る舞台を規則に合わせます。各ターンには入りません。
- `sheetSummary`は各キャラクターについてGMに見せるフィールド、派生値、リスト行を選びます。Engineは能力修正値、習熟済みのスキルとセーヴ、ライブ値を常に見せます。毎ターン送るため、それ以外は短くしてください。要約リストの`nameColumn`はテキスト列か列挙列にでき(列挙列は値のラベルを表示します)、`columns`は名前の後に表示する行自身の列を最大3つ追加で指定します。そのためブロックは名前だけでなく`Gear: Crowbar 1d6`のようになります。真偽値列はオンのときにラベルを表示します。どちらも、パッケージ形式のルールセットではCapability API 1.37です。
- `sheetGuidance`でシートコマンドを教える必要はありません。Engineはファイルが宣言する名前を使ってすべてのコマンドを自ら教えます。ルールセットに負傷トラックがあれば、印を付ける`op="damage"`コマンドを加え、段階と負傷の種類を列挙します。ライブステートがあれば、`op="state"`コマンドを加え、各ステートが取り得る値を列挙します。

## カタログ: シートのリスト用の既製項目

呪文リスト、装備表、クラス特性を行ごとに入力するのは大変です。カタログはルールセットに同梱する、名前付きの既製項目集です。供給先の各リストでシート編集画面が選択肢として表示し、1つ選ぶと行を埋めます。

カタログは任意で、最大12個です。Engineはそれぞれが何についてのカタログか知りません。ID、列、フィルター、用語はすべてファイルから来ます。

### ヘッダー

ヘッダーはファイルのトップレベルで、`gm`と並ぶ`catalogs`に入れます。

```json
"catalogs": [
  {
    "id": "knacks",
    "label": "Knacks",
    "feeds": ["knacks", "tricks"],
    "filters": [
      { "id": "grit", "label": "Grit cost", "type": "number" },
      { "id": "road", "label": "Road", "type": "text" },
      { "id": "callings", "label": "Calling", "type": "tags", "startFrom": { "field": "calling" } }
    ],
    "units": { "distance": { "label": "paces", "perCell": 2 } },
    "entries": []
  }
]
```

- `id`と`label`: IDはシートのID規則に従い、ラベルは選択画面の名前です。
- `holds`: `"rows"`(デフォルトで、このリリース以前の全カタログの形式)、`"creatures"`、`"items"`のいずれかです。クリーチャーのカタログは戦闘が読む図鑑で、アイテムのカタログはパーティーが持ち運ぶものの一覧です。どちらもシートへ書かず、`feeds`を宣言せず、選択画面にも出ません。下の[クリーチャー](#creatures-a-bestiary-a-fight-reads)と[アイテム](#items-what-a-party-carries)を参照してください。
- `feeds`: このカタログの項目が書き込めるシートのリストを1～8個指定します。行のカタログでは必須で、クリーチャーやアイテムのカタログでは禁止です。未掲載のリストには書けず、列が保持できない値も書けません。
- `filters`: 任意で最大8個です。選択肢を絞り込む条件で、`number`、`text`、`tags`(複数の語)があります。`startFrom`は開いたときの条件に使うシートのフィールドを指定し、CallingがTinkerならTinkerの項目が最初に見えます。
- `units`: 任意です。項目の`mechanics`の射程や範囲サイズが、システム内で何を意味するかを定めます。

### 項目

```json
{
  "id": "road-sense",
  "label": "Road Sense",
  "summary": "You read a road the way other people read a face.",
  "filters": { "grit": 0, "road": "Ash Flats", "callings": ["Scout", "Courier"] },
  "rows": [
    {
      "list": "knacks",
      "values": { "name": "Road Sense", "notes": "Sneak to notice where a road turns bad." }
    }
  ]
}
```

- `id`: 小文字、数字、単独のハイフンで構成し、カタログ内で一意です。
- `label`と`summary`: 選択画面に表示します。要約は任意で1行、最大300文字です。
- `filters`: ヘッダーが宣言した条件の値です。`number`は数値、`text`は文字列1つ、`tags`は文字列のリストです。
- `rows`: 選択時に書き込む1～6行です。`list`は`feeds`の1つで、`values`はそのリストの列IDをキーにします。
- `creature`: クリーチャーを`holds`するカタログで、行の代わりに敵を指定します。`rows`か`creature`の厳密に片方だけが必要です。クリーチャーは自身の行動で効果を定めるので、`mechanics`を持ちません。

各値を対象リストの列と照合するため、列名の誤字や列の範囲外の値は、出所の項目とともに報告します。ルールセット内に書いた項目はセット読込時、インポートファイルならインポート時に検査します。パッケージの独立したカタログファイルは選択画面が最初に要求した時に検査し、誤りがあれば項目の代わりに理由を表示します。

### 1つの項目から複数のリストへ

回数制限のある特性は、特性本体と使用回数カウンターの2行をシートに持ちます。それでも選ぶのは1項目です。

```json
{
  "id": "last-ember",
  "label": "Last Ember",
  "rows": [
    {
      "list": "knacks",
      "values": { "name": "Last Ember", "notes": "Spend 1 Grit to give a downed friend 3 Grit back." }
    },
    { "list": "tricks", "values": { "name": "Last Ember", "uses": 1, "recharge": "camp" } }
  ]
}
```

### ルールセットが更新を保つ値

選んだ行の数値はプレイヤーのものになります。ただし、能力値と等しい使用回数や、レベルに応じて増えるクラスリソースなど、キャラクターに連動する最大値は例外にする価値があります。行は`scaled`マップに自身の数値列を最大4つ指定でき、シート編集画面がその値を更新します。

```json
{
  "list": "tricks",
  "values": { "name": "Last Ember", "uses": 1, "recharge": "camp" },
  "scaled": { "uses": { "from": { "abilityScore": "heart" } } }
}
```

- キーはリストの`number`列の1つです。
- `from`は他の場所と同じ限定された語彙を使う、通常の値参照です。複雑なものはシートで`derived`値として宣言し、`from`から指します(`"from": { "derived": "lay_on_hands_max" }`)。新しい計算は追加しません。
- `table`は任意です。参照値を段階表で引くことで、レベルから数値を得られます。`"scaled": { "max": { "from": { "field": "level" }, "table": [[1, 2], [3, 3], [6, 4]] } }`です。
- `values`にはその列の通常の数値も必要で、省略した行は拒否します。シートが不明なときの値であり、その参照を持たないシートが維持する値です。
- `scaled`を持つ行は、その項目が同じリストへ書く唯一の行でなければなりません。シート上の印付き行が常に1つの仕様に対応するためです。

値は編集時に計算し、読取時には計算しません。保存行は常に記述どおりの数値です。格納先列の`min`と`max`に制限し、整数列では切り捨てます。上の例ではHeart 3なら3回、Heartが0以下なら0回です。行は使用回数0のまま残り、最大0のカウンターはプールではないため、プレイ中に消費できるものはありません。

パッケージ形式の連動列はCapability API 1.23です。コミュニティのインポートは読み取るEngineが検証するため、別の指定は不要です。

### 選んだ行はコピー

選んだ各行はシートにコピーし、追加キー`_catalog`へ`<catalog id>/<entry id>`を入れます。列IDは必ず英字で始まるため、このキーが自作の列と衝突することはありません。

コピーはキャラクターに属します。プレイヤーは後からどの内容でも編集でき、ルールセットが未インストールでもシートは動作し、新版の公開が誰かのキャラクターを書き換えることもありません。選択画面はこの印から取得済みの項目を示し、下記のRefreshもこれを読みます。

### ルールセットから更新する

選んだ行は印を保つため、シート編集画面はルールセットの新しい文章と保存行との差を通知できます。リストの下に更新のある行数が表示され、**Review**(確認)でシートの内容とルールセットの内容を並べ、各行のチェック欄を表示します。**Update selected**(選択項目を更新)を押すまでは何も書かず、チェックした行の差のある列だけを更新します。印も含め、ほかの内容は維持されます。

比較範囲は意図的に狭くしています。

- 既存値を比較するのは`text`、`longtext`、`dice`、`enum`列だけです。既存の`number`と`boolean`は0やfalseも含めプレイヤーの値として保持します。まだ行にない列は数値やスイッチも含め、型付きの値で提示できます。連動列はすでにシートに従うため除外します。
- 項目が設定する列だけを比較します。項目が省略した列は、シートの内容にかかわらず触りません。
- 廃止した`enum`値や`maxLength`を超える文章など、列自体が拒否する値は書かずに省略します。
- 行は、同じリストで同じ印を持つ行の中の位置によって元の項目の行に対応付けます。項目が書く数とシートの行数が同じ場合に有効です。それ以外は、そのリストへ1行だけ書く項目のみ対応できます。2行の片方をプレイヤーが削除した場合は、推測せず項目全体をそのままにします。
- カタログからなくなった項目の行は、通知なしでそのままにします。

したがって、表現や名前の変更は、プレイヤーが承認すれば取得済みのキャラクターにも反映できます。数値の意味の変更は反映できず、行を取得した後の数値列はプレイヤーのものです。

### `mechanics`: 項目の数値による効果

任意の`mechanics`ブロックで効果を数値化できます。`kind`(`attack`、`heal`、`buff`、`debuff`、`utility`、`rider`)、`range`、`area`、`targets`、`targetCount`、`friendlyFire`、`amount`(`2d6`などのダイスか固定値)、`damageType`、`attackRoll`、`autoHit`、`save`(シートのセーヴと成功時の効果)、`applies`(対象への状態付与)、`temporary`(体力プールの一時ポイント)、`scales`(シートに応じて増える量)、`cost`(消費プール)、`perCostStep`、`budget`(消費する行動枠)、`concentration`、`reaction`、`plus`、`free`、`gives`、`standard`、`rider`、`check`があります。

選択画面はこのブロックを1行で表示します。そのほかの読み手は、ルールセットが選んだブロックで決まります。

- [`combat`ブロック](#combat-a-fight-your-own-rules-resolve)では、戦闘が戦闘効果を読みます。`range`、`area`、`friendlyFire`は位置のある戦場で作用します。`reaction`はターン中に実行するのではなく何かに応じる項目であることを示し、待つ瞬間を指定します([ウィンドウ](#windows-holding-the-fight-open)を参照)。単に`true`とした項目は瞬間を指定せず、メニューにも出ません。`check`は上記のとおりスキル判定に適用します。
- [`battle`ブロック](#battles-lending-the-sheet-to-marinaras-combat)だけなら、戦闘は`kind`、`range`、`area`、`friendlyFire`、`amount`、`damageType`、`cost`を読みます。Marinara独自の戦闘が対応する部分だからです。

語彙は限定され、上記以外のキーや値は黙って無視せず拒否します。

`cost`は戦闘外でGMの`use`コマンドが支払うものでもあります。次の節で説明します。

### `use`コマンド: 指定した価格をGame Masterに支払わせる

GMは描写しながら`[sheet: ...]`でシートを更新します。`spend`、`restore`(`heal`も同義)、`damage`、`temp`、`track`、`condition`、`note`、`rest`です。カタログを持つルールセットでは、さらに1つ加わります。

```
[sheet: who="Mira" op="use" name="Fireball"]
[sheet: who="Mira" op="use" name="Fireball" pool="3rd-level slots"]
```

`op="cast"`は`op="use"`、`spell=`は`name=`と同じ意味です。形式に「呪文」という概念を組み込まなくても、GMが使いやすい言葉で動作します。

名前は、キャラクターシートのカタログ由来の行に、大小文字を区別せず照合します。行はGMに見せた名前(そのリストの`sheetSummary`名前列、次に`pools.nameColumn`、最後に最初のテキスト列)と、元項目の`label`の両方に応じるため、改名しても使えます。該当しない名前と、異なる2項目に該当する名前はどちらも拒否します。

消費するものは次のとおりです。

- 項目の`mechanics.cost`の全要素です。ライブプール指定ならそのプールから払い、プールグループなら宣言順で最初に支払えるプールから払います。グループは必ずしも段階表ではないため、上位プールへ自動的に繰り上げることはありません。
- 加えて、同じ項目が書いた全リスト行プールから1回分を消費します。上の`Last Ember`の2行目のような特性の使用回数です。最大値0のカウンターには使える回数がなく、無料で通さずコマンドを拒否します。

`pool=`は上位発動です。同じ単一の価格を、同グループの別プールから払います。コストが厳密に1要素で、指定プールがそのグループに属する場合だけ受け付けます。それ以外は解釈し直さず拒否します。

一括で成否を決めます。どれか1つでも払えなければ全コマンドを拒否し、何も変えずプレイヤーへ通知します。初級呪文や常時特性など、コストがまったくない項目は受け付け、何も変更しません。

### インラインか独立ファイルか

小さなカタログは`ruleset.json`のヘッダーの`entries`内に置きます。長いものは別ファイルに置き、ヘッダーは代わりに`asset`で指定します。厳密に片方だけが必要です。

```json
{ "id": "knacks", "label": "Knacks", "feeds": ["knacks"], "asset": "catalogs/knacks.json" }
```

パスは常に`catalogs/<the catalog's id>.json`です。ファイルの形は次のとおりです。

```json
{ "schemaVersion": 1, "catalog": "knacks", "entries": [] }
```

独立したカタログファイルは公式カタログ経由のパッケージ用です。`contributions.assets.paths`で`ruleset.json`とともに宣言し、Capability API 1.21が必要です。クリーチャーのカタログはインラインでも別ファイルでも1.27、アイテムのカタログは1.49が必要です。**単一ファイルでインポートする、またはGitHubリポジトリで共有するルールセットはカタログをインラインで持つ**ため、ファイル全体の256 KB以内に収めます。短い項目なら数百件入ります。

上限はルールセットごとに12カタログ、どちらの形式も1カタログ2,000項目、独立カタログ1ファイル1 MBです。

## アイテム: パーティーが持ち運ぶもの

鎧、武器、ポーション、装備品、弾薬、お金はアイテムです。任意の`items`ブロックはルールセットのすべてのアイテムを記述する語彙を宣言し、`holds: "items"`のカタログがアイテムそのものを列挙します。どちらもCapability API 1.49が必要です。機能ごとに必要なバージョンは次のとおりです。GMが作るアイテムを制御するブロックの`rarityCaps`と`propose`は1.51、キャラクターが持つアイテムを読む値(`itemStat`)は1.52、装備中や携行中のアイテムが判定に与える効果とブロックの`bonus`上限は1.53、アイテムが装備者に求める要件と変更する能力値は1.54、武器の`attack`は1.55、アイテムの戦闘中の効果は1.56、武器が撃つものと装填しておく数は1.57、武器のモード、オフハンド攻撃、下限、命中時の状態は1.58、戦闘でのアイテム使用の効果と保持するチャージは1.59、プールを回復する使用は1.60、休息で回復するチャージや使い切ると壊れるアイテムは1.61、先に判定を求める使用(`gate`)は1.62、戦利品表とクリーチャーの戦利品は1.63、硬貨を落とす戦利品の行や硬貨を除くレイヤーは1.64、市場、アイテムの`sold`の場所、`service`は1.65、市場の一日(財布、`buyBack`、売り手の`stock`、`limited`の数、場所を指定しない`sold`)は1.69、手に持った武器で発動する追加効果(`weapons`)は1.70です。

### アイテムブロック

ブロックはファイルのトップレベルの`items`に置きます。以下はEmber Roadsのもので、少し短くしています。

```json
"items": {
  "categories": [
    { "id": "weapon", "label": "Weapon" },
    { "id": "armor", "label": "Armor" },
    { "id": "ammunition", "label": "Ammunition" }
  ],
  "rarities": [
    { "id": "common", "label": "Common" },
    { "id": "storied", "label": "Storied" }
  ],
  "tags": [
    { "id": "thrown", "label": "Thrown" },
    { "id": "ranged", "label": "Ranged" },
    { "id": "two_handed", "label": "Two-handed" },
    { "id": "arrow", "label": "Arrow" }
  ],
  "stats": [
    { "id": "bulk", "label": "Bulk", "type": "number", "min": 0, "max": 10, "default": 0 },
    { "id": "guard", "label": "Guard", "type": "number", "min": 0, "max": 4, "default": 0 },
    { "id": "damage", "label": "Damage", "type": "dice", "example": "1d6" },
    { "id": "swing", "label": "Rolls with", "type": "enum", "values": ["brawn", "wits", "heart"], "default": "brawn" },
    { "id": "reach", "label": "Reach", "type": "enum", "values": ["close", "near", "far"], "default": "close" }
  ],
  "slots": [
    { "id": "body", "label": "Body", "count": 1 },
    { "id": "hands", "label": "Hands", "count": 2 }
  ],
  "carry": { "stat": "bulk", "encumberedAbove": { "derived": "load" }, "limit": { "const": 12 } },
  "rarityCaps": [
    { "rarity": "common", "stats": { "guard": 1 }, "bonus": 1 },
    { "rarity": "storied", "stats": { "guard": 3 }, "bonus": 2 }
  ],
  "currencies": [
    {
      "id": "coin",
      "label": "Coin",
      "perWeight": 100,
      "units": [
        { "id": "bit", "label": "bits", "value": 1 },
        { "id": "mark", "label": "marks", "value": 10 },
        { "id": "sovereign", "label": "sovereigns", "value": 100 }
      ]
    },
    {
      "id": "salt",
      "label": "Salt",
      "perWeight": 10,
      "units": [
        { "id": "pinch", "label": "pinches", "value": 1 },
        { "id": "cake", "label": "cakes", "value": 20 }
      ]
    }
  ]
}
```

- `categories`: 1～24個です。すべてのアイテムは鎧、武器、ポーションなど、厳密に1つのカテゴリーを持ちます。
- `rarities`: 任意で最大12個です。最もありふれたものから最も希少なものの順に並べます。
- `tags`: 任意で最大48個です。投擲用や銀製など、アイテムが持てる特性です。
- `stats`: 任意で最大24個です。アイテムが持つ数値や語で、リストの列とまったく同じく`number`、`text`、`boolean`、`enum`、`dice`として宣言し、型に応じて範囲、値、デフォルトを指定します。`promptVisible`(デフォルトは`true`)は、GMにアイテムと並べてそのステータスを見せるかです。アイテムの隠し場所など、プレイヤーだけが見るべきものには`false`を設定します。
- `slots`: 任意で最大12個です。アイテムを身に着ける、または持つ部位と、キャラクターが持つその部位の数(1～20)です。
- `binding`: 任意です。同調や授与など、1人のキャラクターが同時にバインドできるアイテム数を制限するものです。`label`はその呼び名、`max`はキャラクターのシートから読む値で、`{ "abilityScore": "nerve" }`や派生値などです。バインドできるアイテム数は打撃のたびに変わるものではないため、ライブ状態は読めません。
- `carry`: 任意です。`stat`はアイテムの重量となる数値ステータスを指定し、その`min`は0以上です。`encumberedAbove`は重量超過になるまでに運べる量、`limit`(任意)は運べる最大量です。どちらも`binding.max`と同じくシートから読みます。`carry`がなければ重量は意味を持たず、誰も重量超過になりません。
- `currencies`: 任意で、1～10種類の硬貨からなる系統を最大6つ持てます。
  - 同じ系統の硬貨は、系統の最小硬貨を単位に数える`value`によって互いに両替できます。そのため最小硬貨の価値は1で、同じ系統の2つの硬貨が同じ価値を持つことはありません。
  - 2つの系統は互いに両替できません。他国の硬貨や、舞台設定上の恩義などは独立した系統です。
  - アイテムのコストは硬貨だけを指定するため、硬貨のIDはすべての系統を通じて一意です。
  - `perWeight`(任意で、`carry`がある場合だけ)は、その系統の硬貨がいくつで運搬ステータス1単位の重さになるかです。
  - 硬貨はパーティーのお金で、ほかのアイテムと同じく袋に入れて持ち運びます(後述の「お金」を参照)。
- `rarityCaps`: 任意で、レアリティーごとに最大1つです。GMが作るアイテムがそのレアリティーで与えられる上限です。`stats`で指定した各数値ステータスの最大値(そのステータス自身の範囲内で、整数のステータスなら整数)と、`bonus`(Capability API 1.53)、つまり装備中・携行中の修正値の1つが加えられる最大の固定ボーナスです。`bonus`のあるレアリティーでは、ダイスは数値に制限できないため、ダイスによるボーナスは省きます。ペナルティには上限を設けません。作られたアイテムはこれに制限されます。カタログに載せたアイテムは作者のもので、制限しません。
- `propose`: デフォルトは`true`です。`false`にすると、GMはルールセットのアイテムを作れません。
- `native`: デフォルトは`true`です。`false`にすると、ルールセットのゲームでGame Mode自身の型なしアイテムをオフにします(**アイテムを読み取るもの**を参照)。GMは引き続き、ルールセットの語彙でアイテムを作れます。
- `freeform`: プレイヤーが入力したアイテムの扱いです。`"plain"`(デフォルト)は現在と同じく、規則を持たないアイテムとして残します。`"refuse"`はルールセットのアイテムだけを許可します。
- `lootTables`(Capability API 1.63): 任意で最大24個です。勝利した戦闘のクリーチャーとGMの`[loot:]`が落とすものです(後述の「戦利品」を参照)。

### アイテムの項目

アイテムのカタログは`feeds`を宣言しません。

```json
{ "id": "outfitter", "label": "Outfitter", "holds": "items", "entries": [] }
```

各項目は`rows`や`creature`の代わりに`item`を持ちます。

```json
{
  "id": "hunting-bow",
  "label": "Hunting bow",
  "summary": "Yew, waxed string, and a grip worn smooth by someone else's hand.",
  "item": {
    "category": "weapon",
    "rarity": "common",
    "tags": ["ranged", "two_handed"],
    "stats": { "bulk": 2, "damage": "1d8", "swing": "wits", "reach": "far" },
    "slots": { "hands": 2 },
    "cost": { "amount": 3, "unit": "sovereign" }
  }
}
```

- `id`、`label`、`summary`、`filters`はほかの項目と同じです。ラベルはアイテムの名前です。
- `category`は必須です。`rarity`と`tags`は任意で、3つともブロック自身のIDを指定します。アイテムがレアリティーを持てるのは、ブロックがレアリティーを宣言している場合だけです。
- `stats`: ブロックのステータスの値です。それぞれ、そのステータスが持てる値です。
- `slots`: アイテムが占める各スロットの数で、キャラクターが持つ数を超えません。
- `stack`: 1スタックの最大数で、1～999,999です。指定しなければ、Game Modeのスタックと同じ数まで入ります。`charges`を持つアイテムは1スタックに1つです。
- `cost`: 1種類の硬貨の整数の`amount`で、硬貨は`unit`のIDで指定します。選択画面に表示し、GMもアイテムと並べて見ます(後述の「お金」を参照)。
- `sold`(Capability API 1.65): `{ "place": "city" }`で、市場の場所のうちアイテムを売る最小の場所を指定し、ほかの規則より優先します。1.69では、その代わりに、またはそれに加えて、ある場所が1日に置いておく数も指定できます(`"limited": 2`または`"limited": "1d3"`)(後述の「市場」を参照)。
- `service`(Capability API 1.65): 宿泊、渡航、祝福などには`true`を指定します。アイテムと同じく購入しますが、持ち運びません。購入は支払うだけで、ほかに袋へ入れる処理はありません(追加しようとすると`service`として拒否されます)。選択画面もサービスを除外します。サービスは`cost`を持ち、持ち運びや使用に関するもの(`slots`、`stack`、`binds`、`worn`、`carried`、`requires`、`attack`、`use`、`charges`)は持ちません。
- `binds`: 装備中に効果を発揮するには、アイテムのバインドが必要です。`restriction`(任意)はバインドできる人を文章で示し、`cursed: true`は外れなくなるアイテムを示します。バインドするアイテムを持てるのは、`binding`のあるルールセットだけです。
- `worn`と`carried`(任意、Capability API 1.53): 装備中と、携行しているだけの間に、アイテムが持ち主の判定とセーヴに与える効果、(1.54)設定または上昇させる能力値、(1.56)戦闘中の効果です。[戦闘外の判定](#checks-outside-a-fight)と[戦闘中の鎧と装備効果](#armor-and-worn-effects-in-a-fight)を参照してください。
- `requires`(任意、Capability API 1.54): アイテムが装備者に求めるものと、満たさない間に適用されるものです。[戦闘外の判定](#checks-outside-a-fight)を参照してください。
- `attack`(任意、Capability API 1.55): 装備中に戦闘で武器としてアイテムが行うこと、(1.57)撃つものと装填しておく数、(1.58)ほかのモード、オフハンド攻撃、被害の下限、命中時に付与する状態です。[戦闘中の武器](#weapons-in-a-fight)、[弾薬と再装填](#ammunition-and-reloading)、[モード、2つ目の武器、下限、命中時の状態](#modes-a-second-weapon-a-floor-and-conditions-on-a-hit)を参照してください。
- `use`と`charges`(任意、Capability API 1.59): 戦闘中と戦闘外でアイテムを使用したときの効果、その使用が消費するチャージ、(1.60)回復するプールです。[戦闘中のアイテム使用](#using-items-in-a-fight)と[戦闘外のアイテム使用](#using-items-outside-a-fight)を参照してください。

アイテムは`mechanics`を持ちません。効果は`item`ブロックに書きます。

### アイテムを読み取るもの

上記はすべてルールセットのインポート時に検査し、アイテムのカタログはルールセットとともに配布されます。ゲームでは、Game Modeのインベントリーがそれを読み取ります。

- **アイテムは袋に入ります。** スタックはルールセットのアイテムの1つにでき、プレイヤーが何と呼んでもそのアイテムのままです。インベントリーの**From the ruleset**(ルールセットから)ボタンは、カタログが列挙するすべてのアイテムを並べた選択画面を、カタログの検索とフィルター付きで開きます。項目を隠すレイヤーは、そこでも隠します。
- **名前でアイテムを見つけます。** プレイヤーが入力した名前や、GMが`[inventory: action="add"]`に書いた名前が、大文字・小文字を問わずルールセットのアイテムの`label`なら、そのアイテムを追加します。2つのアイテムが同じラベルを持つ場合は、カタログで先に列挙したものが見つかります。
- **`stack`**は維持されます。追加、設定、統合、譲渡でそれを超えるとスタックを満たし、新しいスタックを始めます。
- **`freeform: "refuse"`**では、プレイヤーはルールセットのアイテムだけを扱えます。選択画面と、ルールセットのアイテムである名前です。
- **`native: false`**では、GMはルールセットのアイテムと自ら作るアイテムだけを扱えます。どちらでもない名前は拒否されます(`not-ruleset-item`)が、すでに持っているものは引き続き追加でき、GMへの指示にもそう書かれます。戦闘はインベントリーのアイテムが何をするかをモデルに尋ねなくなるため、戦うのはルールセットのアイテムだけです。ルールセットの戦闘では手に持った武器とアイテムの使用(後述の「戦闘中の武器」を参照)、ClassicやTacticalの戦闘では`use`を持つアイテム(後述の「ClassicとTacticalの戦闘でのアイテム」を参照)です。プレイヤーの入力は引き続き`freeform`に従い、パーティーが持っていたものはどちらの場合も新しいセッションに戻ります。
- **アイテムの情報**は選択したスタックに表示されます。ラベルによるカテゴリー、レアリティー、タグ、与えるステータス、要約、1スタックの最大数です。選択画面は`cost`も表示します。GMは手元にある各アイテムを、カテゴリー、レアリティー、タグ、`promptVisible`のままにしたステータスとともに見ます。`Hand axe [Weapon, Common, Thrown; Damage 1d6, Reach close]`のような形です。

- **`slots`**: スロットを占めるアイテムは、それを運ぶキャラクターのスロットに空きがある間、装備できます。大きなスタックのアイテムは、1つを別のスタックに分けて装備します。インベントリーはキャラクターごとに使用中のスロットを表示します。
- **`binding`**: `binds`を持つアイテムは、持ち主自身のシートから読む`binding.max`までバインドできます(シートのないキャラクターは空白のシートを読みます)。`cursed`のアイテムは一度バインドするとバインドされたままです。プレイヤーはバインド解除、取り外し、譲渡、削除ができず、呪いを解けるのはGMだけです。
- **`carry`**: アイテムの重量は`carry.stat`の値で(値のないアイテムは重さがありません)、キャラクターの荷重は袋の重さです。それを自分のシートから読む`encumberedAbove`や`limit`と比べます。プレイヤーや、`who=`のないGMがインベントリーの共有ビューに追加したアイテムは、重量超過にならずに運べる人へ渡ります(まずプレイヤー、次にパーティーの順)。全部を引き受けられる人がいなければ、各自の残りの余裕に応じて分けます。誰の`limit`も超えません。誰も運べないものは置いていき、GMに伝えます。1/4ポンドのような重さには、重量ステータスに`"integer": false`を指定します。
- **GMはルールセットの語彙でアイテムを作ります。** `propose: false`を設定しない限り、GMの`[inventory: action="add"]`は新しいアイテムを記述できます。出発点にするルールセットのアイテムを`like=`で指定し、続いて`category=`、`rarity=`、`tags=`、`stats=`(`id=value`の組)、`slots=`(`id=count`)、`binds=`(`yes`、`cursed`、`no`)、`worn=`と`carried=`(`;`で区切った変更。それぞれ、名前で指定したスキルやセーヴ、またはすべてを表す`checks`や`saves`に対する`+N`、`-N`、`advantage`、`disadvantage`、セーヴの`fails`、能力値名に対する上下の`+N`や`-N`、さらに戦闘があるルールセットでは、攻撃に対する`+N`、`-N`、有利、不利と、防御(またはルールセットでの呼び名)に対する`+N`や`-N`です。`worn="+1 Sneak; disadvantage on Sway checks"`、`carried="+1 Brawn"`、`worn="+1 Guard"`、または`none`と書きます)、`summary=`のいずれかを、それぞれIDかラベルで指定します。防御がすでに数えているアイテムのステータス(Ember RoadsのGuardは装備品の`guard`を合計します)は鎧が防御を上げる手段なので、そうしたステータスと並べた装備中の防御変更は省き、回答でもそう伝えます。小さなモデルは1つの+1に対して`guard=1`と`+1 Guard`の両方を書くためです。小さなモデルが代わりに書きがちなものも読み取ります。名前の後の数値(`Brawn +1`)、攻撃や防御の後の「bonus」(`+1 attack roll bonus`)、タグ、ステータス、スロットの空のリストを表す`none`、同名のステータスがない場合の`stats=`内の`worn=`、`carried=`、`summary=`です。Engineはブロックにあるものだけを残します。未知のカテゴリー、タグ、ステータス、スロット、スキル、セーヴは省き、ないレアリティーは最低のものになり、数値はステータスの範囲、次にそのレアリティーの`rarityCaps`に制限し、装備中や携行中のボーナスはそのレアリティーの`bonus`に制限します(`like`で引き継いだ部分も同様です)。ルールセットのアイテムの名前は、そのままそのアイテムになります。回答はGMに変更内容を伝え(GMに見せないステータスについては伝えません)、アイテムの詳細はすべての変更をプレイヤーに示します。ゲームはアイテムを保持するため、同じ名前はゲームの終わりまでそのアイテムを指し、誰かが持っている限り新しいセッションでも保持されます。
- GMは、ルールセットに`slots`があればインベントリーコマンドで`equip`と`unequip`を、`binding`があれば`bind`と`unbind`を使えます。GMに伝えるのは、ルールセットにあるものだけです。GMは各キャラクターの荷重、バインド済みのアイテムとスロット、装備中またはバインド済みのものを見ます。

- **装備中や携行中のアイテムの効果**は、選択したスタックと選択画面に表示され(「While worn: -1 on checks (Sneak)」)、GMもアイテムと並べて見ます(`worn: -1 on checks (Sneak)`)。戦闘外の判定がこれを適用します(後述の「戦闘外の判定」を参照)。
- **武器の効果**も同様に表示され(「Attack (Action): Brawn to hit, 1d6 + Brawn cut damage」)、手に持っている間、戦闘で提示されます(後述の「戦闘中の武器」を参照)。
- **アイテム使用の効果**も同様に、残りのチャージとともに表示されます(「Use (Action): heals 1d4 + 1, range 0 paces, used up」)。戦闘で提示され、インベントリーの**Use**(使用)ボタンとGMの`[inventory: action="use"]`でも使えます(後述の「戦闘中のアイテム使用」と「戦闘外のアイテム使用」を参照)。

ClassicやTacticalの戦闘では、`use`を持つ各アイテムが記述どおりに働き、持たないものは提示されません(後述の「ClassicとTacticalの戦闘でのアイテム」を参照)。`native`の設定にかかわらず、シートはアイテムを読めます(後述)。手に持った武器はルールセットの戦闘での攻撃となり、撃つものを袋から取り出します。装備中や携行中のアイテムの効果はルールセットの戦闘でも数えます(後述の「戦闘中の鎧と装備効果」を参照)。`use`を持つアイテムは、戦闘中も戦闘外も独自の規則で使用されます(後述の「戦闘中のアイテム使用」と「戦闘外のアイテム使用」を参照)。`currencies`はパーティーのお金です(後述の「お金」を参照)。

<a id="items-on-the-sheet"></a>

### シート上のアイテム

値参照は`itemStat`でキャラクターが持つアイテムを読めます(Capability API 1.52)。Ember Roadsは、旅人が装備している鎧のガード値をGuardに加えます。Guardは打撃が上回る必要がある値です。

```json
{
  "id": "guard",
  "label": "Guard",
  "op": "sum",
  "of": [{ "const": 6 }, { "abilityMod": "wits" }, { "itemStat": { "stat": "guard", "from": "worn", "pick": "sum" } }]
}
```

- `from`: `"worn"`はキャラクターが身に着けているアイテムです。スロットを占めるアイテムは装備中、`binds`を持つものはバインド中、両方を持つものはその両方の間が対象です。どちらも持たないアイテムは身に着けている扱いになりません。`"carried"`は持っているそれ以外のもの、`"all"`は両方です。
- `pick`: `"sum"`は各アイテムの値に個数を掛けて合計し、`"max"`と`"min"`は単一の値の最大または最小を読み、`"count"`はアイテムを個数で数えます。
- `stat`はアイテムのステータスの1つを指定します。`sum`、`max`、`min`には`number`のステータスが必要です。`count`は省略してすべてのアイテムを数えるか、任意のステータスを指定してそれを与えるアイテムだけを数えられます。
- `slot`、`category`、`tag`(それぞれ任意)は、そのスロットを占める、そのカテゴリーの、そのタグを持つアイテムだけに絞ります。
- `default`(任意、省略時は0)は、アイテムが選ばれない場合や、どれもそのステータスを与えない場合に読む値です。

アイテムはプレイ中に変わるため、`itemStat`はライブ値の読み取りと同じ規則に従います。プールやトラックの`max`、習熟ボーナス、`binding.max`、`carry`の数値、カタログの連動列やスケーリングは、派生値を通じてもそれを読めません。それ以外で数値を読む場所なら読めます。派生値、判定の`adjust`、スキルの`cap`、戦闘の防御、吸収、イニシアチブです。

キャラクターのアイテムは自分の袋に入っているものです。プレイヤーのカード(チャットで演じている人物の名前を持つカード、なければ最初のカード)はプレイヤーの袋を、ほかのカードはそれぞれ自分の袋を読みます。普通のアイテムには読むステータスがないため、数えるのはルールセットのアイテムだけです。画面上のシート、判定、GMのシートブロック、開始時の戦闘は、いずれもその時点で各キャラクターが持っているものを読みます。ゲーム外のシートエディターやインポートの確認画面では誰も何も持っていないため、`itemStat`は`default`を読みます。


<a id="checks-outside-a-fight"></a>

### 戦闘外の判定

GMが戦闘外で求める判定やセーヴは、シート以外も読みます。キャラクター自身の有効な状態、到達した段階、装備中や携行中のアイテムの効果、満たしていない装備品の要件によるコストです。戦闘の状態と同じ語彙を使います(アイテムのキーと絞り込みはCapability API 1.53)。

アイテムは、身に着けている間(バインドが必要ならバインド中)に適用する`worn`と、携行しているだけの間に適用する`carried`で効果を示します。Ember RoadsのLeather coatは忍び歩くと軋み、Waystoneを持っていると隊商の人々に信用されます。

```json
"worn": { "modifiers": [{ "to": "checks", "skills": ["sneak"], "flat": -1 }] }
```

```json
"carried": { "modifiers": [{ "to": "checks", "skills": ["sway"], "flat": 1 }] }
```

どちらも、状態のうち判定が読む部分を受け付けます。

- `effects`: `own-checks-advantage`、`own-checks-disadvantage`、`own-saves-advantage`、`own-saves-disadvantage`です。
- `modifiers`: 判定やセーヴへの変更(`to`)で、状態とまったく同じく`flat`、`dice`(と`minus`)、`mode`、独自の`skills`や`saves`を持ちます。
- `failsSaves`: 持ち主がロールせずに失敗するセーヴです。
- `skills`と`saves`: 効果と、独自の対象を指定しない修正値が対象とするスキルやセーヴです。
- `abilities`(Capability API 1.54): IDで指定する、変更する能力値です。それぞれ`{ "set": N }`(最低N。それより高い値はそのまま)か`{ "add": N }`(負の数値で下げます)です。シートの計算前に適用するため、その能力値を読むものはすべて変更後の値を読みます。画面上のシート、派生値、判定、GMのシートブロック、開始時の戦闘です。先に加算を適用し、次に最も高い`set`を適用し、能力値自身の`min`と`max`は守られます。プールやトラックの最大値と習熟ボーナスはシートだけから計算するため、アイテムはそれらを動かしません。

Ember RoadsのOx-hide gauntletsは、握力の弱い者に牛追いの握力を貸します。

```json
"worn": { "abilities": { "brawn": { "set": 2 } } }
```

戦闘でのアイテムの効果(防御、攻撃、速度、戦闘のほかの効果、防ぐ被害と状態)は[戦闘中の鎧と装備効果](#armor-and-worn-effects-in-a-fight)で説明します。戦闘外の判定が読むのは上記の部分だけです。1つのアイテムは、何スタック持っていても1回だけ適用します。

アイテムは`requires`で装備者に何かを求めることもできます。シート上の値(`value`。任意の値参照で、プレイ中のすべての値と同じように読みます)、その最低値(`atLeast`)、満たさない間に適用するもの(`otherwise`。同じ語彙ですが、求めるものが能力値を読むことがあるため、能力値は変更できません)です。最大4つです。GravewatchのGrave spadeは、非力な番人には重労働です。

```json
"requires": [
  {
    "value": { "abilityScore": "sinew" },
    "atLeast": 3,
    "otherwise": { "modifiers": [{ "to": "checks", "skills": ["dig"], "flat": -1 }] }
  }
]
```

要件は装備者のアイテムを反映した後の能力値を読むため、Sinewを3にする篭手があれば、Grave spadeの要件を満たします。

判定では次のように扱います。

- 対象となるすべての修正値が数値を加え、ダイスを振ります。合計方式の判定では固定値、プールではダイスです。能力値判定と、ルールセットが名前を付けられない判定は、何にも絞り込まれていないものだけを読み、セーヴはセーヴを対象とするものだけを読みます。
- GMの`mode=`も含め、すべての出所からの有利と不利は打ち消し合います。有利と不利がそれぞれ1つ以上あれば、判定は1回だけ振ります。偏るのは、そもそも2回振るルールセット(`resolution.advantage`)だけです。
- 状態やアイテムで失敗するセーヴは、ロールせずに失敗し、何も消費しません。
- 記録には変更の理由が残ります。数値は`effects="-1"`、変更したものは`from="Leather coat"`、ロールせずに失敗したセーヴは`automatic="true"`です。ダイスカードも同じ内容を示し、GMは次のターンにそれを読みます。GMにはEngineがこれらを適用することが伝えられるため、重ねて加えることはありません。

Gravewatchはプールで同じことを示します。バインドしたDawn bellはWardにダイスを1個加え、RattledはSootheとBarterから1個減らします。

<a id="weapons-in-a-fight"></a>

### 戦闘中の武器

アイテムは武器にできます(Capability API 1.55)。その`attack`は、combatブロックの[攻撃の行](#combat-a-fight-your-own-rules-resolve)と同じ形で、列の代わりに値を持ちます。[ルールセットの戦闘](#combat-a-fight-your-own-rules-resolve)は、アイテムを身に着けている間、つまり占める手に持ち、バインドが必要ならバインドしている間、それを攻撃として提示します。しまっているものや携行しているだけのものは何も提示せず、攻撃の行とクリーチャー自身のアクションは従来どおりに動作します。Ember RoadsのHand axeは次のとおりです。

```json
"attack": {
  "budget": "act",
  "toHit": { "abilities": { "stat": "swing" } },
  "damage": { "dice": { "stat": "damage" }, "abilities": { "stat": "swing" }, "type": "cut" },
  "reach": 2,
  "range": { "normal": 10, "long": 20 }
}
```

- `budget`: 消費する行動枠で、`combat.economy.budgets`の1つです。
- `toHit`: 命中に加えるものです。`abilities`は1つ以上の能力値IDで、その最良のものを数えます(フィネス武器は2つ列挙します)。`skill`は、攻撃の行と同じく、スキル自身の能力値の代わりに攻撃の能力値を使って、そのスキルの判定が加える値を加えます。`proficiency`は持ち主のシート上の値で、0より大きければルールセットの習熟ボーナスを加えます(常に加えるなら`{ "const": 1 }`)。`bonus`は数値です。`target`はプール方式の戦闘でのこの武器の攻撃のダイスごとの目標値です(GravewatchのGrave spadeは、プールの7ではなく6以上の目をすべて数えます)。指定できるのは`target`を動かせる`dice-pool`のルールセットだけで、合計方式の戦闘では`bonus`が同じことを表します。
- `damage`: 与える`dice`、加えるダメージの`abilities`の最良のもの、`bonus`、`type`です。合計方式の戦闘には`dice`が必要です。プール方式の戦闘では、命中で成功数分のダメージを与え、`dice`はプール自身のダイスをその数だけ加えます。
- `reach`と`range`(`normal`と、それを超えても届く`long`)は`combat.distance`の単位で、それが必要です。両方を持つ武器は、攻撃の行と同じく投擲武器です。近くでは振るい、その先では投げます。どちらもなければ1マスに届きます。
- `versatile`: 持ち主が身に着けているものの中で、占める各スロットに同じだけの空きがある間に代わりに与える`dice`です。片手で持ち、もう片方の手が空いている槍などです。
- `strikes`: 攻撃の行の`strikes`と同じく、1回の消費で得る打撃の回数で、持ち主のシートから読みます。これがない武器は、使い手が何回攻撃できても1回の消費で1打撃です。

これらの数値や語は、代わりにアイテム自身のステータスを読めます。`{ "stat": "damage" }`はアイテムの`damage`で、アイテムが何も与えないステータスは値を書かなかったのと同じです。`abilities`と`skill`は語が能力値IDやスキルIDである列挙ステータスを、`type`はテキストや列挙のステータスを読みます。そのため、GMが武器を`like=`にして作るアイテムも、自身のステータスで戦う武器になり、ほかのステータスと同じく`rarityCaps`に制限されます(書き込んだ値はそのままコピーします)。スロットもバインドもなしに作ったものは身に着けられないため、攻撃なしで作られます。小さなモデルは武器を記述しても`like=`を省きがちなので、出発点なしで武器のカテゴリーに作られたものは、そのカテゴリーの武器のうち名前が最も似たもの(どちらかの向きで共有する語。crossbowはbowに似ています)、なければ最初のものとして戦い、提案が省いた、その攻撃が読むステータスを引き継ぎます。回答もそう伝えます(「It fights as Hand axe does.」)。GMの提案フォームも、ある武器に似せて作った武器はそれと同じように戦うことを伝えます。

武器のタグは、その打撃が帯びるものです。クリーチャーの`resist`や`immune`の項目は、何がそれを通り抜けるかを指定できます。`{ "type": "tearing", "except": ["silver"] }`は、`silver`タグの武器からは全量を受け、それ以外からは抵抗します。GravewatchのGrave wightはそのように書かれ、Silver coffin nailが通ります。

武器の詳細とGMへの行には、その効果が示されます。`attack (Action): Brawn to hit, 1d6 + Brawn cut, reach 2 paces, range 10 to 20 paces`で、Ember RoadsのBoar spearには`1d8 with a hand free`、GravewatchのGrave spadeには`at 6`が付きます。

<a id="ammunition-and-reloading"></a>

#### 弾薬と再装填

武器は何かを撃つことができ、自身に装填数を保持できます(Capability API 1.57)。Ember RoadsのHunting bowは矢を撃ち、GravewatchのWatch pistolは番人の弾と火薬から装填した1発を保持します。

```json
"ammo": { "tag": "arrow", "recover": 0.5 }
```

```json
"ammo": { "tag": "shot" },
"clip": { "max": 1, "reload": "act" }
```

- `ammo`: 武器が撃つもので、アイテムの`tags`の1つで指定します。攻撃ごとに、持ち主が持つ(身に着けているかどうかを問わない)そのタグのアイテムを`perAttack`個(指定がなければ1)、袋の最初の該当スタックから、次に次のスタックから取ります。十分に持っている間だけ武器を提示し、戦闘メニューに残数を表示します。パーティーが勝った戦闘の後、各自が撃ったものの`recover`(0から1)の割合が、元のスタックに戻ります。割合は戦闘全体で合計し、スタックごとに1回切り捨てるため、1つの矢筒から撃った5本の矢の半分は2本です。負けた戦闘や逃げた戦闘では何も戻りません。
- `clip`: 武器自身が保持する装填数です。`max`は保持できる数で、直接書くかアイテムの数値ステータスから読みます。`reload`は再装填で消費する行動枠です。攻撃は袋から取る代わりに装填分を消費し、武器は1回分を保持している間だけ提示されます。戦闘メニューの**Reload**(再装填)は`reload`を消費して装填します。`ammo`があれば袋から(袋の残りが少なければその分だけ)、なければ全量を装填します。数は武器のインベントリーのスタックに保持するため、ある戦闘で空になったピストルは次の戦闘でも空です。まだ誰も撃っていない武器は装填済みで、プレイヤーが同じ武器を複数まとめたスタックに入れたものも同様です。装填数は1つの武器のものだからです。装填した弾は戦闘後に回収しないため、`recover`は装填数を持たない武器用です。

戦闘で撃ったもの、装填したもの、回収したものは、パーティーの体力と同じく各段階でインベントリーに書き込み、Journal(記録)に使ったものが残ります。スタックがなくなった段階や、戦闘が当てにしていたより少ない段階は、戦闘が見つけられない消費アイテムと同じく拒否されます。戦闘ログはすべての射撃、再装填、回収を示し(「Hunting bow: 2 left to shoot.」、「Ada loads 1 into Watch pistol: 1 of 1 loaded.」)、アイテムの詳細とGMへの行は武器が撃つものと保持するものを示します。`ammunition Arrow (1 an attack, 50% picked up after a won fight)`と`holds 1, reload (Act)`です。

<a id="modes-a-second-weapon-a-floor-and-conditions-on-a-hit"></a>

#### モード、2つ目の武器、下限、命中時の状態

武器は、攻撃の別の方法、オフハンドの相棒、与える被害の下限、命中した相手に付与する状態を持てます(Capability API 1.58)。Ember RoadsのHunting bowは一斉射撃ができ、GravewatchのSilver coffin nailは両手に1本ずつ持てて、深く刺さった相手に印を付けます。

```json
"modes": [{ "id": "volley", "label": "Volley", "ammo": 2, "toHit": -2, "targets": 2 }]
```

```json
"offHand": true,
"onHit": [{ "condition": "marked", "atLeast": 2, "rounds": 2 }]
```

- `modes`: 攻撃の別の方法で、最大6つです。それぞれ`id`、`label`、変更する内容を持ちます。`ammo`はそのモードの1回の攻撃で撃つ数なので、武器は撃つための`ammo`か`clip`を持ちます。`toHit`は命中に加える値で、プール方式の戦闘ではダイス、合計方式では数値です。`target`は、プールの目標値を動かせる場合に、プール方式の戦闘のダイスごとの目標値をこの量だけ動かします(武器自身の目標値、なければプールの目標値から。`+1`は難しくなります)。`targets`は狙える相手の数で、それぞれ個別に攻撃判定をします。戦闘メニューは攻撃を選んだ後(スタイルがあればイニシアチブのスタイルの後)に方法を尋ね、それぞれの見込みを示し、持ち主が撃てる分のあるモードだけを提示します。Engineが操作するパーティーメンバーは1体を狙うすべてのモードを比較し、複数を狙うモードはプレイヤーに任せます。ウィンドウ内では、攻撃はそのまま行います。
- `offHand`: オフハンド(利き手でない手)用の武器です。combatブロックは、2回目の攻撃が消費する行動枠と、そのダメージが正の能力値を保つかを指定します。

  ```json
  "offHand": { "budget": "quick", "ability": "full" }
  ```

  その持ち主がこのターンに`offHand`の武器の1つで攻撃すると、身に着けているほかのそうした武器はそれぞれ、その行動枠で2回目の攻撃を提示し、メニューでは「Silver coffin nail, off hand」と表示されます。`ability`は`full`(デフォルト)か`penalty-only`です。後者は5eの二刀流と同じく、何かを差し引く場合だけダメージの能力値を加えます。オフハンド攻撃は、主攻撃が得る打撃の数にかかわらず1撃で、離れていく相手への打撃には使えません。`offHand`の武器には、combatブロックの`offHand`が必要です。
- `floor`: 命中が与える最小値で、直接書くかアイテムの数値ステータスから読みます。プール方式の戦闘の吸収後の被害、または合計方式の戦闘のダメージを、抵抗で半減する前にこの値まで引き上げ、ログにもそう示します。費やす打撃は使い手の数値を振るため、引き上げません。
- `onHit`: 打撃が与えた被害が`atLeast`に達したとき、標的が受ける状態で、最大4つです。持続は標的自身のターンで`rounds`回、指定がなければ何かが解除するまでです。被害は吸収と抵抗の後に届いた量です。奪う打撃は被害ではなくイニシアチブを奪うため、状態を付与しません。

武器の詳細とGMへの行には、そのすべてが示されます。`modes Volley (2 shots, -2 to hit, up to 2 targets)`、`off hand (Quick)`、`at least 1 on a hit before resistance`、`Marked for 2 rounds when a hit deals 2 or more`です。

<a id="armor-and-worn-effects-in-a-fight"></a>

### 戦闘中の鎧と装備効果

装備中や携行中のアイテムの効果は、持ち主の状態や段階と並んで、戦闘も変えられます(Capability API 1.56)。どちらも、状態のうち戦闘が読む部分を受け付けます。

- `effects`: 段階が持てない4つ(`half-move-to-stand`、`ends-on-damage`、`cannot-target-source`、`cannot-approach-source`)以外の、状態の任意の効果です。誰かがアイテムを持ち主に付けたわけではなく、ひとりでに終わることもないためです。`own-attacks-advantage`、`attacks-against-disadvantage`、`resist-all`、`speed-zero`などです。
- `modifiers`: 状態とまったく同じく、判定とセーヴに加えて防御、攻撃、速度への変更(`to`)です。`dice-pool`の戦闘では、状態と同じく、攻撃への変更はダイスの固定数です。
- `resist`、`vulnerable`、`immune`: クリーチャーと同じく、持ち主が半分、2倍、ゼロだけ受ける被害の種類です(宣言している場合は`combat.damageTypes`と照合します)。`conditionImmunities`: 持ち主に決して付与されない独自の状態です。

GravewatchのWidow's ringは呪われていて、すべての攻撃でダイスを1個失わせます。バインドしたDawn bellは持ち主をRattledから守り、Ember RoadsのWaystoneは持っているだけで熱を防ぎます。

```json
"worn": { "modifiers": [{ "to": "attacks", "flat": -1 }] }
```

```json
"worn": { "modifiers": [{ "to": "checks", "skills": ["ward"], "flat": 1 }], "conditionImmunities": ["rattled"] }
```

```json
"carried": { "modifiers": [{ "to": "checks", "skills": ["sway"], "flat": 1 }], "resist": ["burn"] }
```

戦闘は判定と同じく各アイテムを1回だけ読み、スタックの名前で示します(ログのロールの横や防御に「Widow's ring」)。満たされない要件の`otherwise`も戦闘で数えるため、装備者に重すぎる鎧は速度を下げることがあります。アイテムの詳細とGMへの行には、そのすべてが示されます(「While worn: -1 on attacks」、「worn: +1 on checks (Ward), immune to Rattled」)。防御や吸収に単純に加算する鎧は、`itemStat`で読むアイテムのステータスです(「シート上のアイテム」を参照)。Ember RoadsのGuardが身に着けたコートを読むのと同じです。

**硬度。** イニシアチブを攻撃で動かす数値として扱う場合、`combat.pool.hardness`は戦闘員の硬度で、戦闘開始時にシートから(鎧の値は`itemStat`を通じて)読みます。クリーチャーは独自の`hardness`を指定します。ダイスがそれ未満の費やす打撃は、当たっても何も起こしません。使い手の数値は基準値に戻り、ログにもそう示され(「Ada's Grave spade lands on the warden with 5 dice, below a hardness of 6, and does nothing.」)、メニューもその打撃に被害を見込みません。指定できるのは費やすスタイルを持つルールセットだけで、シートとして記述したクリーチャーはシートから取ります。

<a id="using-items-in-a-fight"></a>

### 戦闘中のアイテム使用

アイテムは戦闘中に使用できます(Capability API 1.59)。傷に当てる湿布、飲む強壮剤、鳴らす鐘などです。`use`は、カタログ項目の`mechanics`と同じ語彙で使用の効果を示します([戦闘が`mechanics`から読み取るもの](#what-a-fight-reads-from-mechanics)を参照)。`kind`(`heal`、`attack`、`buff`、`debuff`)、`amount`、`damageType`、`plus`、`attackRoll`、`save`、`applies`、`temporary`、`range`、`area`、`targets`、`targetCount`、`friendlyFire`と、消費する`budget`または`free`です。Ember RoadsのPoulticeと、GravewatchのWarming tonicとDawn bellは次のとおりです。

```json
"use": { "kind": "heal", "budget": "act", "range": 0, "targets": "ally", "amount": { "dice": "1d4", "flat": 1 }, "consumes": true }
```

```json
"use": { "kind": "heal", "budget": "quick", "targets": "self", "amount": { "flat": 1 }, "consumes": true }
```

```json
"stack": 1,
"use": {
  "kind": "debuff",
  "budget": "act",
  "targets": "enemy",
  "save": { "save": "steel", "onSuccess": "negates" },
  "saveDifficulty": 7,
  "applies": [{ "condition": "rattled", "duration": { "rounds": 2 } }],
  "charges": 1
},
"charges": { "max": 3 }
```

- 使用は戦闘メニューの**Items**(アイテム)の下にあり、スタックの名前にかかわらずアイテム名(「Poultice」)で表示します。スロットを占めるかバインドが必要なアイテムは、鐘のように身に着けている間(バインドが必要ならバインド中)に使い、それ以外は携行中に使います。
- 行動枠を消費するか`free`で、アイテム自身で支払います。`cost`、`perCostStep`、`check`、`concentration`、`reaction`、`scales`、`gives`、`standard`、`rider`はシートが持つカタログ項目用で、使用では拒否されます。
- `toHit`は、`attackRoll`を持つ使用で命中に加える値で、武器の`toHit`と同じように指定します(「戦闘中の武器」を参照)。能力値、スキル、ボーナス、プール方式の戦闘ではダイスごとの目標値です。指定しなければ、ロールに何も加えません。
- `saveDifficulty`: 使用が求めるセーヴ(自身のもの、付与する状態を終わらせるもの、`difficulty`のない節のもの)の対象値で、直接書くかアイテムの数値ステータスから読みます。シート上の項目はその数値をカタログの出所から読みますが、アイテムにはそれがないため自身で指定します。
- `consumes: true`は使用するたびにアイテムのスタックから1つ減らし、メニューに残数を表示します。最後の1つを使うとスタックもなくなります。
- `restore`(Capability API 1.60)は、効果が及んだ各シートのプールの一部を回復します。血液パックが血を戻すように、`{ "pool": "resolve", "amount": { "flat": 1 } }`と書き、`dice`と`flat`は`amount`と同じです。指定するのはライブプールの1つで、体力のプールは指定できません(体力は回復で戻ります)。`heal`や`buff`など、助ける使用に付けます。クリーチャーはプールを持たないため、何も受けません。ログにも示され(「Ada gets back 1 Resolve, and is on 3 of 4.」)、Engineが操作するパーティーメンバーは満タンのプールには使いません。GravewatchのWarming tonicは、回復と並んでResolveを1回復します。
- `charges`は、アイテム自身の`charges`をその数だけ消費します。`max`は保持できる数で、1から100です。直接書くかアイテムの数値ステータスから読みます(そのステータスが1未満のアイテムは拒否され、100を超えるものは100を保持します)。数はアイテムのインベントリーのスタックに保持するため、ある戦闘で2回鳴らした鐘は次の戦闘ではチャージが1つ残り、誰も鳴らしていない鐘は満タンです。チャージは1つのアイテムのものなので、チャージを持つアイテムの`stack`は1です。使用は使い切るかチャージを消費するかのどちらかで、両方はしません。アイテムのチャージは常にその使用で消費します。GravewatchのDawn bellのように、`charges`には2つのキーを追加できます(Capability API 1.61)。

  ```json
  "charges": { "max": 3, "recharge": { "rests": ["vigil"], "amount": "max" }, "breaksOn": { "die": 20, "atMost": 1 } }
  ```

  - `recharge`: チャージを戻す`rests`とその量です。`"max"`はアイテムを満タンにし、量(`{ "dice": "1d6", "flat": 1 }`)はその数だけ戻しますが、`max`を超えません。休息は、シートのRestボタンでもGMの`[sheet: op="rest"]`でも、そのキャラクターが持つ、その休息を指定するすべてのアイテムのチャージを戻します。シートと袋は一緒に書き込み、再生成した返信が再充填するのは1回だけです。休息後、シートには戻ったものが表示され(「Dawn bell 3/3 charges」)、GMはインベントリーで各アイテムの横に残りのチャージを見ます(「2 of 3 charges left」)。
  - `breaksOn`: 使用が最後のチャージを消費すると、Engineはd`die`を振り、`atMost`以下ならアイテムが壊れて袋からなくなります。戦闘中でも戦闘外でも同じです。戦闘ログにも(「Dawn bell breaks (a 1 on its die).」)、Useボタンの報告にも(「Its last charge spent, it breaks.」)示され、Journalは失ったものとして数えます。
- `gate`(Capability API 1.62)は、アイテムが働く前に使用者が通る判定です。読み手より高位の呪文の巻物が判定を求めるようなものです。`check`は振るものを指定します。`{ "skill": "ward" }`、`{ "ability": "wits" }`、またはシート上の値(`{ "value": { "derived": "spell_mod" } }`。5eの術者の呪文発動修正値のように、キャラクターごとに異なる数値用)です。`difficulty`は1から100で、直接書くかアイテムの数値ステータスから読みます(それを与えないアイテムはメニューから除外し、Useボタンもそれをはっきり示します)。`unless`は、使用者のシート上の値が`atLeast`以上なら判定を省きます。判定に失敗すると、アイテムを無駄に使い切ります(またはチャージを消費します)。戦闘中は、アイテムを消費する時点で、戦闘自身のダイス(プール方式の戦闘ではプールで、`difficulty`は必要な成功数)と、戦闘開始時に読んだシートの数値で判定を振り、使用者の状態と身に着けたアイテムがその判定に加えるものも、スキル自身のものを含めて数えます。ログにも示されます(「Ada rolls Ward to use Page of the vigil litany: 2 successes from 2 dice at 7 or more (8, 9), needing 2 successes, a success.」)。GravewatchのPage of the vigil litanyは次のように指定します。

  ```json
  "gate": { "check": { "skill": "ward" }, "difficulty": 2, "unless": { "value": { "abilityScore": "nerve" }, "atLeast": 3 } }
  ```

戦闘で使い切ったものと残ったチャージは、武器の射撃と同じく各段階でインベントリーに書き込み、Journalが使ったものを記録します。戦闘ログは各使用を示します(「Poultice: 1 of 2 left.」、「Dawn bell: 2 of 3 left.」)。Engineが操作するパーティーメンバーは負傷した相手にだけ回復を使い、離れていく相手への打撃にアイテムを使う者はいません。アイテムの詳細とGMへの行は使用の効果を示し(「Use (Action): heals 1d4 + 1, range 0 paces, used up」と`use (Act): Steel 7 save negates it, Rattled, 1 of 3 charges`)、詳細には残りのチャージも表示します。GMがルールセットのアイテムを`like=`にして作ったアイテムは、チャージも含めてそのアイテムと同じように使います。

### ClassicとTacticalの戦闘でのアイテム

独自に戦闘を解決しないルールセットは、Game Mode自身のClassicとTacticalの戦闘に任せます。そこでは戦闘開始時に、インベントリーのアイテムが何をするかをモデルに尋ねます。ルールセットのアイテムは推測しません。`use`を持つ各アイテムはEngine自身の数値で記述どおりに働き、GMの推測を求めるのはルールセットのものでないアイテムだけです(`native: false`なら何も求めません)。

- `heal`は回復し、`attack`は被害を与えます。量は`amount`の平均から求める、標的の最大体力に対する割合です。平均7(基本的な武器の`1d8+3`)は5分の1を少し超える程度で、20分の1を下回らず、最大で全部です。これは戦闘への橋渡しがカタログ項目の数値を読む尺度です。`damageType`は属性になります。
- `applies`の最初の状態を、その名前の状態異常として`rounds`の間(なければ2)付与します。`buff`や`debuff`はその状態異常だけで、Engine自身の状態異常と同じく防御を上げ下げします。
- `targets`は使う相手を示します。指定しなければ、回復と強化は味方へ、攻撃と弱体化は敵へ向かいます。
- `consumes: true`はスタックから1つ減らし、それがない使用ではアイテムはそのまま残ります。
- 命中判定、セーヴ、範囲、一時ポイント、プールの回復は、カタログ項目の`mechanics`と同じく、これらの戦闘には受け皿がありません。メニューのアイテムの説明には引き続き表示されます。
- スロットを占めるアイテムは身に着けている間だけ、バインドが必要なアイテムはバインド中だけ使えるのは、ルールセットの戦闘と同じです。使い切るものは身に着けているものから取り、袋の予備からは取りません。
- 使用が`charges`を消費するアイテムは、使用回数が残っている間提示され、Itemsメニューにその回数が表示されます。各使用はアイテムのスタック(プレイヤー自身のものから先)から消費し、最後に消費したときに`breaksOn`を振ります。壊れると袋からなくなり、Journalは失ったものとして数えます。
- 先に判定を求めるアイテム(`gate`)は、パーティーメンバーが使うとき、Useボタンと同じく、そのメンバーのシートと身に着けたものでサーバー上で判定を振り(自分のカードを持たない仲間は空白のシートで振り、プレイヤーのカードにフォールバックするのはプレイヤー自身のユニットだけです)、`unless`が成り立てば省きます。失敗すると、アイテム(またはチャージ)を消費して何も起こらず、ログにもそう示されます(「Ada rolls Ward to use Page of the vigil litany: 0 against 2, failed, and it is used up for nothing.」)。
- `use`のないアイテムはこれらの戦闘で提示されず、`amount`のない回復も同様です。

Engineが各アイテムの効果を自ら計算するため、画面が送る内容がルールセットのアイテムの効果を決めることはありません。

### 戦利品

勝利した戦闘は、すべてのGame Modeのゲームで1回だけ、パーティーの袋に戦利品を落とします。ルールセットがなければGame Mode自身の表から出て(難しいゲームほど多く、レアになります)、戦利品表を宣言せず`native`をオンのままにしたルールセットでも同様です。戦利品表を宣言したルールセットは代わりに独自のアイテムを落とし、`native: false`で表のないルールセットは何も落としません。

`items`ブロックの`lootTables`(Capability API 1.63)が表を列挙します。GravewatchのGrave goodsは次のとおりです。

```json
"lootTables": [
  {
    "id": "grave_goods",
    "label": "Grave goods",
    "rolls": "1d2",
    "entries": [
      { "item": "kit/shot-and-powder", "weight": 4, "count": "1d4" },
      { "item": "kit/warming-tonic", "weight": 3 },
      { "item": "kit/litany-page", "weight": 2 },
      { "filter": { "category": "arm" }, "weight": 1 },
      { "coins": "shilling", "weight": 2, "count": "1d6" }
    ]
  }
]
```

- `rolls`は表が選ぶ回数です。0から20の数値かダイス(`"1d2"`)で、デフォルトは1です。
- 各選択では、ほかの行に対する`weight`(デフォルトは1)で1行を引きます。行は、`<catalog>/<entry>`としてアイテムの1つを指定するか、`rarity`、`category`、`tag`による`filter`(一致するすべてのアイテムから均等に選びます)か、(Capability API 1.64)IDで硬貨の1つを指定する`coins`です。`count`は落とす数で、数値かダイス、デフォルトは1です。レイヤーが除いたアイテムや硬貨は何も落とさず、何も見つからないフィルターも同様です。
- ベスティアリのクリーチャーは、`loot`で持っている表を指定します(後述の「クリーチャー」を参照)。勝利したルールセットの戦闘は、倒した各クリーチャーの表を振ります。Engineがルールセットの規則で解決しない戦闘にはベスティアリのクリーチャーがいないため、何も落としません。
- 落としたものは追加と同じく共有ビューに入り、まずプレイヤーの袋を確認し、誰も運べないものは置いていきます。GMが受け取る要約は、何が落ちたか、それがすでに袋に入っていることを伝え、Journalにも記録され、通知も表示されます。
- GMは物語の中で`[loot: table="grave_goods" who="Ada"]`で表を振ります(`who=`は1人のキャラクターの袋に入れる場合)。インベントリーのタグと同じくターン開始時点から計るため、再生成した返信が落とすのは1回だけです。落とした各アイテムは追加として応答し、GMへの指示に表が列挙されます。

### お金

`currencies`はパーティーのお金です。硬貨は袋の中のアイテムで、ほかと同じく硬貨ごとのスタックになり、`label`で呼びます。

- 系統の硬貨`perWeight`枚ごとに運搬ステータス1単位の重さがあり、持ち主の荷重に数え、入手時には運搬の規則で渡す人を決めます。`perWeight`のない系統は重さがありません。
- プレイヤーは選択画面の**Coins**(硬貨)リストから硬貨を追加し、ほかのスタックと同じく分割、譲渡、統合できます。
- インベントリーのスタックの上の行に、表示中の各系統の硬貨と、系統の最小硬貨での価値を表示します。GMは各袋の横にその価値を(`Coin worth 432 pennies`、空の財布なら`no coins`。プレイヤーの袋は何もなくても表示します)、アイテムの横に`cost`を(`costs 3 shillings`)見ます。
- GMは`[inventory: action="pay" amount="3 shillings" who="Ada"]`で支払い、`action="earn"`で受け取ります。`amount`は数と硬貨で、硬貨はIDかラベル、単数形でも複数形でも、大文字・小文字も問いません(`1 penny`、`12 pennies`)。支払いは1つの袋(`who=`がなければプレイヤーの袋)から、その硬貨の系統の中だけで行います。収まる最大の硬貨から使い、次に残りの不足額をまかなえる最小の硬貨を崩し、お釣りは系統の小さい硬貨で、大きいものから戻します。回答は支払ったものと戻ったものを示します。1 crownが入った財布から3 shillingsを払うと`Paid with crowns ×1; shillings ×2 back.`です。袋で払えない支払いは拒否され(`cannot-afford`)、ない硬貨(`unknown-coin`)や通貨のないルールセットでの支払い(`no-currencies`)も拒否されます。受け取りはその硬貨の追加で、`who`の袋に入るか、運搬の規則で分けます。Journalは使ったものと得たものを記録し、通知も表示されます。GMへの指示には硬貨が列挙され、硬貨のあるルールセットだけにあります。
- 購入は支払いの後の追加か、市場のあるルールセットでは`buy`(後述)です。店の画面はありません。

### 市場

`items`ブロックの`market`(Capability API 1.65)は、すべての店がすべてを定価で売る代わりに、場所が何をいくらで売るかを示します。Gravewatchのものを少し短くすると次のとおりです。

```json
"market": {
  "prices": [
    { "id": "cheap", "label": "cheap", "times": 0.75 },
    { "id": "fair", "label": "fair", "times": 1, "default": true },
    { "id": "dear", "label": "dear", "times": 1.5 }
  ],
  "places": [
    { "id": "hamlet", "label": "hamlet" },
    { "id": "village", "label": "village" },
    { "id": "town", "label": "market town" },
    { "id": "city", "label": "city" }
  ],
  "sold": [
    { "filter": { "rarity": "rare" }, "place": "town" },
    { "filter": { "category": "arm" }, "place": "village" }
  ],
  "sellers": [
    { "id": "chandler", "label": "chandler", "sells": [{ "category": "coat" }, { "category": "tonic" }] },
    { "id": "smith", "label": "smith", "sells": [{ "category": "arm" }], "place": "village" },
    {
      "id": "chapel",
      "label": "chapel of the Vigil",
      "sells": [{ "category": "page" }],
      "place": "town",
      "only": { "value": { "abilityScore": "nerve" }, "atLeast": 3, "label": "wardens of Nerve 3 or more" }
    }
  ]
}
```

- `prices`: 1～8の価格水準で、それぞれアイテムの`cost`への倍率(`times`、0より大きい値)で、1つが`default`です。価格は、系統の最小硬貨でのコストに水準を掛けて最小硬貨単位で丸めたもので(コストのあるものは1枚未満になりません)、コストを書いた硬貨でちょうど払えればその硬貨で、そうでなければレイヤーが残す硬貨のうちちょうど払える最大のもので示します。`dear`では8 shillingsのコートは12 shillingsで、50 gpの5eのポーションは50 gold piecesであり、5 platinumにはなりません。値切りや売り手の機嫌は水準を動かし、数値は動かしません。
- `places`: 1～12の場所の規模で、小さい順に独自の言葉で書きます。
- `sold`: フィルターが選ぶものを売る最小の場所の規則です。フィルターは`rarity`、`category`、`tag`のいずれかを指定し、指定したすべてを持つアイテムに一致します。アイテムに一致する最初の規則が決めます。アイテム自身の`sold`が規則より優先し、何も指定しないアイテムはどこでも売られます。
- `sellers`: 売り手の種類です。それぞれ`sells`(フィルターで、いずれかがアイテムを選びます)、売り手がいる最小の`place`(なければどこでも)、任意で売る相手を限る`only`を持ちます。売る相手の条件は、買い手のシート上の値(ライブ状態と持ち物を含む)が`atLeast`以上であることで、GMには`label`として伝えます。`sellers`がなければ、その場所の誰でも、その場所で売るものを売ります。
- `cost`のないアイテムは売り物ではなく、レイヤーが隠すアイテムや、レイヤーが硬貨を除いたアイテムも同様です。

**パーティーの居場所。** GMは`[place: name="Millbrook" size="market town"]`で場面の場所とその規模を示します。規模はIDかラベルで指定し、市場のない場所(道中、荒野)では規模を省きます。Engineは各タグにその場で応答し、ない規模は拒否します。最新の会話開始以降、プレイヤーが見るEngine自身の返信の中で最後に応答した場所が、別の場所が示されるまで有効な場所です。プレイヤーが入力した場所タグは数えません。再生成した返信は、置き換える告知より前にあったものだけを読みます。

**購入。** GMは`[inventory: action="buy" item="Hand axe" count="1" level="dear" seller="smith" who="Ada"]`で購入します。`level`(なければデフォルト)と`seller`(なければ、ここでそのアイテムを売る任意の売り手)は任意です。Engineは返信の終了時に有効な場所で価格を付け、支払いと同じくお釣りを含めて買い手の財布(`who=`がなければプレイヤーの財布)から代金を取り、アイテムを袋に入れます。サービスなら支払うだけです。両方が起きるか、どちらも起きないかです。回答は価格(`price="12 shillings"`)と、支払ったものと戻ったものを示し、通知も表示されます。購入は次の場合に拒否され、何も変わりません。場所が示されていない(`no-place`)、ない水準、アイテム、売り手(`unknown-level`、`unknown-item`)、価格がない(`not-for-sale`)、アイテムには場所が小さすぎる(`not-here`)、ここにそれを売る売り手がいない(`no-seller`)、買い手が売り手の`only`を満たさない(`not-to-you`)、財布で払えない(`cannot-afford`)、袋で運べない場合です。

**GMが見るもの。** 市場のある場所での場面の間、MARKETブロックが場所とその規模、価格水準、そこにいる各売り手と、デフォルトの水準で安い順に並べた売り物12個を示します。売り物はどれでも名前で購入できます。GMへの指示は`[place:]`と`buy`を教え、市場のあるルールセットだけにあります。

#### 市場の一日

市場の一日(Capability API 1.69)は、場所の品揃えを変化させて売り切れさせ、パーティーが売り戻せるようにします。Gravewatchのものを少し短くすると次のとおりです。

```json
"places": [
  { "id": "hamlet", "label": "hamlet", "purse": { "amount": 10, "unit": "shilling" } },
  { "id": "town", "label": "market town", "purse": { "amount": 100, "unit": "shilling" } }
],
"buyBack": 0.5,
"sold": [{ "filter": { "rarity": "rare" }, "place": "town", "limited": "1d2" }],
"sellers": [
  { "id": "smith", "label": "smith", "sells": [{ "category": "arm" }], "stock": { "table": "smiths_odd_lot" } }
]
```

- **一日。** ある場所での一日は、GMが別の場所を示すまで続きます。同じ場所で新しい日を始めるには、`day="new"`を付けてもう一度示します(`[place: name="Millbrook" size="market town" day="new"]`)。以下はすべて、プレイヤーが見るGMの返信から日ごとに計算するため、スワイプ、再生成した返信、分岐に保存するものは不要で、同じ日は常に同じ品揃えになります。
- **`limited`**は`sold`の規則かアイテム自身の`sold`に付け、ある場所がその日に置いておく数で、数値か、その日のために振るダイスです。規則は場所なしで上限を指定できます(どこでも売られ、一度に少数)。アイテムの場所は場所を指定する最初の規則から、上限は上限を指定する最初の規則から取ります。売り切れると、新しい日まで購入は拒否されます(`sold-out`)。
- **`stock`**は売り手に付け、戦利品表の1つです。1日に1回振り、その売り手が売り物に加えて在庫として持つものを決めます。振って出たもの(アイテムだけで、硬貨は出ません)は、`sells`や`sold`の指定にかかわらず、その売り手だけが出た数だけ売ります。売り手の`only`は引き続き適用されます。
- **`buyBack`**: 売り手がアイテムに支払う、デフォルト価格に対する割合(0より大きく1以下)です。その種類のものを売るここの売り手が買い取ります(売り手がいなければ誰でも)。`buyBack`がなければ、誰も買い取りません。
- **`purse`**は場所の規模に付け、その売り手たちが1日に合計で支払える最大額で、硬貨の1つで指定します。その硬貨の系統で支払う売却がそれに数えられ、財布がなければ無制限に買い取ります。
- **売却。** GMは`[inventory: action="sell" item="Silver coffin nail" count="1" seller="smith" who="Ada"]`で売ります。Engineは価格を付け、売るキャラクターの袋(`who=`がなければプレイヤーの袋。バインドした呪われたアイテムは不可)からアイテムを取り出し、硬貨を大きいものから入れるか、拒否して何も変えません。拒否するのは、場所が示されていない、ここで誰も買い取らない(`not-bought`)、価格がない(`not-for-sale`)、今日の財布を使い切った(`purse-spent`)、持っていない、袋が硬貨を運べない場合です。回答は売値(`price="4 shillings"`)を示し、Journalは売却として記録し、通知も表示されます。
- MARKETブロックには、各売り手の今日の在庫、上限のあるアイテムの残数、ここの売り手が支払う額と今日の財布の残りが加わります。GMへの指示は`sell`と`day="new"`を教えます。

<a id="using-items-outside-a-fight"></a>

### 戦闘外のアイテム使用

同じ`use`は戦闘外でも使えます(`restore`はCapability API 1.60で、それ以外に新しい指定は不要です)。`use`を持つルールセットのアイテムに付くインベントリーの**Use**ボタンと、GMの`[inventory: action="use" item="Poultice" who="Juno"]`は、どちらもEngineのダイスで、アイテムを持つ人にその効果を適用します。

- 回復は体力を戻します。戦闘中の回復と同じく、体力のプールには量を戻し、負傷トラックでは印を1つ消します。`temporary`のポイントは体力のプールに付き、`restore`はそのプールを回復し、`applies`の各状態は何かが解除するまで付与します。
- 被害を与える使用や、相手側を狙う使用(`kind`が`attack`か`debuff`、または`targets`が`enemy`)は誰にも当たりません。戦闘外には盤面上に当てる相手がいないためです。アイテムは使用され、GMには語りのためにその効果が伝えられます。
- 戦闘とまったく同じく、スタックから1つ減らすかチャージを消費します。残りがないもの、スロットを占めるかバインドが必要で身に着けていないものは拒否され、何も変わりません。シートと袋は一緒に書き込みます。
- `gate`は判定と同じく最初に振ります。ルールセット自身のダイスとシートの数値に、使用者の負傷ペナルティと、状態や装備中・携行中のアイテムがその判定に与えるものを加えます。失敗すると無駄にアイテムを使い切り、結果の行にもそう示されます(「Ada uses Page of the vigil litany: Ward check 1 against 2, failed; it is used up for nothing. 1 left.」)。

起きたことは「Juno uses Poultice: heals 4 (Grit 6/11). 1 left.」のように1行で示されます。Useボタンはこれを「I use my Poultice.」の後の`[item_used]`ブロックでGMに送り、チャットではバッジとして表示されます。GM自身のタグにはこの行で応答し、ほかのタグと同じくターン開始時点から計るため、再生成した返信がアイテムを2回使うことはありません。`use`のないアイテムや、ルールセットのないゲームでは、従来どおり単に「I use my rope.」と書かれます。

<a id="battles-lending-the-sheet-to-marinaras-combat"></a>

## 戦闘への橋渡し: シートをMarinaraの戦闘に貸す

既定では戦闘はシートを知りません。従来どおりに戦闘者を組み立て、戦闘後もシートのHPが変わらないことがあります。

任意の`battle`ブロックは、シートの数値を戦闘へ貸し、結果を書き戻すという一方向でこれを変えます。**戦闘を独自の規則に従わせるものではありません。** ダイス計算も、誰が誰に何点当てるかもMarinaraの規則です。そのため体力は元の数値ではなく最大値への割合で渡します。シートで半分ならMarinaraが作るHPバーも半分で始めます。HP9のプールを、1撃12ダメージの戦闘へそのまま持ち込みません。

```json
"battle": {
  "health": { "pool": "grit" },
  "energy": { "pool": "luck" },
  "skills": [{ "list": "knacks" }]
}
```

- `health`: 必須です。戦闘中のHPとなるライブプールで、`sheet.live.pools`の1つが必要です。行がプールになったリストは使えません。
- `energy`: 任意です。戦闘が消費し、MPバーになるライブプールです。HPを燃料にできないため、`health`とは別のプールが必要です。
- `slots`: 任意です。1回に1つ消費するライブプールで、それぞれ1～9の`level`を持ちます。`[{ "pool": "slots_1", "level": 1 }]`のように指定し、レベルとプールはそれぞれ重複不可です。
- `skills`: 任意で最大8個です。行が戦闘スキルになるシートのリストです。カタログ由来で、元項目に`mechanics`がある行だけが対象です。手入力の行は数値上の効果を示しません。`onlyWhen`は準備済み呪文など、行で有効であるべき真偽値列です。`alwaysWhen`は未準備でも唱えられる呪文など、例外的に通す列と値です。`onlyWhen`の例外なので、併記なしでは拒否されます。

### 持ち込むものと持ち帰るもの

**開始時**、ゲームがシートを持つ各仲間について、体力プールの最大値に対する割合でMarinaraのHPバーの開始位置を決め、エネルギーをMP、各スロットプールをそのレベルのスロット、印付きの行をスキルにします。最大HP、攻撃、防御、速度、レベルはMarinaraの数値のままです。体力プールが0なら倒れた状態で始め、0より大きければHP1未満にはしないため、小さい割合の丸めで倒れることはありません。

**終了時**、最終HPバーの割合を体力プールの尺度へ戻し、開始時との差をダメージか回復として適用します。エネルギーとスロットは割合でなく個数なのでそのまま戻します。シートのボタンと同じ規則を通し、拒否された変更は強制せず省略して報告します。HPが変わらなかった戦闘では体力の変更を書かないため、往復の変換だけでシート値が変わることはありません。

**どちらにも含まれないもの**は、攻撃ロール、セーヴィングスロー、精神集中、高いコストによる追加効果です。将来の本格的な戦闘システムが読むために`mechanics`へありますが、この橋渡しは適用せず、対応すると称してはいけません。

放棄した戦闘は何も書き戻しません。開始元のメッセージを削除したり、戦闘が終了しなかったりした場合、シートは元のままです。その戦闘は起きなかったことになります。

### 項目がスキルになる仕組み

カタログ項目の`mechanics`ブロックは、次のように読み取られます。

- `kind`がスキルの種類になります。`utility`項目と`reaction`の指定があるものは、Marinaraの戦闘に受け皿がないため除外されます。
- `amount`は威力を決めますが、ダメージの数値ではなく戦闘者自身の攻撃力に対する倍率として使います。より大きいダイスがより弱く当たることはなく、倍率も自動生成スキルがすでに使う範囲に収まります。
- `range`と`area.size`をカタログの`units.distance.perCell`で割り、グリッドのマス数にします。切り捨てでゼロになることはありません。バーストは半径、コーンはその半分、ラインは1マスになります。範囲のあるものは覆う敵全員を対象とし、`friendlyFire`も反映されます。
- `damageType`はスキルの属性になります。`targets`は引き継ぎません。回復、強化、攻撃を誰に向けられるかは、Marinaraの戦闘がスキルの種類から判断します。
- エネルギープールの`cost`はMPコストになり、複数のエネルギーコストは合算します。スロットちょうど1つの`cost`は、そのレベルのスロットを1つ消費します。Marinaraの戦闘が請求するのは1種類のエネルギー量かスロット1つだけで、両方には対応しません。そのため、スロット2つ、2つのレベルのスロット、スロットとエネルギーの両方を消費する項目は戦闘から除外されます。体力やクラスの資源など、ほかのプールのコストも同様です。そうしないと、Engineが無料で提供してしまうためです。
- `buff`と`debuff`はMarinara自身の強化と弱体化になります。項目の文章にシートの状態の解除など、ほかの効果が書かれていても戦闘では適用されません。戦闘外でしか意味を持たない効果の項目には、`mechanics`を付けないでください。

`coverage.combat`は別の指定で、意味も変わりません。戦闘が実際にそのシステムのルールに従う場合だけ設定してください。

<a id="combat-a-fight-your-own-rules-resolve"></a>

## Combat: 独自のルールで解決する戦闘

前述の`battle`ブロックは、計算をMarinaraに任せたままシートの数値を戦闘に貸し出します。任意の`combat`ブロックは別のもので、独自のルールが戦闘をどう解決するかを定めます。`resolution`が判定の種類にパラメーターを渡すのと同じように、Engineが持つ戦闘の種類をパラメーター化し、その中の名称はすべて作者が決めます。種類は2つです。ダイスを合計して数値と比較する`attack-vs-defense`と、戦闘で`dice-pool`ルールセット自身のプールを振って成功を数える`dice-pool`です(後述の「プールで振る戦闘」を参照)。

**`combat`を宣言するルールセットのゲームは、そのブロックに従って戦います。** パーティーの数値は各自のシートから読み取り、敵は独自のベスティアリか脅威尺度から取り、各ターンを独自のダイスで解決します。キャラクターが消費したものや失ったものは、その都度シートに書き戻すため、戦闘の途中でタブを閉じても何も失われません。戦闘画面も独自の言葉で進行します。攻撃と能力がメニューになり、独自の行動枠と状態を使い、ログには実際の計算が残ります。未対応の内容は「未対応」にまとめています。

```json
"combat": {
  "kind": "attack-vs-defense",
  "health": { "pool": "grit" },
  "defense": { "derived": "guard" },
  "initiative": { "dice": { "count": 2, "sides": 6 }, "modifier": { "abilityMod": "wits" } },
  "attackRoll": { "dice": { "count": 2, "sides": 6 } },
  "economy": { "budgets": [{ "id": "act", "label": "Action", "per": "turn", "count": 1 }] },
  "attacks": [
    {
      "list": "gear",
      "budget": "act",
      "name": "name",
      "toHit": { "ability": { "column": "swing" } },
      "damage": { "dice": { "column": "damage" }, "ability": { "column": "swing" }, "type": { "column": "harm" } }
    }
  ],
  "abilities": [{ "list": "knacks", "budget": "act" }],
  "standard": ["dodge", "help"],
  "conditions": [
    { "condition": "shaken", "effects": ["own-attacks-disadvantage", "ends-on-damage"] },
    { "condition": "pinned", "effects": ["cannot-act", "speed-zero"] }
  ]
}
```

これがEmber Roadsのブロック全体であり、Ember Roadsのゲームはこのルールで戦います。5eの草案では、同じキーをd20システムに使います。

```json
"combat": {
  "kind": "attack-vs-defense",
  "health": { "pool": "hp" },
  "defense": { "field": "ac" },
  "initiative": { "dice": { "count": 1, "sides": 20 }, "modifier": { "derived": "initiative" } },
  "attackRoll": {
    "dice": { "count": 1, "sides": 20 },
    "advantage": true,
    "naturals": { "max": "critical", "min": "miss" },
    "critical": "double-dice"
  },
  "economy": {
    "budgets": [
      { "id": "action", "label": "Action", "per": "turn", "count": 1 },
      { "id": "bonus", "label": "Bonus action", "per": "turn", "count": 1 },
      { "id": "reaction", "label": "Reaction", "per": "turn", "count": 1 }
    ],
    "movement": { "field": "speed" }
  },
  "abilities": [
    {
      "list": "spells",
      "onlyWhen": "prepared",
      "alwaysWhen": { "column": "level", "equals": 0 },
      "budget": "action",
      "toHit": { "derived": "spell_attack" },
      "saveDifficulty": { "derived": "spell_save_dc" }
    }
  ],
  "concentration": { "text": "concentration", "save": "con_save", "floor": 10, "fromDamage": 0.5 }
}
```

### 各キー

- `kind`: `"attack-vs-defense"`(片方が相手の防御に対してダイスを振り、命中すればダメージを与えます)か`"dice-pool"`(「プールで振る戦闘」を参照)です。以下のキーはどちらでも同じ意味で、その方式の数値の読み方で読みます。
- `health`: 必須です。戦闘で減るものです。`{ "pool": "grit" }`なら減算するライブプールで、一時的なバッファがある場合はダメージで先にそれを消費します。`{ "track": "harm" }`なら印を付ける負傷トラックです。トラックには`damageKinds`の併記が必要で、一時ポイントは与えません。
- `defense`: 必須の値参照です。プレイヤーが入力するフィールドか、作者が計算する派生値です。
- `initiative`: 必須です。開始時に一度振るダイスと、任意の修正値参照です。同値なら修正値が高い方が先で、それも同じなら戦闘の設定時の順序に従います。`"each": "round"`は、新しいラウンドの開始ごとに、その時点の修正値で全員のイニシアチブを振り直し(そのため負傷トラックを読む修正値なら、負傷後は遅くなります)、ラウンドは新しい順序の先頭から始まります。Capability API 1.47です。`dice-pool`の戦闘では、代わりにプールとして振れます。`pool`(値参照)はダイスの個数で、その成功数に`plus`を加えた値が数値になり、`dice`や`modifier`は併記しません。`pool`が必要な`resource`は、その数値を保持して攻撃で動かせるようにします(後述の「攻撃で動くイニシアチブ」を参照)。Capability API 1.48です。
- `attackRoll`: `attack-vs-defense`では必須で、解決方式自身のプールを振る`dice-pool`では拒否されます。ダイス、2回振って片方を使うか(`advantage`)、単一ダイスの最大・最小の目の効果(`naturals.max`: `critical`、`hit`、`none`、`naturals.min`: `miss`、`none`)、クリティカルヒットがダメージに与える効果(`critical`: `double-dice`はダメージダイスをもう一度振り、`max-dice`はその最大の目を一度加え、`none`は通常の命中)を指定します。判定と同じく、特別な出目には単一のダイスが必要です。戦闘内のセーヴィングスローも同じダイスを振ります。
- `economy`: 必須です。`budgets`は1ターンに使える行動枠で、ID、ラベル、`per`(`turn`は所有者自身のターン開始時に、`round`は新しいラウンドの開始時に補充)、`count`を持ちます。最初に宣言した行動枠が主枠で、標準アクションはこれを消費します。`movement`は任意の値参照で、独自の距離単位による1ターンの歩行距離です。盤面上の戦闘が読み取ります(「位置」を参照)。
- `attacks`: 任意です。行が武器になるシートのリストです。`name`は行の名前にするテキスト列、`damage.dice`はダイス列で、`toHit.ability`、`toHit.proficiency`、`toHit.bonus`、`damage.ability`、`damage.bonus`、`damage.type`はそれぞれ同じリストの列を指定します。`ability`列は独自の能力値IDのいずれかを持つ`enum`です。それ以外の値は何も加算しません。`proficiency`列は`boolean`で、オンなら習熟ボーナスを加算します。読み取れるダイスがない行は攻撃にならないため、同じリストのロープは単なるロープのままです。`toHit.skill`は、スキルIDのいずれかを持つ`enum`列を指定します。行はそのスキルの判定が加える値を加え、行自身の`ability`が能力値を指定する場合は、判定の`with=`による入れ替えとまったく同じく、スキルの能力値の代わりにそれを使います(Capability API 1.47)。`strikes`は任意の値参照で、このリストの行動枠を1回消費すると何回の打撃を得るかを示します。手持ちの打撃がない状態で行を選ぶと行動枠を消費し、残りを手持ちにします。手持ちがある間、`strikes`を宣言したすべての行は行動枠を消費しません。そのため、別の武器、別の標的、合間の歩行が自然にメニューから選べます。`strikesCappedBy`は、その行自身をリストの打撃回数に関係なく1回に制限するブール列を指定します。使い手の回数にかかわらず1ターンに1回しか撃てない武器のためのもので、SRD 5.1のLoading特性を表現するために用意されています。もともと1回の消費で1打撃しか得ないリストでは意味がなく、拒否されます。手持ちの打撃は1つのリストではなく戦闘者に属します。2つの武器リストが両方とも`strikes`を宣言しているキャラクターは、どちらの行を振るっても同じ手持ちを消費します。獲得したターンの終了時に消去されます。何も指定しないリストは、1回の消費で1打撃を得ます。この機能以前のすべての戦闘と同じです。

  ```json
  {
    "list": "attacks",
    "budget": "action",
    "name": "name",
    "strikes": { "field": "attacks_per_action" },
    "damage": { "dice": { "column": "damage" } }
  }
  ```

- `abilities`: 任意です。カタログの印が付いた行が能力になるシートのリストで、`battle.skills`とまったく同じく`onlyWhen`と`alwaysWhen`で絞り込みます。各能力の効果は元の項目の`mechanics`に従います。このブロックでは、デフォルトで消費する`budget`、命中判定をする項目に加える`toHit`、項目のセーヴの目標値となる`saveDifficulty`を指定します。項目自身のセーヴであれ、付与した状態を終了するセーヴであれ、配置先のリストに`saveDifficulty`がない項目は拒否されます。目標値のないセーヴは常に成功してしまうためです。
- `standard`: 任意で、固定リスト`dash`、`disengage`、`dodge`、`help`、`hide`、`ready`から選びます。`dodge`(回避中の者への攻撃は2回振って悪い方を使う)と`help`(援護された味方の次の攻撃は2回振って良い方を使う)は常に解決します。`dash`(同じ移動量をもう一度得る)と`disengage`(このターン、離れる際に攻撃されない)は盤面上では解決し、盤面外では記録します。`hide`と`ready`は受け付けますが、まだ何もしません。
- `standardEffects`: 任意で、標準アクションのフラグだけでは表せない部分です。現在対応するのは`dodge`だけです。`{ "dodge": { "saves": ["dex_save"] } }`は、回避が続く間に2回振って良い方を使うセーヴを指定します。シートに宣言したセーヴだけを指定し、`standard`リストに`dodge`がある場合だけ使ってください。省略すれば回避は従来どおり、命中しにくくなるだけです。
- `conditions`: 任意です。独自の状態IDを効果に対応付けます。シートと戦闘の状態は1つの記録となり、毒を受けたキャラクターは戦闘後も毒のままです。効果は固定リストです。`own-attacks-advantage`、`own-attacks-disadvantage`、`attacks-against-advantage`、`attacks-against-disadvantage`、`attacks-against-adjacent-advantage`、`attacks-against-far-disadvantage`、`attacks-from-adjacent-critical`、`cannot-act`、`cannot-react`、`speed-zero`、`half-move-to-stand`、`ends-on-damage`、`own-saves-advantage`、`own-saves-disadvantage`、`own-checks-advantage`、`own-checks-disadvantage`、`resist-all`、`cannot-target-source`、`cannot-approach-source`です。`failsSaves`は、ダイスを振らずに失敗するセーヴを指定します。距離や移動が必要な6つ(`attacks-against-adjacent-advantage`、`attacks-against-far-disadvantage`、`attacks-from-adjacent-critical`、`speed-zero`、`half-move-to-stand`、`cannot-approach-source`)は盤面のある戦闘だけが読み取り、盤面なしでは意味を持ちません(「位置」を参照)。`cannot-react`の所有者は歩行で開く応答ウィンドウから除外されるため、応答を求められません。効果に加えて、4つのキーがあります。
  - `modifiers`: 状態の間に変更する数値です。後述の「状態が変更する数値」を参照してください。
  - `saves`: 2つのセーヴ効果と、セーヴへの修正値の対象とするセーヴです。省略するとすべてが対象です。どちらも併記せずに指定すると拒否されます。
  - `skills`: 2つの判定効果と、独自のスキルを指定しない判定への修正値の対象とするスキルです。省略するとすべてが対象です。どちらも併記せずに指定すると拒否されます。戦闘の対抗判定はスキルではなく戦闘自身の判定を振るため、スキルに絞り込んだものは対抗判定には届きません。それらのスキルでの戦闘外の判定はこれを読みます(後述の「戦闘外の判定」を参照)。Capability API 1.53です。
  - `whileSourceInSight`: 状態を付与した相手が所有者の視線内にいる間だけ有効になるものです。`true`なら状態全体を制限し、その状態自身の効果のリストなら列挙した効果だけを制限して残りは維持します。相手が見えるかに関係なく近づけなくする恐怖は、これを必要とします。状態が持っていない効果を指定すると拒否されます。盤面がなければ視線を遮れないため、どちらの場合もすべて有効です。
  - `endsWhenSourceDown`: 状態を付与した相手が倒れた瞬間に解除します。

  `own-saves-advantage`とその反対の効果は、攻撃と同じくセーヴを2回振って片方を使い、互いに打ち消し合います。`own-checks-advantage`とその反対の効果は、戦闘が能力値判定を行う場である対抗判定の持ち主側と、戦闘外の判定に同じことをします。`resist-all`は標的自身の耐性などに加えてあらゆる種類の被害を半減し、同じように脆弱性と相殺します。`cannot-target-source`は、状態を付与した相手に何かを向けることを禁じます。`cannot-approach-source`は、移動経路も含め、現在のマスよりその相手に近づくことを禁じます。同じ距離のマスへ迂回する経路は引き続き提示されますが、相手の近くを通って反対側に出る経路は提示されません。

  ```json
  { "condition": "restrained", "effects": ["own-saves-disadvantage"], "saves": ["dex_save"] }
  ```

  **状態が変更する数値。** `modifiers`の各項目は、変更するもの(`to`)と量を指定します。
  - `defense`: 持ち主への攻撃が到達すべき数値です。固定値だけです。
  - `attacks`、`saves`、`checks`: 持ち主自身の攻撃判定、セーヴ、対抗判定です。固定値か、ロールのたびに振る`dice`(`"1d4"`)です。`minus: true`はダイスを加える代わりに差し引きます。
  - `speed`: 持ち主が歩く距離で、独自の距離単位による`flat`か、半分や2倍にする`times` 0.5または2です。倍率はすべての固定値の変更の後に適用します。`speed-zero`と同じく、盤面上でだけ読みます。

  `checks`への修正値は独自の`skills`を、`saves`への修正値は独自の`saves`を指定でき、状態の指定の代わりにそれで絞り込みます。どちらも`mode: "advantage"`か`"disadvantage"`で2回振ることができ、同名の効果と一緒に数えて同じように打ち消し合い、数値の併記は任意です。そのため1つの状態でSneakを難しくし、同時にClimbを易しくできます。この3つのキーにはCapability API 1.53が必要です。

  ```json
  { "condition": "muddy", "modifiers": [{ "to": "checks", "skills": ["sneak"], "mode": "disadvantage" }] }
  ```

  固定値は独自の符号を持ち、0は拒否されます。すべての修正値は、変更したロールの横に状態の名前とともにログに表示され(「12 + 5 + 3 (Blessed) = 20」)、メニューの命中率と勝率にも数えます。状態同士は累積しますが、同じ状態が2つあっても1つの状態です。

  ```json
  "conditions": [
    { "condition": "blessed", "modifiers": [{ "to": "attacks", "dice": "1d4" }, { "to": "saves", "dice": "1d4" }] },
    { "condition": "shielded", "modifiers": [{ "to": "defense", "flat": 5 }] },
    { "condition": "slowed", "modifiers": [{ "to": "speed", "times": 0.5 }, { "to": "defense", "flat": -2 }] }
  ]
  ```

- `levels`: 任意です。トラックが十分に高い間、状態として数えるライブトラックの段階で、消耗のように段階的に悪化する状態を表す方法です。各項目は普通の`track`(負傷トラックではない)、効果が始まる段階`at`、効果を指定し、状態と同じ`effects`、`modifiers`、`failsSaves`、`saves`、`skills`を持ちます。トラックが到達したすべての段階を数えるため、上がるにつれて累積します。段階は出所を持たず、読み取るものが下がったときだけ終わるため、`half-move-to-stand`、`ends-on-damage`、`cannot-target-source`、`cannot-approach-source`は拒否されます。トラックを持つのはシートを持つ戦闘員だけです。ログはトラックと数値で段階を示します(「- 1 (Heat 3)」)。

  `track`の代わりに、段階はキャラクターのライブ状態とアイテムを使って計算する`derived`値を読めます(Capability API 1.54)。誰も印を付ける必要はありません。Ember Roadsは、Bulkを10以上運ぶ者を遅くします。

  ```json
  { "derived": "bulk_carried", "at": 10, "modifiers": [{ "to": "speed", "flat": -2 }, { "to": "checks", "skills": ["sneak"], "flat": -1 }] }
  ```

  キャラクターごとに異なるしきい値(「Strengthの5倍を超える」)は、それを差し引く派生値で表します。-1の`scale`で差し引く部分を作り、2つの`sum`を段階が読みます。

  ```json
  "levels": [
    { "track": "exhaustion", "at": 1, "effects": ["own-checks-disadvantage"] },
    { "track": "exhaustion", "at": 2, "modifiers": [{ "to": "speed", "times": 0.5 }] },
    { "track": "exhaustion", "at": 3, "effects": ["own-attacks-disadvantage", "own-saves-disadvantage"] }
  ]
  ```

  修正値、段階、判定の効果にはCapability API 1.45が必要です。

- `checks`と`contests`: 任意です。対抗判定が読むものと、戦闘中に誰でも始められる対抗判定です。掴む、押し出す、振りほどくなどです。後述の「対抗判定」を参照してください。Capability API 1.43です。
- `concentration`: 任意です。維持しているものを記録するライブ`text`フィールド、ダメージによって要求される`save`、その難易度の下限`floor`、それを上回る場合に難易度となる被ダメージの割合`fromDamage`を指定します。集中を要する2つ目の能力を開始すると1つ目が終了します。セーヴに失敗した場合も終了し、それによって維持していた状態も解除されます。
- `dying`: 任意で、`kind: "saves"`です。判定の回数を数える2つのトラック(必要回数は各トラック自身の最大値)、`dice`、`succeedAt`、最大・最小の目の効果(`naturals.max`: `revive-1`または`success`、`naturals.min`: `one-failure`または`two-failures`)、倒れている間のダメージのコスト(`damageWhileDown`、`criticalWhileDown`)、倒れたキャラクターの`condition`を指定します。このブロックがなければ、0になったキャラクターは単に倒れ、回復すると復帰します。
- `damageTypes`: 任意です。独自システムのダメージ種別で、大文字・小文字を区別せず照合します。
- `damageKinds`: `health`が負傷トラックを指定する場合は必須で、プールを指定する場合は拒否されます。種類を保持できるのは印だけで、点数のプールにはそれを記録する場所がないためです(前述の「負傷トラック」を参照)。打撃がトラックのどの`kinds`で印を付け、何マスを埋めるかを定めます。`default`は、種別のない打撃も含め、対応付けのないすべての被害の種類です。`byType`は独自の`damageTypes`を印の種類に対応付け、キーは種別と同様に大文字・小文字を区別しません。そのため`"Fire"`と`"fire"`は同じキーで、両方を指定すると拒否されます。`marks`にデフォルトはありません。2つの選択肢の意味が正反対だからです。`"per-point"`はダメージ判定が体力段階を数える方式で、3の打撃なら3マスを埋め、1だけ軽減することにも意味があります。`"per-blow"`は打撃が当たるか当たらないかの方式で、強さにかかわらず1マスを埋めます。ダメージ節が複数ある打撃でも、実際に届いた最も重い種類で1マスだけを埋めます。自分のシステムに合う方を指定してください。`{ "default": "bashing", "byType": { "fire": "aggravated" }, "marks": "per-point" }`。
- `pool`: `dice-pool`では必須で、`attack-vs-defense`では拒否されます。「プールで振る戦闘」を参照してください。
- `spendLimits`: 任意です。戦闘の方式にかかわらず、1人の戦闘員が`turn`または`round`ごとにライブプールから消費できる量です。`[{ "pool": "blood", "max": { "derived": "blood_per_turn" }, "per": "turn" }]`のように書きます。`max`は戦闘開始時に1回読みます。上限の残りを超えるコストは、プールにどれだけあっても支払えないため、メニューに出ません。ターンごとの上限は持ち主自身のターン開始時に、ラウンドごとの上限はラウンド開始時にリセットします。数値で直接書いた敵はシートから何も支払わないため上限に縛られず、シートとして書いた敵は自身のプールから支払い、ほかと同じく上限に従います。Capability API 1.47です。
- `threat`: 任意ですが、ベスティアリには必要です。`tiers`は敵を選ぶ尺度で、ID、ラベル、`health`の帯域、`defense`、`toHit`、`damagePerRound`の帯域、`saveDifficulty`を持ちます。提供するすべてのクリーチャーはこの段階のいずれかを指定します。作者が用意していない敵はGame Masterが求めた段階に調整するため、尺度から外れません。`damagePerRound`の帯域は、一連の行動全体を含め、1ラウンドに1体の標的へ与える量として読み取ります。

### プールで振る戦闘: `dice-pool`

`dice-pool`ルールセットはダイスを合計せずに成功を数え、その戦闘も同じようにできます。`"kind": "dice-pool"`には`"dice-pool"`の`resolution.kind`が必要で、プール判定と同じようにシートを読みます。**ロールが加える数値はすべてダイスの個数で、ロールが対抗する数値はすべて成功数です。** そのため名前を変えるものはありません。

- 命中の数値(攻撃の行のもの、能力リストの`toHit`、クリーチャーのアクションのもの)は、攻撃が振るプールです。ダイス、ダイスが到達すべき目標値、2倍、爆発、相殺、大失敗となる目は`resolution`のものです。`resolution.penaltyFrom`が指定する負傷トラックは、判定と同じくプールからペナルティを引きます。
- `defense`は攻撃に必要な成功数で、1未満にはなりません。状態の`defense`への修正値と`cover.bonus`がそれに加わります。
- 必要数を超える成功1つごとに、ダメージダイスが1個増えます。大失敗は、数えた成功にかかわらず外れです。クリティカルはありません。強い命中はその追加ダイスに価値があります。
- セーヴの数値はそのプールで、難易度は必要な成功数です。対抗判定は両者の判定をプールとして振り、成功の多い側が勝ちます。
- 状態の攻撃、セーヴ、判定への修正値はダイスの増減なので、`flat`の数値です。振る修正値(`dice`)は拒否されます。
- ダメージはルールセットのダイスで振ります。量の`dice`(クリーチャーや項目のもの)が個数を示し、ルールセットのダイスでなければならず、`flat`の部分は振らない自動成功です。攻撃の行のダメージダイス列は個数として読み、`damage.ability`はその能力値の評価値をダイスとして加え、`damage.bonus`は自動成功を加えます。`perCostStep`と`scales`は従来どおりダイスを加えます。回復と一時ポイントは量で、従来どおり合計します。
- イニシアチブは合計(`initiative.dice`と`modifier`)か、要求すればプール(後述の`initiative.pool`)で、死亡ルールは独自のダイスを保ちます。

プール方式の戦闘がそれ以外に振るものは`pool`ブロックです。

```json
"pool": {
  "advantage": true,
  "damageTarget": 6,
  "soak": { "roll": true, "byKind": { "knock": { "abilityMod": "sinew" } } }
}
```

- `advantage`: 偏りのあるロールを2回振り、成功の多い方を使うかです(大失敗は、大失敗しなかったどの結果よりも少ないと数えます)。これがなければ、状態が何を示しても戦闘は1回だけ振ります。
- `damageTarget`: ダメージダイスと吸収ダイスを振るときのダイスごとの目標値です。省略すると解決方式のデフォルトの目標値です。これらのダイスはそれ以上の目を1回ずつ数えるだけで、2倍、爆発、相殺、大失敗は起きません。
- `soak`: 標的が命中の被害から差し引くもので、被害の種類ごとに指定します。`all`はあらゆる種類に対する値参照で、`byKind`は体力トラックの種類ごとの値参照で、その種類では`all`より優先します。どちらも指定しない種類は吸収しません。`"roll": true`なら、標的はその数のダイスをダメージの目標値に対して振り、成功1つごとに1を差し引きます。`"roll": false`なら、振る前にその数をダメージダイスから差し引くため、自動成功には影響しません。振る吸収なら、自動成功もほかと同じく差し引きます。0未満にはならず、何も数えなかった打撃を吸収するために振ることもありません。クリーチャーは独自の数値を`soak: { "all": 1, "byKind": { "knock": 3 } }`として指定し、そのためにはブロックの`soak`で吸収の方法を示す必要があります。抵抗、脆弱性、完全耐性、`resist-all`は吸収の後に残りへ適用します。
- `hardness`: イニシアチブを攻撃で動かす数値として扱う場合の、戦闘員の硬度の値参照です。[戦闘中の鎧と装備効果](#armor-and-worn-effects-in-a-fight)を参照してください。

命中が必要数を超えて得たものと吸収するものは各標的のものなので、ダメージは標的ごとに振ります。打撃の2つ目の節と追加効果は、それぞれ独自の種類のダメージプールで、命中による追加ダイスはありません。メニューはプールを正確に予測します。必要な成功数に届く確率と、最初の標的の吸収後のダメージダイスの価値です。

Gravewatchはこの方法で書かれています。番人は評価値と専門技能を振り、knockはSinewで吸収してtearはまったく吸収せず、1ターンにResolveを1ポイント消費でき、毎ラウンドイニシアチブを振り直します。

**逆順の宣言は実装していません。** 行動前に全員が遅い順に行動を宣言するシステムもあります。各戦闘員が自分のターンに1つの行動を選ぶ戦闘では、先に宣言しても規則が読むものは何も変わらないため、キーで示すことはありません。

### 攻撃で動くイニシアチブ

プールのシステムには、戦闘全体を通じてイニシアチブを数値として保持し、攻撃で動かせるものがあります。ある攻撃方法は標的からそれを奪い、別の方法は攻撃者自身の数値をダメージとして費やし、決まった線まで落ちた者はクラッシュします。`dice-pool`の戦闘はこれを表せます(Capability API 1.48)。

```json
"initiative": {
  "pool": { "abilityMod": "nerve" },
  "plus": 3,
  "resource": {
    "base": 3,
    "styles": [
      { "id": "press", "label": "Press", "takes": { "gain": 1 } },
      { "id": "telling", "label": "Telling blow", "spends": { "onMiss": [[0, 1], [6, 2], [11, 3]] } }
    ],
    "crash": { "at": 0, "condition": "reeling", "bonus": 5, "recoverAfter": 3 }
  }
}
```

- **開始時。** 戦闘開始時に全員が`pool`個のダイスを振り、成功数に`plus`を加えた値がその数値です。合計したダイスは順序であってダイスの個数ではないため、`resource`には`pool`が必要です。プール方式の戦闘で加える数値はすべてダイスなので、クリーチャーの`initiativeModifier`はそのプールです。数値は保持され、振り直しません(`resource`と並べた`each`は拒否されます)。各ラウンドの開始時に、その時点の数値で順序を並べ替えます。
- **スタイル。** すべての攻撃(攻撃の行、命中判定をして被害を与える能力やカタログ項目、被害を与えるクリーチャーのアクション、ほかのアクションで構成するアクション)はスタイルごとに1回ずつ提示され、プレイヤーは標的の前にスタイルを選びます。最大4つで、それぞれ奪うか費やすかのどちらかで、少なくとも1つは奪うスタイルです。スタイルを指定しない選択は最初のスタイルで行い、攻撃が提示されていないスタイルは拒否されます。命中前に応答で使い手の数値が変わっても、攻撃は終わるまで選んだスタイルを保ちます。
- **奪うスタイル。** 命中すると、ダメージは通常どおり振り(命中による追加ダイス、武器のダイス、種類ごとの吸収、自動成功)、数えた量は体力ではなく標的の数値から差し引きます。攻撃者はそのすべてに`gain`を加えて得ます。
- **費やすスタイル。** 攻撃者の数値がクラッシュの線(`crash`がなければ0)を上回る間だけ提示され、数値は1撃で費やすため、ほかのアクションで構成するアクションには提示されません。命中すると、ダメージは攻撃時の攻撃者の数値で、それをダメージの目標値に対するダイスとして振り、ほかには何もありません。武器のダイスも、命中による追加ダイスも、自動成功も、吸収もありません。攻撃自身の被害の種類で体力に印を付けます。攻撃が終わると、どこかに当たった数値は`base`に戻り、どこにも当たらなかった数値は、攻撃時の数値で`onMiss`が示す分を失います(段階表で、`[at least, lose]`の組を昇順に並べます。最初の段階未満では何も失いません)。
- **クラッシュ。** 数値が`crash.at`以下に落ちるとクラッシュします。`condition`(独自の状態の1つで任意)が付与され、そこまで追い込んだ者が`bonus`を得ます。自分の外れでクラッシュした場合は、誰もボーナスを得ません。クラッシュした戦闘員は費やせません。クラッシュは状態も含めて、数値が再び線を上回ったとき、自身のターンで`recoverAfter`回経過した後(そのターンの開始時に数値が`base`に戻ります)、そして戦闘がどのように終わってもその終了時に解けます。開始時のロールが線以下の者は、クラッシュした状態で戦闘を始めます。`base`は`crash.at`より大きくなければなりません。そうでなければ、戻るたびに再びクラッシュします。

メニューは各スタイルの見込みを示します。命中率と、奪うスタイルなら奪う量、費やすスタイルなら与える被害です。ステータスパネルは全員の数値を示し、ログはすべての変化とその理由を示します(「Ada gains 5 initiative for crashing Rats, and is on 14.」)。Engineの選択処理は奪う打撃を1ターン先まで評価し、奪ってから費やす場合と、今費やして基準値から再び費やす場合を比べます。

<a id="what-a-fight-reads-from-mechanics"></a>

### 戦闘が`mechanics`から読み取るもの

`kind`は`amount`がダメージか回復かを決めます。`reaction`が付いた項目はメニューから除外され、`utility`項目もターン自体に使えるものを変えない限り除外されます(後述)。`attackRoll`はリストの`toHit`を使って標的の防御への判定を行わせ、`autoHit`はそれを完全に省略します。`save`はリストの`saveDifficulty`に対して標的自身のセーヴを振り、`onSuccess`が成功時に半分を受けるかゼロになるかを決めます。`targetCount`は向けられる標的の数です。攻撃判定をしない能力(全員がセーヴする範囲や、自動で命中するもの)は全員分のダイスを一度だけ振り、各標的への命中判定をするものは命中ごとにダイスを振り直します。`applies`は影響を与えるものに状態を付与します。各状態は`duration`として`instant`(独自の時計がなく、何かで解除されるまで残る)、`until-save`(`saveEnds`の併記が必要)、`{ "rounds": n }`のいずれかを持ち、任意の`saveEnds`でセーヴと、それを`turn-end`か`turn-start`のどちらで繰り返すかを指定します。ラウンドは持ち主自身のターンが終わるごとに減ります。`{ "rounds": 1, "at": "turn-start" }`はターンが始まるごとに数え、「次の自分のターンの開始まで」を表します。`endsAfter`は、時計の指定にかかわらず、最初の`own-attack`(持ち主の次の攻撃判定)、`attacked`(持ち主に対する次の攻撃判定)、`own-save`(持ち主の次のセーヴ)の後に状態を解除します。そのため`{ "duration": { "rounds": 1 }, "endsAfter": "own-attack" }`は「次のターンの終了前に行う次の攻撃まで」を表します。1回の攻撃の間続くものは、ダメージも含めてその攻撃全体の間続き、同じ打撃が新たに付与したものは残ります。どちらにもCapability API 1.45が必要です。`temporary`は体力プールに一時ポイントを与えますが、累積せず、大きい方のバッファが残ります。`scales`は読み取った値に対応して表が与える追加ダイスで量を増やします。`cost`はシート自身の`use`コマンドで支払い、`budget`は消費する行動枠を上書きします。

`plus`は`amount`に加えて同じ打撃に最大3つの量を追加し、それぞれ独自に振り、種別を持たせます("and 2d6 fire")。節は`{ "dice": "2d6", "flat": 1, "type": "fire" }`の形で、独自の`save`として`{ "save": "con_save", "difficulty": 13, "onSuccess": "none" | "half" }`を持つこともできます。アクションがすでに何を要求していても標的がこれを振ります。成功時、`none`ならその節はゼロ、`half`なら半分となり、どちらでも打撃のほかの部分は変わりません。`difficulty`がなければ、アクション自身のセーヴが使う数値、次いでリストの`saveDifficulty`にフォールバックします。クリティカルは最初の量と同じルールで各節のダイスを倍にします。`type`がない節は打撃自身の被害の種類を使います。打撃全体は依然として、合計ダメージによる1回の集中判定と、1回の倒れるかどうかの判定です。節を付けるには`amount`が必要で、`heal`には付けられません。

```json
{
  "kind": "attack",
  "attackRoll": true,
  "amount": { "dice": "1d8" },
  "damageType": "piercing",
  "plus": [{ "dice": "2d6", "type": "fire" }]
}
```

3つのキーで、項目がターン自身の行動枠に何をするかを指定します。そのいずれかを宣言する`utility`項目は、除外せず提示されます。

- `free`: 行動枠をまったく消費しません。ただし指定した`cost`は支払い、同時に`budget`を指定することはできません。
- `gives`: `[{ "budget": "action", "count": 1 }]`。最大4つです。使用した瞬間にそれらの行動枠へ加算しますが、加算後の値は1ターンの枠に贈与分を足した量が上限です。後のターン用に貯めることはできません。
- `standard`: `{ "actions": ["dash", "disengage", "hide"], "budget": "bonus" }`。所有者はそれらの標準アクションをその行動枠で使えます。通常のものと並んで`standard:<id>@<budget>`として提示されます。その許可しか与えない項目自体はメニューに出ません。許可は実行するものではないためです。

新しい`kind: "rider"`の項目は受動的です。誰も実行せず、メニューにも出ず、各期間で最初の条件を満たす命中に、ダメージ節を1つ自動で追加します。`rider`を持ち、ほかの実行する内容は持ちません。

```json
{
  "kind": "rider",
  "rider": {
    "on": "hit",
    "sources": ["attacks"],
    "requires": { "column": "finesse" },
    "when": ["advantage", "ally-adjacent"],
    "oncePer": "turn",
    "amount": { "dice": "1d6" }
  },
  "scales": {
    "from": { "field": "level" },
    "table": [
      [1, 0],
      [3, 1]
    ]
  }
}
```

`sources`は対象とする攻撃リストを、`requires`はその行の真と評価される列を1つ指定します。特定の武器だけで発動する追加効果でも、Engineが武器の意味を知らずに対象を指定できます。どちらも指定しなければ、所有者によるあらゆる命中が対象です。袋から手に持った武器は行ではないため、`weapons`(Capability API 1.70)で発動するアイテムのタグも指定します。`"weapons": { "tags": ["finesse",
"ranged"] }`は、どちらかのタグを持つ手持ちの武器による命中で、オフハンドの打撃も含めて発動します。`weapons`だけを指定すると行では発動せず、行だけを指定すると手持ちの武器では発動しません。`when`はいずれか1つを満たせば成立します。`advantage`は最終的に攻撃判定がどちらに有利だったかを表し、`ally-adjacent`は攻撃者の立っていて行動可能な味方で、盤面上なら標的から1マス以内、盤面なしならどこにいても該当します。`oncePer`は`turn`(存在するすべてのターンの開始時に更新するため、他者の行動中の打撃にも乗せられる)か`round`です。`amount`は項目自身の`scales`で増え、`type`は被害の種類で、デフォルトは打撃自身の種類です。

<a id="creatures-a-bestiary-a-fight-reads"></a>

### クリーチャー: 戦闘が読み取るベスティアリ

`"holds": "creatures"`を宣言するカタログは、シートの行ではなく敵を含みます。どのリストにも供給せず、シートエディターの選択画面にも出ません。すべての数値は、`combat`ブロックがすでに宣言しているキーで記述します。クリーチャーを独自の段階の1つに分類するため、`combat`ブロックと`threat`尺度が必要です。

```json
{
  "id": "road_trouble",
  "label": "Road trouble",
  "holds": "creatures",
  "filters": [{ "id": "tier", "label": "How bad", "type": "text" }],
  "entries": [
    {
      "id": "rust-jackal",
      "label": "Rust Jackal",
      "summary": "A lean thing that lives on the metal roads.",
      "filters": { "tier": "Pack trouble" },
      "creature": {
        "health": { "dice": "3d6" },
        "defense": 6,
        "initiativeModifier": 1,
        "speed": 16,
        "abilities": { "brawn": 1, "wits": 0, "heart": -1 },
        "tier": "pack",
        "actions": [
          {
            "id": "bite",
            "name": "Bite",
            "budget": "act",
            "toHit": 2,
            "damage": { "dice": "1d6", "flat": 1, "type": "cut" },
            "reach": 2
          },
          {
            "id": "worry",
            "name": "Worry",
            "budget": "act",
            "toHit": 2,
            "damage": { "dice": "1d4", "type": "cut" },
            "applies": [{ "condition": "shaken", "duration": { "rounds": 2 } }]
          },
          {
            "id": "snap_and_worry",
            "name": "Snap and worry",
            "budget": "act",
            "sequence": [
              { "action": "bite", "times": 1 },
              { "action": "worry", "times": 1 }
            ]
          }
        ]
      }
    }
  ]
}
```

以下は数値を直接使ってクリーチャーを書く方法です。独自のルールセットの言葉で`sheet`として書いた場合、`health`、`defense`、`initiativeModifier`、`speed`、`abilities`、`saves`、`checks`、`soak`、`hardness`はそのシートから取得します(後述の「独自のルールセットの言葉で書くクリーチャー」を参照)。

- `health`: 数値か、戦闘作成時に一度振る`{ "dice": "3d6", "flat": 2 }`です。予測には平均を使うため、まだ誰も振っていないダイスの結果をメニューが約束することはありません。
- `defense`、`initiativeModifier`、`speed`: それぞれ攻撃判定の対象値、イニシアチブに加える値(イニシアチブをプールで振る場合は振るダイスの個数)、独自の距離単位による1ターンの歩行距離です。
- `abilities`と`saves`: シートに宣言した能力値IDとセーヴIDをキーにします。指定しないセーヴはゼロとして読み取ります。
- `checks`: 対抗判定で加える値で、`combat.checks`のIDをキーにします。指定しないものはゼロとして読みます。Capability API 1.43です。
- `soak`: `dice-pool`の戦闘だけで使う吸収量です。`all`はあらゆる被害、`byKind`は体力トラックの種類ごとです。Capability API 1.47です。
- `hardness`: イニシアチブを攻撃で動かす数値として扱う場合、ダイスがこれ未満の費やす打撃は何も起こしません。Capability API 1.56です。
- `resist`、`vulnerable`、`immune`: ダメージ種別です。大文字・小文字を区別せず照合し、`combat.damageTypes`を宣言した場合はそれと検証します。`resist`や`immune`の項目は、何がそれを通り抜けるかも`{ "type": "tearing", "except": ["silver"] }`で指定できます。それらのアイテムタグのいずれかを持つ武器アイテムからの打撃は、そのまま受けます(Capability API 1.55。[戦闘中の武器](#weapons-in-a-fight)を参照)。`conditionImmunities`は独自の状態を指定します。
- `tier`: `combat.threat`のどの段階に属するかです。
- `loot`(Capability API 1.63): 勝利した戦闘がこのクリーチャーについて振る戦利品表のIDです(前述の「戦利品」を参照)。
- `traits`: Game Masterに見せる短い名前と説明の組です。自動解決しないため、数値を持つ内容はアクションに書きます。
- `signaturePoints`: 自身のターン開始時に戻るポイントで、`signature`アクションに消費します。
- `riders`: 最大4つで、カタログ項目の`rider`と同じものをブロックに記述します。各項目は`{ "id": "pack", "name": "Pack", "on": "hit", "oncePer": "turn" | "round", "amount": { "dice": "1d6" } }`で、任意の`type`と、このブロック自身のどのアクションで発動するかを指定する任意の`actions`を持てます。ブロックの追加効果はシートのリストを読まないため、`sources`と`requires`の2つのキーを持ちません。シートとして記述したクリーチャーは、キャラクターと同じくリストの追加効果を得ます。
- `actions`: 最大12個で、それぞれ独自の`id`を持ちます。アクションは手書きのステータスブロックの内容(`toHit`、`autoHit`、`damage`、`save`、`applies`、`targetCount`、`reach`、`range`、`area`)に加え、クリーチャーだけが持つ4つの要素を持ちます。`reach`は打撃が届く距離、`range`は投擲や射撃の距離、`area`は着弾する形状で、すべて独自の距離単位です。`range`は単なる数値か、不利を受けてさらに届く場合は`{ "normal": 30, "long": 120 }`にできます。`area`は`{ "shape": "burst" | "cone" | "line", "size": n, "friendlyFire": false }`です(「位置」を参照)。
  - `uses`: `{ "per": "encounter" | "day", "count": n }`。使い切るとアクションはメニューから消えます。
  - `recharge`: `{ "dice": { "count": 1, "sides": 6 }, "from": 5 }`。戦闘開始時は使用可能で、使うと消費されます。自身のターン開始時に振り、`from`以上なら回復します。どちらの結果でもダイスをログに残します。
  - `sequence`: 同じブロックのほかのアクションを順番に並べ、それぞれに標的を指定します。**1つのアクションで2回攻撃するクリーチャーはこの方法で書きます。** 1回の行動枠で連続行動全体を支払います。連続行動は独自の内容を持たず、別の連続行動を指定することもできません。
  - `signature`: `{ "cost": n }`。行動枠ではなくクリーチャー自身のポイントで支払い、他者の行動中だけ使えます。戦闘はあるターンと次のターンの間のウィンドウで提示します(「ウィンドウ」を参照)。
  - `reaction`: カタログ項目の`mechanics.reaction`と同じオブジェクトです(「ウィンドウ」を参照)。アクションはどのターンのメニューにも出ず、代わりに指定した瞬間に提示されます。リアクションは固有アクションを兼ねられず、連続行動もリアクションを含められません。
  - `self: true`: 他者ではなくクリーチャー自身に作用するため、`targetCount`や`area`を持ちません。どちらにもCapability API 1.46が必要です。Parryはその両方で、防御に2を加える`parrying`状態を伴います。

    ```json
    {
      "id": "parry",
      "name": "Parry",
      "budget": "reaction",
      "self": true,
      "reaction": { "on": "hit" },
      "applies": [{ "condition": "parrying", "duration": { "rounds": 1 }, "endsAfter": "attacked" }]
    }
    ```
- セーヴにはアクション自身に難易度が必要です。アクションが要求するセーヴなら`save.difficulty`、アクション自身のセーヴがなく、セーヴで終了する状態なら`saveDifficulty`です。シートを持つクリーチャーでもブロックのアクションは直接の数値で書くため、その値はアクションに置きます。節自身のセーヴは`difficulty`を省略して同じ数値にフォールバックできます。
- `damage.plus`はカタログ項目の`plus`と同じ節のリストで、読み方もまったく同じです。`"damage": { "dice": "1d6", "flat": 2, "type": "piercing", "plus": [{ "dice": "1d4", "type": "fire" }] }`は、熱を独立した量として持つ噛みつきで、その熱は独立して抵抗され、独立して倍化されます。

5eの草案のベスティアリは、`docs/development/ruleset-5e-2014.example.json`にある手書きの5体です。連続行動、再充填、状態を伴うセーヴ、抵抗と完全耐性、使用回数制限、固有ポイント、シートとして記述した1体を網羅しています。

#### 独自のルールセットの言葉で書くクリーチャー

クリーチャーは数値を直接書く必要はありません。代わりにキャラクターのシートとまったく同じ形の`sheet`を与えると、戦闘はパーティーメンバーと同じ方法で構築します。体力、防御、セーヴ、イニシアチブ、速度、リスト上のすべての攻撃と能力は、独自のシートの式から得られます。敵がキャラクターと同じ能力値、スキル、リストを持つルールセットでは、それが何であってもこの方法で表現できます。Ember RoadsのToll Wardenは次のとおりです。

```json
{
  "id": "toll-warden",
  "label": "Toll Warden",
  "creature": {
    "tier": "pack",
    "traits": [{ "name": "Knows the road", "text": "It will not follow anyone past the last milestone." }],
    "sheet": {
      "abilities": { "brawn": 2, "wits": 1, "heart": 1 },
      "skills": { "sway": "trained" },
      "fields": { "calling": "Hauler", "toughness": 3 },
      "lists": {
        "gear": [{ "name": "Toll hook", "swing": "brawn", "damage": "1d6", "harm": "cut" }],
        "knacks": [{ "name": "Hold the Line", "_catalog": "knacks/hold-the-line" }]
      }
    }
  }
}
```

- **すべての部分は任意です。** `abilities`、`skills`、`saves`、`bonuses`、`fields`、`lists`を、シートに宣言したIDをキーとして使います。省略したものは、空白のキャラクターと同じくシート自身のデフォルトを読み取ります。番人のGritが9なのは`grit_max`が4、Toughness、Brawnを足すためで、Guardが7なのも同じような理由です。
- **各数値の出所は1つです。** シートを持つクリーチャーは`health`、`defense`、`initiativeModifier`、`speed`、`abilities`、`saves`、`checks`を別途指定できません。指定するとEngineはファイルを拒否します。リストが行動を定めるため、独自の`actions`を持たなくてもかまいません。シートのないクリーチャーは、引き続き最初の3つと少なくとも1つのアクションを指定します。
- **作者が書いたデータとして検証します。** IDはすべてシートに宣言したものでなければなりません。スキルとセーヴはその項目に提供した習熟段階のいずれかに設定し、フィールド、能力値、ボーナス、列は宣言された値(範囲内の整数、選択肢の1つなど)を持ち、リストの行数は上限を超えられません。クリーチャーの消費分は戦闘が記録するため、`live`部分はありません。
- **行はカタログから取得できます。** `_catalog: "<catalog>/<entry>"`はキャラクターのシートと同じく行の選択元の項目を指定し、戦闘はその項目から行のコストと効果を読み取ります。カタログはそのリストに供給するものでなければなりません。インラインのカタログなら項目がその中に必要です。別ファイルなら、ファイルにない項目を指定する行はクリーチャーに何も与えないだけです。ベスティアリのシートが指定するカタログは、ベスティアリと一緒に戦闘用に読み込みます。
- **シートの外に書いた内容も有効です。** `tier`、`traits`、`actions`、`signaturePoints`、`riders`、`resist`、`vulnerable`、`immune`、`conditionImmunities`です。
- **自身のプールから支払います。** プールは満タンで始まり、リストが与える行動に消費します。EngineとGame Masterのどちらが決める場合も、パーティーメンバーと同じく、より大きな支払い方法(高いスロットからの呪文など)が提示されます。番人のHold the LineはLuckを消費します。
- **負傷トラックの場合、体力はトラックです。** 打撃は`resist`、`vulnerable`、`immune`を適用した後、`damageKinds`に従ってクリーチャー自身のトラックに印を付けます。ある種類の被害への完全耐性があれば、その印は付きません。
- **あくまで敵です。** ゼロになると瀕死ではなく脱落し、死亡に対する判定はしません。画面には従来の敵の情報だけを出し、シートは表示しません。同名のキャラクターがいても、消費したものをどこかに書き戻すことはありません。
- **計算結果として体力がまったくないシート**は戦闘から除外し、開始ログで理由を示します。誰も傷つけられない存在として参加させることはありません。
- レイヤーが列挙フィールドからある値を除いても、それを使うクリーチャーが失われることはありません。レイヤーの有効中はキャラクターと同じくそのフィールドをデフォルトとして読み取り、そのためにクリーチャーを拒否しません。
- Game Masterもクリーチャーを作れます。その場合は段階に収めます(「作者が用意していない敵」を参照)。
- この形式を提供するパッケージはCapability API 1.34を宣言します。

5eの草案のToll Sergeantは、同じ仕組みをd20シートで表したものです。Armor Class、体力、セーヴ、1アクションで2回の攻撃は、すべて自身のフィールドと攻撃リストに由来します。

#### 作者が用意していない敵

Game Masterが敵を作ると、Engineは何かを振る前にその提案を`threat`尺度に収めます。体力は段階の帯域内、防御、命中補正、セーヴ難易度は段階の値より最大2上までとし、最強の1ラウンド(最も強い連続行動か単独アクションを、1体の標的に対して測ったもの)がその段階の`damagePerRound`内になるまでダメージを減らします。最初にダイス個数、次に固定値、次に連続行動から打撃1回、最後にダイスの面数を減らし、ゼロにはしません。ルールセットにない名称は削除します。未知のダメージ種別、状態、セーヴと、最初の6つを超えるアクションが対象です。宣言されていない段階は尺度の最下段にフォールバックします。変更はすべて平易な文として返され、ログで内容を説明できます。

作られる敵も、ベスティアリのクリーチャーと同じく`sheet`として書けます。これによって、即興の魔術師もスロットと呪文を持てます。Game MasterにはシートのIDと各項目に入る値、戦闘が読むリスト、カタログがそれらに提供する名前を見せるため、呪文は説明するのではなく名前で指定します。大文字・小文字を問わずカタログ項目を名指す行はその項目となり、Game Master自身の値(呪文の準備状態など)を上に重ねます。モデルが書くため、シートは寛容に読み取ります。ルールセットにない名前は削除し、値はフィールドや列に合わせ、シートの横に書かれた数値は使いません。

ボスではない即興のクリーチャーは、ルールセットがそれに開放する範囲に制限されます。カタログフィルターの`startFrom`は、項目を分類するシートのフィールドを指定します(5eパッケージの呪文リストなら`class`)。クリーチャーには、そのフィールドの自身の値にフィルターが一致する項目だけを残し、照合方法は選択画面を開くときと同じです。そのためSorcererが呪文リスト全体を持つことはなく、クラスを指定しない者はクラス別カタログから何も得ません。未選択の内容はGame Masterに聞き直さず埋めます。選択した行だけが有効な各リスト(戦闘能力の参照元に`onlyWhen`があるもの)について、開放されていて自身のプールで支払える項目から、持っている各プールに対応するものと自由に使えるものを少数ずつ補充します。能力の高いクリーチャーほど多くなります。選ぶ内容は、戦い方にも使う気質と熟達度に寄せます。守備的・支援的なものは味方を支える効果、無謀なものは加害、几帳面・忍耐強いものは敵を抑える効果を選び、熟達するほどリアクション、対抗手段、その他ターンを変えるものを持ちやすくなります。抽選は戦闘自身のシードを使うため、同じ戦闘なら常に同じように埋まります。そのようなリストでGame Masterが名指した行は、選択済みとして扱います。

ボスは例外となり得るため、Game Masterが全体を書きます。何も取り除かず、何も補充しません。

その後、どちらも段階に収めます。

- 体力は、その値の参照元となる1つのフィールドを通じて段階の帯域に収めます。プールの最大値はそのフィールドか、フィールドをちょうど1つ含む`sum`です(5eの最大体力、Ember RoadsのToughness)。単一のフィールドを含まない体力の式はそのままにし、ログで説明します。負傷トラックの長さは作者の指定なので、変更しません。
- クリーチャーの構築後、防御、命中補正、セーヴ難易度は段階の値より2上までに制限し、支払える最大のコストも数えた最強の1ラウンドが段階の`damagePerRound`内になるまでダメージを減らします。まず大きな支払いによる上乗せ、次にダイス、固定値、打撃1回、最後にダイスの面数を減らします。

作者自身のベスティアリは制限しません。作者が書いたデータなので、Engineはそのまま受け取ります。

### 位置: 盤面上の戦闘

ブロックが盤面1マスの距離を定めるまでは、戦闘は想像上で進みます。`distance`を宣言するとグリッドで戦えるようになり、移動、間合い、射程、範囲、視線、遮蔽、離れていく相手への打撃が意味を持ち始めます。それぞれの数値は作者が書くもので、Engineが提供するのは盤面だけです。

```json
"distance": { "label": "ft", "perCell": 5 },
"ranged": { "long": "disadvantage", "adjacentFoe": "disadvantage" },
"cover": { "bonus": 2 },
"opportunity": { "budget": "reaction" }
```

Ember Roadsはこの1行だけを宣言します。それ以外が必須ではないことを示す例です。

```json
"distance": { "label": "paces", "perCell": 2 }
```

**マス。** `distance.perCell`は1マスが独自の単位のいくつ分かを表し、`label`はその単位の呼び名です。ブロックの世界のすべての距離、つまり`economy.movement`、クリーチャーの`speed`、武器の`reach`と`range`、クリーチャーのアクションの`reach`と`range`がこの単位です。独自の`units.distance`を宣言するカタログは、自身の`perCell`で`mechanics.range`と`area.size`を変換します。宣言しないものはこの設定を使います。ゼロより大きな距離は最も近いマス数に丸め、ゼロにはしないため、数値を指定したものは少なくとも1マス届きます。ゼロは短い距離ではなく、独自の意味を保ちます。`mechanics.range`の0は自分か接触を意味します(他者への接触は隣のマスに届きます)。武器の`reach`または`range`列が0の行は、その種類の距離を持ちません。

**盤面上で戦うかどうか。** 2つの条件を満たす必要があります。ブロックが`distance`を宣言し、プレイヤーのゲームがTactical戦闘スタイルに設定されていることです。Classicスタイル、または`distance`のないルールセットでは、従来どおり想像上の戦闘となります。誰でも誰にでも向けることができ、以下の内容は一切読み取りません。

**プレイヤーの画面。** Tacticalスタイル自身の地形を使って盤面を描きます。各マスはポインターや矢印キーで操作できるボタンで、その場所の種類、誰がいるか、選択途中の操作にとって何を意味するかを示します。歩行ではメニューが提示したマスを光らせ、それぞれに独自の単位でコストを表示し、経路を描きます。その経路上で誰かが攻撃するマスは琥珀色で示し、盤面の下に相手の名前を出します。標的を取る選択肢では、選べる相手を盤面とリストの両方で同時に強調します。`area`のある選択肢はマスに向け、ポインターの下のマスには味方も含めて巻き込む相手を表示します。残りの移動量は行動枠の横に、ここでも独自の単位で表示します。画面は測定しません。すべてのマス、コスト、経路、標的、狙い位置はサーバーから送られます。

**移動。** 1ターンの移動量は、パーティーメンバーなら`economy.movement`、クリーチャーなら自身の`speed`を`perCell`で割って切り捨てます。ただし移動可能な限り最低1マスです。所有者自身のターン開始時に補充し、アクションの前、合間、後に使えます。歩き、攻撃し、また歩けます。1マスに入るコストは1で、移動しにくい地形では増えます。この機能が想定するテーブルトップのグリッドに合わせ、8方向すべて同じコストです。味方は通り抜けられますが、誰かの上では止まれません。敵は壁になり、固体のマスには入れず、固体の2マスの角を斜めに抜けることもできません。

**間合いと射程。** 武器の行は`combat.attacks[].reach`と`.range`から取得します。それぞれ同じリストの列か、全行共通の数値です。

```json
"attacks": [
  {
    "list": "attacks",
    "budget": "action",
    "name": "name",
    "toHit": { "ability": { "column": "ability" } },
    "damage": { "dice": { "column": "damage" } },
    "reach": { "column": "reach" },
    "range": { "normal": { "column": "range" }, "long": { "column": "long_range" } }
  }
]
```

列が0の行は、その種類の距離を持たないことを示します。通常の剣と投げ斧が同じリストに入る仕組みです。間合いがまったくない行は1マスに届きます。クリーチャーのアクションは自身の`reach`か`range`を使い、カタログの能力は`mechanics.range`を使います(0は自分か接触で、他者に向ける場合は1マスです)。

両方を持つ行は投擲武器です。間合いの内側では振るい、外側では射撃します。そのため、以下の射撃ルールは手に持って振るうときには適用されません。弓と違い、通り過ぎる相手を打つこともできます。

クリーチャーのアクションは、独自の単位で着弾する`area`も持てます。`{ "shape": "cone",
"size": 15 }`のように書き、`"friendlyFire": false`なら味方を除外します。これによりブレスは標的数ではなく、盤面上の実際のコーンになります。連続行動は独自の形状を持たず、指定された各アクションが持ちます。盤面のない戦闘は形状を無視して`targetCount`を使うため、クリーチャーの項目は両方を持てば、どちらでも正しく表現できます。

**形状をどこまで送れるか。** `range`で指定します。100フィート先へ投げる球なら射程を持ちます。射程がなければバーストは置いた場所、つまり実行者自身のマスで発生します。コーンとラインは描く長さの範囲内のどこにでも向けられます。その場合のマスは方向を示すだけだからです。これはクリーチャーだけでなく、カタログ項目の`mechanics.area`にも当てはまります。

`ranged`は、通常の`normal`距離を超える射撃や、隣のマスに敵がいるときの射撃の不利益を指定します。どちらも`"disadvantage"`か`"normal"`です。ブロックを省略すると、どちらも不利益を受けません。近接の打撃は射撃ではないため、これらのルールは適用されません。自身の間合い内で使う投擲武器も同様です。

**範囲。** 項目の`mechanics.area`は盤面上の実際の形状になり、誰かではなくマスに向けます。`targetCount`は関係せず、届く数は形状が決めます。項目に`"friendlyFire": false`がない限り、そのマスに立つ全員、味方も敵も巻き込みます。

```
burst, size 2, aimed at X        cone, size 3, aimed right      line, size 3, aimed right
. . . . .                        . . . .                        . . . .
. # # # .                        . . # .                        A # # #
. # X # .                        A # # #                        . . . .
. # # # .                        . . # .
. . . . .                        . . . .
```

バーストは狙ったマスからサイズ以内のすべてのマスです。コーンは実行者からそのマスの方向へ伸び、各段階で距離と同じ幅になります。ラインは同じ方向へ1マス幅で伸びます。3つとも固体にぶつかると止まります。

**視線と遮蔽。** 両者を結ぶマスの直線を使います。その上に固体があれば射撃を遮り、範囲が向こうへ広がることを止め、標的は単にメニューに出なくなります。遮蔽となる地形は、攻撃判定の対象となる防御に`cover.bonus`を加え、ログでも示します。四分の三遮蔽、完全遮蔽、高低差はありません。

**離れていく相手への打撃。** `opportunity.budget`を宣言すると、立っていて行動可能で、その行動枠と近接攻撃手段を持つ敵の間合いから戦闘者が出るとき、歩行はその場で止まり、敵に攻撃するか尋ねます。実行すれば行動枠を消費し、自身のターンに同じ攻撃をした場合とまったく同じく解決します。見送ればコストはありません。どちらでも、歩行は停止した地点から再開し、実際に通った各マスのコストを支払います。打撃で移動者が倒れれば、倒れた場所で歩行を終えます。同じ間合いから経路が何度出ても、歩行全体につき各敵に1回の機会です。`disengage`は残りのターン中これを防ぎ、`opportunity`を宣言しないルールセットにはこの仕組み自体がありません。

この問いかけはウィンドウで、戦闘全体を止めます。尋ねられた全員が答えるまで、ほかは何も動きません。パーティーメンバーのウィンドウはプレイヤーが答え、打撃とその隣のPassが表示されます。ほかの者はその操作担当が答え、Game MasterのボスはGame Master自身の判断を通じて答えます。後述の「ウィンドウ」を参照してください。

**敵の盤面の使い方。** 誰も操作しない敵は、到達可能な各マスと、そこから使える各選択肢を組み合わせて評価し、歩行に対して受ける打撃ごとに減点します。現在地から最善の行動をすでに取れるなら、移動しない方を好みます。何も届かなければ距離を詰め、`standard`リストに`dash`があれば先に疾走します。

**表示される拒否理由。** `out-of-reach`(届く距離より遠い)、`no-line-of-sight`(固体が間にある)、`unreachable`(歩行コストを支払えない、または止まれないマス)、`bad-cell`(形状を向けられない場所に向けた)です。

### サーバー側で戦闘がブロックを使う仕組み

ルールセットが`combat`を宣言したゲームでは、Engineが従来から使う保存済み戦闘の上で、そのブロックに従って戦闘を解決します。

- **参加者。** 誰が戦うかはGame Masterが定め、Engineは各パーティーメンバーの数値を自身のシートから読み取ります。そのルールセットのシートがないメンバーには作者が書いていない数値を与えず、名前を示して拒否します。
- **敵の数値の取得元**は、次の順です。Game Masterがベスティアリで名指したクリーチャー、敵自身の名前とラベルが一致するクリーチャー、Game Masterがこの戦闘用に提案して制限処理で脅威尺度に収めたステータスブロック、最後にその段階自身の数値から構築する単純なクリーチャーです。すべてのフォールバックと制限を平易な言葉で記録し、戦闘が処理内容を説明できるようにします。ベスティアリの項目も提案も脅威尺度もないルールセットは、敵をでっち上げるのではなく戦闘を拒否します。
- **シートが記録です。** 受け付けたアクションごとに、体力、プール、状態、集中、瀕死ルールのカウントをシート自身のルールを通じて書き込みます。そのため途中で再読み込みしても戦闘の結果が正確に表示され、食い違う可能性のある戦闘終了時の集計はありません。
- **メニューだけが合法性を定めます。** プレイヤーも敵も、行動するすべての者はブロックが生成する同じメニューからIDを選びます。Engineが操作する敵はEngine自身の戦術で選び、Game Masterが操作する敵には同じメニューからIDを1つ選ぶよう求めます。独自の数値を見せますが、ダイスの結果は教えません。
- **独自のダイス。** 戦闘は自身のシードとカーソルを持つため、ディスクから読み直した戦闘も、本来振るはずだったダイスで続きます。

### 画面上の表示

戦闘画面は作者の言葉で進みます。メニューは独自の攻撃、能力、対抗判定、列挙した標準アクションで、それぞれ独自の行動枠とプールから何を消費するかを示します。行動順、ラウンド、指定したすべての状態と残りラウンド、一時ポイント、集中、瀕死ルールの2つのカウントを表示します。ログも独自の言葉で実際の計算を出力します。"Juno attacks Rust jackal with Road axe: 8 (5 + 3) + 3 = 11 against Guard 6, a hit."。受け付けた各アクションはその場でシートに書くため、途中で再読み込みしても正確で、後からGame Masterには数値を再び変更しないよう伝えます。

位置のある戦闘は、ポートレートのステージではなく盤面に描きます。プレイヤーの操作については「位置」を参照してください。盤面、メニュー、ログの距離はすべて独自の単位で表します。"Juno moves to 4, 6 for 6 paces and has 2 paces left."。

### 対抗判定: 掴む、押し出す、振りほどく

防御に対する攻撃ではなく、対抗判定となる行動もあります。両者がロールし、結果の良い方が思いどおりにします。誰かを掴む、押し倒すか押しやる、振りほどくは、どれも同じ形なので、ルールセットはそれぞれをデータとして記述します。

```json
"checks": [
  { "id": "brawn", "label": "Brawn", "value": { "abilityMod": "brawn" } },
  { "id": "wits", "label": "Wits", "value": { "abilityMod": "wits" } }
],
"contests": [
  {
    "id": "grab",
    "label": "Grab",
    "budget": "act",
    "attacker": { "checks": ["brawn"] },
    "defender": { "checks": ["brawn", "wits"] },
    "onWin": { "applies": [{ "condition": "held" }] }
  },
  {
    "id": "break_free",
    "label": "Break free",
    "budget": "act",
    "attacker": { "checks": ["brawn", "wits"] },
    "defender": { "checks": ["brawn"] },
    "from": { "holding": "held" },
    "onWin": { "ends": [{ "condition": "held", "on": "actor" }] }
  },
  {
    "id": "shove",
    "label": "Shove back",
    "budget": "act",
    "attacker": { "checks": ["brawn"] },
    "defender": { "checks": ["brawn"] },
    "ties": "attacker",
    "onWin": { "push": 4 }
  }
]
```

- **`checks`**は対抗判定が読む数値で、それぞれシート上の値です。防御やセーヴと同じく、戦闘開始時に1回読みます。数値で直接書いたクリーチャーは独自の値を指定し(`"checks": { "brawn": 2 }`)、シートを持つクリーチャーはシートから読みます。最大12個です。
- **ロール。** 両者が`attackRoll.dice`を振り、ここで使える判定(`attacker.checks`、`defender.checks`)の最良のものを加えます。合計が高い方が勝ち、同値は`ties`が`"attacker"`でない限り防御側の勝ちです。ログは両者を示します(「Juno tries Grab on Ash-hound: 12 (6 + 6) + 3 = 15 with Brawn against 2 (1 + 1) + 2 = 4 with Brawn, and wins.」)。
- **勝利**すると`onWin`の内容を行い、少なくとも1つ必要です。
  - `applies`は勝者を出所として敗者に状態を付与します。そのため`endsWhenSourceDown`を付けた状態は、掴んでいる者が倒れると終わります。`rounds`は状態に時計を与え、なければ何かが終わらせるまで続きます。
  - `ends`は実行者か標的から状態を解除します。
  - `push`は敗者を勝者から真っすぐ離れる方向へ、独自の距離単位でその距離だけ動かし、固体、立っている者、盤面の端、すり抜けられないほど狭い角の手前で止まります。強制移動なので、移動量を消費せず、誰もそれに打撃しません。盤面のない戦闘では誰も動きません。
    負けても何も起きません。それが掴みの失敗です。
- **`from: { "holding": "held" }`**は、実行者にその状態を付与した者だけを対抗判定の対象にし、その状態がある間だけメニューに載せます。振りほどくことはこう表します。
- **`reach`**は独自の距離単位で届く距離で、省略すると隣のマスです。`reach`と`push`には`combat.distance`が必要です。
- **`strike: true`**は、攻撃と同じく、アクションが複数の打撃を得る場合に1打撃の代わりにできます。最初に行うと行動枠を消費して残りの打撃を手持ちにし、手持ちがある状態で行うとその1つを消費します。5eのリファレンスはこの方法で組み付きと突き飛ばしを行います。
- **メニューでは**対抗判定を独自のグループにまとめ、勝率を示します。Engineが操作する敵はほかと同じく評価しますが、控えめです。掴みや押し出しは何かの下準備であり、振りほどくことは掴まれている間だけ最も価値があります。敵を操作するGMは同じメニューから選びます。
- GMが作る敵の判定は、命中率と同じく段階に制限されます。

対抗判定は、パッケージ形式のルールセットではCapability API 1.43です。

### ウィンドウ: 戦闘を保留する

一部の瞬間には、現在の実行者とは別の者に判断権があります。Engineは代わりに決めず、その者のために戦闘を保留します。この一時停止がウィンドウです。

ウィンドウを開く状況は6つで、そのうち2つはすでに宣言した内容に由来します。

- **誰かが離れる。** 攻撃可能な敵の間合いから出る歩行は、その一歩で止まり、敵に尋ねます。前述の「離れていく相手への打撃」を参照してください。
- **あるターンと次のターンの間。** ターン終了時、次のターンが始まる前に、`signaturePoints`を持ち、自身の`signature`アクションのいずれかを支払える敵全員へ、購入するかを尋ねます。購入できるのはこの瞬間だけです。固有アクションは、自身も含め誰のターンメニューにも出ません。
- **誰かが何かを使う。** 解決前に、それが誰に向けられたかにかかわらず、反対側の者のうち、その瞬間を待つ項目を持つ全員に尋ねます。ただし、その項目が使用者に届く場合に限ります。標準アクションと対抗判定はこの瞬間を開きません。
- **何かが誰かに向けられる。** 解決前に、それが向けられた反対側の者のうち、その瞬間を待つ項目を持つ全員に尋ねます。味方からの回復は対処すべき脅威ではないため、味方のアクションはウィンドウを開きません。
- **攻撃判定が誰かに命中する。** ダメージの前に、命中を受けた者がその瞬間を待つ項目を持っていれば、その者に尋ねます。その者が実行したことはこの攻撃に反映されます。後述の「命中直後の瞬間」を参照してください。
- **何かが誰かを傷つけた。** 解決後、誰が行ったかに関係なく、ダメージを受けた者のうち、その瞬間を待つ項目を持つ全員に尋ねます。傷ついたことは自身の事実ですが、加害者に向け返す項目を味方に向けることは依然としてできません。

最後の4つは、カタログ項目やクリーチャー自身のアクションが、待つ瞬間を指定して求めるものです。1つのアクションが`used`と`aimed`の両方を開く場合は、まず使用について尋ね、誰も取り消さなければ次に向けられた者に尋ね、両方の回答後に解決します。命中は各ロールが命中するたびに、負傷はアクション全体の終了後に尋ねます。

どの状況で開いた場合も、ウィンドウは次のように動作します。

- **開いている間は、ほかは何も動きません。** 現在のターンの実行者も、ターン終了も、別のウィンドウも進みません。戦闘は待機します。
- **行動順に1人ずつ尋ね、各自に1回だけ尋ねます。** 見送りは常に有効な返答で、コストはありません。尋ねる対象に実行可能なものがなければ、質問せず飛ばします。
- **止めた場所から正確に再開します。** 歩行は残りのマスを進み、実際に通った各マスのコストを支払って完了します。
- **操作担当が答えます。** 自分のパーティーメンバーのウィンドウは自分で答え、メニューに選択肢とPassが並びます。敵はその操作担当が答え、Game MasterのボスはGame Masterに尋ねます。機会を見送ることも返答の1つです。
- **戦闘と一緒に保存します。** 歩行の途中で閉じたゲームを再開しても、尋ねる相手と残りのマスは同じです。

最初の2つに追加の宣言は不要です。`opportunity.budget`があるルールセットは一方を、`signaturePoints`があるベスティアリはもう一方を得ます。どちらもなければ表示されません。

**項目がどの瞬間を待つかを指定する。** `mechanics.reaction`を`true`ではなくオブジェクトで書きます。

```json
"reaction": { "on": "aimed", "at": "source", "cancels": true }
```

- `on`は`used`、`aimed`、`hit`、`harmed`のいずれかで、そのウィンドウのメニューに項目を載せる指定です。Engineが監視する瞬間はこの4つだけです。依然として`"reaction": true`とだけ書かれた項目は、ターン中に実行しないことしか伝えません。どこかに提示するには不十分なので、どのメニューにも出ません。
- `at`は`source`(デフォルト)か`chosen`です。`source`はその瞬間を生じさせた相手へ実行内容を向け、標的を自動入力するため、選択を求めません。`chosen`は項目自身の対象設定を保ち、選択を求めます。
- `cancels`は、ウィンドウが保留していた内容自体の発生を止めます。指定できるのは`used`か`aimed`の項目だけです。すでに起きた瞬間は取り消せず、命中は判定済みだからです。
- `against`は、項目が応じる対象を特定のカタログから使われたものに絞ります。`"against": { "catalogs": ["spells"] }`は呪文だけに応じます。背後に項目のないアクション(リストの武器、クリーチャー自身のアクション)はどのカタログにも由来しないため、カタログを指定する項目の瞬間を開きません。`against`を省略すると、項目は何にでも応じます。

`budget`も指定してください。なければリストのデフォルトを消費します。リアクションはほとんどの場合、専用の行動枠を使います。これが1ターンに複数回使うことを防ぎます。

**コストは誰かに尋ねる前に消費済みです。** キャンセルされたアクションは発生を止められるだけで、購入自体は取り消されません。行動枠とプールはすでに失われています。独自のシステムで返却する場合も、まだ表現できません。

対抗手段は次のように書き、盤面上では自身の`range`内の者だけに応じます。

```json
"mechanics": {
  "kind": "utility",
  "range": 8,
  "free": true,
  "cost": [{ "pool": "luck", "amount": 1 }],
  "reaction": { "on": "used", "cancels": true, "against": { "catalogs": ["knacks"] } }
}
```

**命中直後の瞬間。** `hit`の項目で、Shield、Parry、Uncanny Dodgeを表します。攻撃は判定の後で保留され、ダメージを与える前に命中を受けた者に尋ねます。その者が実行したことはその攻撃に反映されます。判定は振り直さず、その時点の防御に対して再確認するため、防御に加算する状態で命中を外れに変えられます。常に命中する出目はそれでも命中します。応答として付与した、1回の攻撃の間続く状態(`endsAfter: "attacked"`)は、ダメージも含めてこの攻撃に適用され、この攻撃で消費されます。「その攻撃のダメージを半減する」は、1回の攻撃に対する`resist-all`で表します。

```json
"mechanics": {
  "kind": "buff",
  "targets": "self",
  "budget": "reaction",
  "reaction": { "on": "hit" },
  "applies": [{ "condition": "shielded", "duration": { "rounds": 1, "at": "turn-start" } }]
}
```

攻撃は保留した場所から正確に再開します。残りの標的と、ほかのアクションで構成するクリーチャーのアクションなら残りの部分です。そうした応答を持つ者に命中した各ロールは順番に保留され、ウィンドウが開いている間に保存した戦闘も同じ状態で戻ります。ウィンドウ内で行った攻撃(離れていく相手への打撃、固有アクション、応答)は保留しません。ウィンドウ内で開いたものは別のウィンドウを開かないためです。ログは、ウィンドウが開いたときにロールとその対象値を示し、応答が防御を変えた場合は外れになったかを示します。Engineが操作する敵は、命中を外れに変えられる場合だけ防御手段を使います。

瞬間を指定するパッケージにはCapability API 1.33が、`used`や`against`を使うものには1.44が必要です。`hit`を待つものには1.46が必要です。

### 未対応

ルールセットがEngineにできないことを主張しないよう、明記します。

- **簡素な盤面を超えるもの:** 四分の三遮蔽と完全遮蔽、高低差、障害物の上を飛ぶこと、狭所の通過、騎乗、隠れ身や不意打ちはありません。自身の歩行と対抗判定の押し出し以外で誰かが動くこともありません。掴んでいるクリーチャーを引きずることもできません。
- **対抗判定は簡素です。** サイズによる制限はなく、ウィンドウも開きません(誰も対抗判定に応答できません)。
- **項目が待てる瞬間は`used`、`aimed`、`hit`、`harmed`の4つだけです**(前述の「ウィンドウ」を参照)。Engineはこれらを項目のために検知します。ほかの2つのウィンドウ、つまり離脱とターン間の一時停止は戦闘自身が開くもので、項目から求める瞬間ではありません。セーヴの判定、死亡、ターン開始、落下に対応する瞬間はありません。
- **対抗手段は応じた対象を完全に止めます。** カタログ内の項目を区別できず、自分より大きなものを止めるための判定もありません。
- **連鎖しません。** 戦闘はウィンドウをスタックではなく1つだけ保持するため、ウィンドウ内で起きたことは別のウィンドウを開きません。対抗にさらに対抗することはできず、リアクションの効果も追加の瞬間を開かず、ウィンドウ内で行った攻撃は命中しても保留されません。
- **命中となるのは攻撃判定だけです。** 攻撃判定なしで当たるもの(単に命中するダーツ、全員がセーヴする範囲)は`hit`の瞬間を開きません。応答は近接と射撃を区別できないため、ルール上は剣にしか使えないParryでも矢を受け流します。
- **ダメージは量ではなく半減で変えます。** 応答で1回の攻撃の被害を半分にはできます(その攻撃に対する`resist-all`)が、振った数値から差し引くことはできません。
- **返却はありません。** キャンセルされたアクションのコストは消費済みです。
- **状態が変えるものは固定リストです。** 防御、攻撃判定、セーヴ、対抗判定、速度だけです(段階と、戦闘中のアイテムの効果も同様です)。持ち主が与えるダメージへのボーナスや、キャラクターの最大値を下げる段階、戦闘から脱落させる段階はありません。
- **数値で直接書いたクリーチャーには負傷トラックがありません。** 体力がトラックのルールセットでも、そのようなクリーチャーは点数を失います。`sheet`を与えると、受ける打撃は自身の`resist`、`vulnerable`、`immune`で先に軽減した後、マスに印を付けます。
- **追加効果は自動発動します。** `on`の値は`hit`だけなので、各期間で最初の条件を満たす命中が効果を使います。消費するか尋ねる瞬間はありません。
- **攻撃で動く数値は簡素です。** 費やす打撃は数値だけを振り、ほかには何もないため、武器がそれを変えることはなく、`floor`も同様です(頑丈な標的は奪う打撃を吸収し、硬度は費やす打撃を止めますが、それ以外にどちらかを小さくするものはありません)。クラッシュはどれだけ深くても決まったターン数の後に解けます。ウィンドウ内で行う攻撃(離脱する相手への打撃、リアクション、固有の行動)は最初のスタイルで行います。
- **作られた敵は何も吸収せず、硬度もありません。** GMが1回の戦闘のために作るクリーチャーは脅威尺度に制限され、尺度は吸収や硬度について何も示さないため、どちらも持ちません。

## レイヤー: ルールセット自身のバリエーション

レイヤーはLow magic、Hard winter、より過酷な難易度など、ゲーム作成時にプレイヤーがオンにする名前付きのルールセット変種です。ルールセットファイル内の任意の`layers`配列に置くため、一緒に移動し、使用したゲームから失われることはありません。ウィザードではルールセットの下にトグルとして表示し、ルールセット自身と同じく、そのゲームの存続中は選択を固定します。

```json
"layers": [
  {
    "id": "hard_winter",
    "label": "Hard winter",
    "summary": "Cold, hunger and short days. Everything is harder.",
    "conflicts": ["mud_season"],
    "gm": {
      "guidance": "Hard winter is on. Let a failed check cost warmth, food or daylight as well as progress.",
      "worldGuidance": "Hard winter is on. Build a world of closed roads, thin stores and rationed settlements."
    },
    "fields": [{ "id": "calling", "removeValues": ["Sailor"], "default": "Hauler" }],
    "difficultyLadder": [{ "label": "Easy", "dc": 7 }],
    "catalogs": [{ "id": "knacks", "hide": { "filter": "grit", "above": 0 } }]
  },
  {
    "id": "mud_season",
    "label": "Mud season",
    "summary": "Thaw, flooded roads and slow going."
  }
]
```

**レイヤーにできること。** リストは固定されており、各効果は何かを絞り込むか、文章を追加します。

- `gm.guidance`は`gm.checkGuidance`へ、作者自身の文章と先行するレイヤーの後に追加します。`gm.worldGuidance`も同様に`gm.worldGuidance`へ追加します。
- `fields`は**enum**フィールドから値を除きます。`removeValues`はフィールドがすでに持つ値を指定し、少なくとも1つを残す必要があります。フィールドの`default`も除く場合、レイヤーは残る値を代わりの`default`に指定します。
- `difficultyLadder`は独自の解決方式と同じ形で難易度表を置き換えます。`dice-sum`なら`{label, dc}`、`dice-pool`なら`{label, successes, target?}`です。元の表とまったく同じ検証を受けます。複数の有効なレイヤーが宣言した場合は、最後のものが優先されます。
- `catalogs`はシートエディターの選択画面から項目を隠します。各ルールはカタログに宣言した`filters`の1つと、ちょうど1つの比較を指定します。`number`フィルターなら`above`か`below`、`text`や`tags`なら`equals`か`notIn`です。そのフィルターをまったく設定していない項目は隠しません。
- `currencies`は硬貨を除きます。`removeUnits`は個々の硬貨を、`removeFamilies`は系統全体を指定します。系統の最小硬貨は系統ごとにしか除けないため、残る系統はすべて支払いとお釣りが可能です。レイヤーの有効中、除かれた硬貨は誰も得たり、支払いに使ったり、選んだり、落としたりせず、財布の行にも表示しません。その硬貨で示す価格は、残る硬貨のうちちょうど払える最大のもので、同じ価値として示します。GravewatchのThe long nightはcrownを除くため、3 crownsのWatch pistolは15 shillingsです。系統全体がなくなったアイテムには価格がありません。

**レイヤーにできないこと。** 列挙値、フィールド、スキル、プール、休息の追加、解決方式の変更、ライブ状態や戦闘数値の変更、モデル呼び出しの追加はできません。レイヤーが_追加した_値は、シートを読むほかのすべての処理には未知となるため、値は除く方向だけです。このリストを超える変更は、ルールセット自身の変更か、別のルールセットになります。

**競合。** `conflicts`は同時に有効にできないレイヤーを指定します。組の片方だけに書けば十分です。ウィザードは相手のトグルを無効にし、保存済みの選択になぜか両方がある場合は、**後で**宣言された方を削除します。そのため、同じ2つの選択からは常に同じルールが得られます。

**除外された値をすでに持つシートは、その値を保ちます。** キャラクターを書き換えるものはありません。エディターが選択肢として出さなくなるだけで、すでに持つキャラクターにはそのまま表示します。新しいゲームでレイヤーをオフにすれば、再び選べます。隠したカタログ項目も同じです。選択画面からは消えますが、プレイヤーがすでに選んだ行はシートに残ります。レイヤーが除いた硬貨をすでに持っている場合は、袋に残ります。

**制限。** ルールセットごとに12レイヤー、各レイヤーのガイダンスは2つの文字列を合わせて4000文字です。`layers`または基本の`gm.worldGuidance`を宣言するパッケージ化されたルールセットにはCapability API 1.25が、硬貨を除くレイヤーを持つものには1.64が必要です。インポートするルールセットは読み取るEngineが検証するため、この宣言は不要です。

**他者が書くレイヤー**(自分が書いていないルールセット向けのLow Magicレイヤーを独立したファイルで配布するもの)は、今後の追加事項です。現在は、所属するルールセットの中で配布します。

## ルールセットを試す

コミュニティのルールセットは、インポートするエージェントと同じスイッチを使います。**Settings**(設定)>**Advanced**(詳細設定)>**Danger Zone**(危険な操作)を開き、**Allow custom Agent imports**(カスタムエージェントのインポートを許可)がオンであることを確認してください。インポートにはlocalhostからのアクセスか、設定済みの**Admin Access**(管理者アクセス)も必要です。

1. **Agents**(エージェント)パネルを開き、**Import agents**(エージェントをインポート)ボタン(パネル上部のボタン列のダウンロードアイコン)を選びます。
2. **Game Mode ruleset**(Game Modeのルールセット)を選び、JSONファイルを指定します。
3. 確認画面を読みます。名前、バージョン、ライセンス、対応範囲、Game Master向け文章が表示されます。**Import**(インポート)を選びます。

ルールセットはパネルの**Rules**(ルール)セクションと、新しいゲームの設定ウィザードの**Rules**選択肢に表示されます。ファイルからインポートしたものは`local/<your id>`として分類するため、公式や他者のルールセットと混同することはありません。

### インポート済みルールセットの変更

インポートしたバージョンは上書きしません。ファイルを変更して同じ`version`で再インポートすると、拒否され、番号を上げるよう求められます。これは意図した動作です。ゲームは作成時の正確なバージョンに結び付くため、進行中のキャンペーンが突然別の計算方式になることはありません。

草案を作るときは、編集、`version`の更新、インポート、新しいゲームの開始を繰り返します。旧版は**Rules**セクションからルールセットを削除するまで、新版と並んでインストールされたままです。ゲームがまだ使っているルールセットを削除すると、再インポートするまでそのゲームにルールセットが見つからないと表示されます。

シートの形(項目の追加、削除、名前変更)を変えた場合は、`sheet.version`も上げてください。既存のシートは寛容に読み取ります。新しいシートにとって未知の値も保ち、ない値にはデフォルトを使います。

## ルールセットの共有

**ファイルで。** JSONファイルを友人に送ります。友人も同じ方法でインポートできます。

**GitHubリポジトリから。** 公開GitHubリポジトリで作業を管理している場合、リポジトリ直下の`rulesets`フォルダーに、ルールセットごとに1ファイルずつ置きます。

```text
your-repository/
  agents.json        (optional, only if you also share agents)
  rulesets/
    ember-roads.json
    another-system.json
```

ユーザーはカスタムエージェントのリポジトリ一覧から一度リポジトリを追加し、内容を確認して、後から同期して新版を取得できます。カスタムリポジトリ一覧は詳細機能で、サーバーの運用者が`ENABLE_CUSTOM_AGENT_REPOS=true`で有効にする必要があります。リポジトリ由来のルールセットは`alice/ember-roads`のように所有者名の下へ分類するため、2人の作者がどちらも`v20`という名前で公開しても競合しません。

制限は2つです。リポジトリの`rulesets`直下に置けるJSONファイルは最大32個で、超えるリポジトリは拒否されます。`local/`はファイルからインポートするルールセット用に予約しているため、`local`というアカウント名ではルールセットを公開できません。

**公式カタログで。** 広く遊ばれ、ライセンスが明確なシステムは、**Download Agents**(エージェントをダウンロード)を通じて全員へ提供できます。[Marinara-Agents](https://github.com/Pasta-Devs/Marinara-Agents)リポジトリへのプルリクエストで行います。構成はそこの`ruleset-5e-2014`パッケージを参考にしてください。

## ライセンス

共有する権利のあるルールの文章だけを公開してください。多くのシステムはオープンライセンスの参照文書を公開しており、複製してよいのはその文書です。ライセンスIDと、ライセンスが要求する帰属表示を`license`に入れてください。オープンライセンスでないルールブックの文章をコピーしないでください。ルールセットに主に必要なのは名前と数値で、Game Master向け文章は自分の言葉で書いてください。

## トラブルシューティング

- **インポート時に名前が存在しないと言われる。** ファイル内の何かが未宣言のIDを参照しています。削除した能力値をスキルが指定している場合などです。メッセージに該当箇所へのパスが表示されます。
- **インポート時に同じバージョンが別の内容でインストール済みと言われる。** `version`を上げて再インポートしてください。
- **設定ウィザードにルールセットが出ない。** **Allow custom Agent imports**がオンか確認してください。オフの間は、インポートしたルールセットを新しいゲームに提示しません。すでに使用しているゲームは動き続けます。
- **ゲームにルールセットが見つからないと表示される。** ゲーム作成時の正確なバージョンがインストールされていません。そのバージョンのファイルを再インポートしてください。
